## Goal

Plan change D-3862: `tests/e2e/webserver.ts:132` gives the keyed binary a random `ASKHAVA_STRIPE_WEBHOOK_SECRET` that no spec can read. The stand-in signs its deliveries with its own default `whsec_fake` (`stand_ins/stripe.py:82`; `/_stand_in/stripe/webhook`, `stand_in_authenticate`), so no spec can post a webhook the keyed binary accepts, and T099's post-payment closing checks (D-1739) cannot run. `confirm_served.spec.ts` stops at "waiting" for this reason. (1) `tests/e2e/webserver.ts`: `keyedSecrets()` also makes the webhook secret, `whsec_` plus 24 random bytes in hex. It is made once per run in the Playwright main process and passed to the workers as `E2E_KEYED_STRIPE_WEBHOOK_SECRET`, like the ID secret and vault keys. `keyedEnv` gives the keyed binary that same value. Nothing prints or logs it, and the suite's own binaries never see it. (2) `tests/e2e/keyed.ts`: `stripeDelivery(payload: string, timestamp: number)` returns the headers of Stripe's scheme, `Stripe-Signature: t=<timestamp>,v1=<hex HMAC-SHA256(secret, "<t>.<payload>")>`, the scheme `stand_ins/stripe.py:67` uses, built with Node's `crypto` only. The payload is a serialization of an event object the stand-in emitted, for example the `json.dumps(event, sort_keys=True)` form `stand_in_authenticate` already returns in `payload` (`stand_ins/stripe.py:296`, `:404`), or the event as `GET /stripe/v1/events` lists it, signed exactly as it is sent. The timestamp is real time: the webhook measures its tolerance on `SystemClock` (`app/server/src/release_sink.rs:313`). The app's checks are unchanged: signature, 5-minute tolerance and stand-in source host (`app/payments/src/routes.rs`). (3) `stand_ins/stripe.py`: `_event` (`:95` to `:99`) emits only `id`, `object`, `type` and `data`, but the app's envelope requires `livemode` (`app/payments/src/routes.rs:232`). Without it `checked` gives nothing and `receive` answers 200 with nothing done (`:187` to `:189`, `:245` to `:253`). So `_event` adds `"livemode": False` and nothing else; real Stripe events always carry it. Plan change D-3869 (Fable's triage, recorded in D-3863): the stand-in PaymentIntent has no `livemode` either (`_intent`, `:169` to `:183`). `paid_release` re-fetches the intent and refuses a missing `livemode` as `WrongMode` (`app/payments/src/release_proof.rs:359`; `app/adapters/src/payments.rs:54` to `:57`). So `_intent` also adds `"livemode": False` and nothing else. `tests/contract/test_stand_in_server.py` gains cases showing every emitted event and every created or fetched intent carries `livemode: false`, and the other stand-in contract tests pass unchanged. `app/adapters/src/tests/ssrf_guard.rs:489` asserts the stand-in intent's `livemode` is `None`; it becomes `Some(false)`. `app/adapters/src/payments.rs`: the doc comment at `:54` to `:56` only; no code in `payments.rs` changes. That comment no longer says the stand-in omits `livemode`, and still says `None` is a mismatch in every mode. No Twin or contract test compares an intent's exact key set. (4) `tests/e2e/keyed_stripe.spec.ts` gains these cases. Proving the effect: hand-seeding a pick and an intent would miss what `paid_release` checks (`app/payments/src/release_proof.rs:206`): the stored intent in `payments.pick_intent` and the re-fetched intent's metadata, which the Confirm path supplies. The release also needs the job's homeowner: with no open `intake.conversation` on the job, the release is `MovedOn` with a High alert and no `picks.release` row (`app/server/src/release_sink.rs:155` to `:157`, `:178` to `:193`; `app/intake/src/models.rs:886`). So the case reaches "waiting" through `confirm_served.spec.ts`'s seed-and-Confirm path (`seedPick`, `:49` to `:93`; the Confirm flow, `:270` to `:277`), then delivers the stand-in's `payment_intent.succeeded` for that intent with `stripeDelivery`. Those helpers are not exported, so T515 moves them (round 3) rather than copying them. `seedPick`, its `psql` helper and the Confirm-to-"waiting" steps leave `confirm_served.spec.ts` and become exported helpers in `tests/e2e/keyed.ts`. The moved `seedPick` also inserts an `intake.homeowner`, an open `intake.conversation` on the job, and a `privacy.contact` sealed with `seal` (fake name, phone and street, as `business_portal_served.spec.ts:5` to `:9` describes). It takes `{ business?, feeCents = 2500 }`, so T099 can use it for a $75 pick on its own signed-up business. `confirm_served.spec.ts` imports them, its test steps and assertions unchanged, and passes unchanged. `keyed_stripe.spec.ts` uses the same helpers. The pick is then released once and recorded once (one release row), and a second delivery of the same event adds nothing. Refusals: the same payload with the stand-in's own default signature, with one changed byte, or with a timestamp outside the tolerance is refused (403). The existing bad-signature case is unchanged. The stand-in still signs with its own default secret, the run's secret stays random, and signature checking is not weakened. Update `docs/decisions.md`.

Acceptance: `tests/e2e/keyed_stripe.spec.ts` passes in the end-to-end run: a pick brought to "waiting" through the seed-and-Confirm path, whose stand-in `payment_intent.succeeded` is then delivered with `stripeDelivery`, is released and recorded once, and a second delivery adds nothing; the default-secret, altered-byte and stale-timestamp deliveries are refused. `tests/contract/test_stand_in_server.py` shows every stand-in event carries `livemode: false`. Every stand-in intent carries `livemode: false` too, and `ssrf_guard.rs` passes with `Some(false)`. In `app/adapters/src/payments.rs`, only the doc comment at `:54` to `:56` changes; no code in `payments.rs` changes. `confirm_served.spec.ts` passes with its steps and assertions unchanged, now using the moved helpers from `keyed.ts` and the richer seed. Every other stand-in contract test and end-to-end spec passes unchanged, and the secret appears in no log or report.
