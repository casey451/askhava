## Goal

Plan change D-4174 (the Opus triage of T594's attempt 1, Nov 17, 2026, checked on `main` f911c8f): T489's chat layer refuses every same-site `POST /request`, and the request page lacks CON-025's 18-or-older line, so T594's end-to-end spec cannot pass; this task fixes both in T489's files (T489 is done) and adds the route test that would have caught the first. (1) SEC-042: `posted_csrf` (`app/server/src/chat_codes.rs:186` to `:201`) re-reads the buffered body through `Request::builder()` with no method, so the rebuilt request is a `GET`, axum's `Form` reads a `GET`'s form from the query string (empty: the builder's URI is `/`), the posted `csrf` is always empty, `csrf_matches` (`app/portals/src/session.rs:327` to `:330`) is false and `check_token` (`chat_codes.rs:171` to `:172`) answers 403 with a `csrf_rejected` event to every `POST`, a right token included. The fix is `.method(Method::POST)` on that builder (`Method` is already imported, `:35`), nothing else in the layer: the order of checks (cross-site refusal outermost, then the token, `POST` only, D-4120 trap (a)), the 403 and its one event per refusal (SEC-048), the body limit, `no-store`, the pre-session cookie and the `ChatCsrf` hand-off stay as they are, and the refusal function is still not spelled `refused(` (D-4120 trap (b)). The bug fails closed: the empty string never equals the 64-hex token, so no forged or missing token was ever accepted, and after the fix a missing, empty, wrong or other-cookie token is still refused. (2) CON-025 (`docs/spec/consent.md:29`: "the start screen says the user must be 18 or older"; TD-CON-10, `docs/test-design.md:349`): `app/site/templates/request.html` shows the line `You must be 18 or older to use {{ brand }}.` (the `brand` already bound at `:10`) in its own `<p>` right after the English consent text (`:17`) and above the chat box, on every step, outside `lang="es"`; it is plain copy (no `data-fixed`: CON-025 fixes the fact, not the wording), so `scripts/check_copy.py` measures it and reports 0 problems; no Spanish copy is added (WEB-006 covers only the consent draft). Nothing else on the page changes, so the `/request` `PAGE_STATES` entries in `tests/a11y/page_states.ts` stay valid and are not edited, and `Ally` stays at 0 violations. (3) Why T489's tests missed it: `app/site/src/chat.rs`'s unit tests call `chat_routes` directly, without `server`'s guard (`chat.rs:524`); `app/server/tests/door_matrix.rs` only proves refusals (`probe_csrf`, `:1263`, a cross-site and a wrong-token `POST`) and accepts any answer below 500 for a Public `POST` with the actor's own token (`judge`, `:448`), so a 403 passed; `app/server/tests/route_wiring.rs` probes with a bodiless `PROBE` request. So this task adds `app/server/tests/web_chat_route.rs` (TD-SEC-72; fake data only, no real number, the router built with `build_router` and `RouterParts::from((None, None, None, None))` as `app/server/tests/business_signin_route.rs:142` to `:143` does, so no code is sent and the code step answers below 500, D-3744; security events counted from the captured log lines as `app/server/tests/owner_signin_route.rs:290` does): a `GET /request` sets the pre-session cookie, shows the token in the form's `csrf` field and shows the 18-or-older line before the form; a same-origin `POST /request` with that cookie, that token and a job message is not a 403, is `no-store`, records no `csrf_rejected` event and answers below 500 with the posted words in the page's chat list (the `<ol>` T594's spec reads); the same `POST` with no `csrf` field, an empty one, a 64-zero token or the token of another pre-session cookie is a 403 with exactly one `csrf_rejected` event for `/request` and changes nothing; a cross-site `POST` (`Sec-Fetch-Site: cross-site`) with the right token is still a 403 with one event. Two traps in that test: (i) the accepted `POST` must carry what `chat.rs`'s `post` handler needs, or it answers 400 with no chat list: the form is `Posted` (`app/site/src/chat.rs:131` to `:141`, `deny_unknown_fields`, so no field outside `csrf`, `chat`, `message`, `g`, `said`, `step`, `words`, `number`, `code`), `chat` a 32-hex key not all zeros (`Turn::posted`, `:176` to `:188`), `message` a UUID (`Uuid::try_parse`, `:292` to `:295`), `step=message` and `words` that are not empty after scrubbing (fake job words with no name or number, `:318` to `:321`); (ii) `is_cross_site` (`app/portals/src/security.rs:334` to `:341`) treats a `POST` with neither `Sec-Fetch-Site` nor `Origin` as cross-site, so every same-site request in the test sends `Sec-Fetch-Site: same-origin` (or an `Origin` of `https://` plus the request's `Host`), as `door_matrix.rs`'s `request` does (`:347` to `:379`); a refusal case differs from the accepted one only in its token or its site header. The test fails on `main` today (the first case) and passes with fix (1). `door_matrix.rs`, `route_wiring.rs`, `tests/security/tests/auth_matrix.rs`, `security_event_cap.rs` and `chat.rs` are not changed and still pass.
