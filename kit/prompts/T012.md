## Goal

`core` owns the PostgreSQL pool, the `sqlx` migrations run by `server migrate` with the app role and the migration role kept apart, and the row-lock helper every status change uses, applying a change only while the row is still in the expected status (JOB-004). Per the skeleton trial (D-488): `MIGRATOR = sqlx::migrate!("../../migrations")`, `build.rs` from `sqlx migrate build-script --source ../../migrations` plus a `//!` line, and `app/core/sqlx.toml` with the uppercase `TIMESTAMPTZ` override to `jiff_sqlx::Timestamp`. Per the second trial (D-491): `scripts/bootstrap_roles.sql` creates `askhava_migrator` and `askhava_app` idempotently with the grants section 1 of the trial report lists (test-cluster extras behind a flag); migrations write `ALTER DEFAULT PRIVILEGES IN SCHEMA x` with no `FOR ROLE`; every migration and `#[sqlx::test]` runs as the migrator; `Guarded<T>` is the JOB-004 outcome and each module writes its own guarded `UPDATE`; `-- no-transaction` is line 1 when used; test database names are a hash shared across the cluster, so one role only.

Acceptance: `cargo test -p askhava-integration --test migrations` shows the migrations apply in order on an empty database; on a test append-only table in `core` the app role (`askhava_app`, created by `scripts/smoke.sh` and `Ci` before any migration, D-491) can INSERT and SELECT but its UPDATE and DELETE fail with a permission error; every GRANT in a migration is guarded so a missing role is reported, never silently skipped; a status change with a stale expected status changes nothing and returns none (JOB-004).

### 2. Principles (lines naming this task's requirements)
**P10. Timeouts on the app role, set by the migration role.** `idle_in_transaction_session_timeout` exists so "idle sessions do not hold locks for an unreasonable amount of time", and an open transaction "prevents vacuuming away recently-dead tuples" (docs via https://postgresqlco.nf/doc/en/param/idle_in_transaction_session_timeout/); default 0 = off. strong_migrations suggests app `statement_timeout` about 15 s and `lock_timeout` about 10 s, migrations `lock_timeout` about 10 s and a long `statement_timeout`, set with `ALTER ROLE`. `transaction_timeout` arrived in PostgreSQL 17 (https://bytebase.com/blog/postgres-timeout), so it does not exist on PG 16. ### 2. Principles that bind this codebase (lines naming this task's requirements)
**R11.
