## Goal

`core` owns the PostgreSQL pool, the `sqlx` migrations run by `server migrate` with the app role and the migration role kept apart, and the row-lock helper every status change uses, applying a change only while the row is still in the expected status (JOB-004). Per the skeleton trial (D-488): `MIGRATOR = sqlx::migrate!("../../migrations")`, `build.rs` from `sqlx migrate build-script --source ../../migrations` plus a `//!` line, and `app/core/sqlx.toml` with the uppercase `TIMESTAMPTZ` override to `jiff_sqlx::Timestamp`. Per the second trial (D-491): `scripts/bootstrap_roles.sql` creates `askhava_migrator` and `askhava_app` idempotently with the grants section 1 of the trial report lists (test-cluster extras behind a flag); migrations write `ALTER DEFAULT PRIVILEGES IN SCHEMA x` with no `FOR ROLE`; migrations and `#[sqlx::test]` run as the database's migration identity (`askhava_ci` in smoke and Ci, `askhava_migrator` on Railway) (D-492); `Guarded<T>` is the JOB-004 outcome and each module writes its own guarded `UPDATE`; `-- no-transaction` is line 1 when used; test database names are a hash shared across the cluster, so one role only.

Acceptance: `cargo test -p askhava-integration --test migrations` shows the migrations apply in order on an empty database; on a test append-only table in `core` the app role (`askhava_app`, created by `scripts/smoke.sh` and `Ci` before any migration, D-491) can INSERT and SELECT but its UPDATE and DELETE fail with a permission error; every GRANT in a migration is guarded so a missing role is reported, never silently skipped; a status change with a stale expected status changes nothing and returns none (JOB-004).
