# T259: payments: the Stripe webhook dispatches refund, dispute and early-fraud events once each by event ID

## Goal

`app/payments/src/routes.rs` acts only on `payment_intent.succeeded`; every other verified event answers 200 and does nothing, so `refunds::refund_failed`, `disputes::record_dispute` and `refunds::early_fraud_warning` are never reached from Stripe, and no event is recorded by ID (D-1543, D-1545; SEC-017; external audit A08, D-1754). (1) Record each event in `payments.webhook_event` (created by T258's migration), written in the same transaction as the event's effect, so a repeat answers 200 and changes nothing (architecture section 7's per-module `webhook_event`). (2) Dispatch: `refund.updated` and `charge.refund.updated` by the refund's status to T258's `refund_succeeded`, `refund_failed` or `refund_canceled`; `refund.failed` to `refund_failed`; `charge.dispute.created` to `record_dispute`; `charge.dispute.closed` records an audit row and one High alert for Casey (no money moves, D-1545); `radar.early_fraud_warning.created` enqueues, in the event's transaction, a `picks.fraud_warning` task for the charge's pick, which T281's handler runs through `picks::api::fraud_warning` (it calls `early_fraud_warning`, so the alert, the refund of an unreleased charge and the job's return happen together, FEE-052, D-1845); `payment_intent.succeeded` as now through the `ReleaseSink`. An out-of-order event (a `refund.updated` succeeded after failed) leaves the row in the state Stripe now reports, by refetching the refund through the adapter when the order is ambiguous. A database error answers 500 so Stripe resends; an event for an unknown object answers 200 with nothing changed. The production `ReleaseSink` and the router merge are T254's (D-1739). Update the `payments` `CLAUDE.md` and `docs/decisions.md`.

Acceptance: TD-FEE-43 passes against PostgreSQL with signed fake events; every existing TD-SEC-31 and TD-FEE-25 case in `routes.rs` still passes.
