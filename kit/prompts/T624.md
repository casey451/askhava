OPS-004 alerts Casey when "the 5-minute health check fails twice". The new `app/server/src/health_watch.rs` registers one worker task kind in `server::worker_registry` (the shared `app/server/src/lib.rs`) that runs, every 5 minutes, the check T106's `/healthz` runs, through T106's `pub(crate)` `healthz::check(pool, now, &limits)`, called as it is (this task does not edit `healthz.rs`); `limits` is built with `HealthLimits::from_pairs` from the worker's `pairs` in `worker_registry`. The chain follows `app/server/src/no_handler_alert.rs` (`schedule` and `run_check`): every due time is a 5-minute slot start (the epoch second divided by 300), and the start-up seed from `schedule_start` and every chained run use the same dedupe key `<kind>.<slot>`, so a restart whose slot is already queued or run queues nothing and the chain never multiplies. The next run's slot is 1 plus the larger of the run's own slot (from its due time, the slot its dedupe key names) and the slot holding `now`, so an application clock slightly behind the database clock can never make the next key equal the run's own and silently end the chain; a late run after downtime and the start-up seed then merge into one chain. Each run first checks, writing nothing; then in one transaction it queues the next slot's run with this check's result in the payload (`{"health_failed": bool}`; the seed carries `false`) and raises or clears the alert. So two failures in a row need no stored row and no in-memory state. A dead-lettered run stops the chain until the next start-up seeds it again; T366's dead-letter alert reports that. Like `no_handler_alert`, it raises and clears only in test and live: in dev and `Ci` each run still checks and queues the next slot but raises nothing. The second failure in a row raises one High `ops.health_check_failed` alert (`ops::api::HEALTH_ALERT`) through `ops::api::raise_kind_once`; the first passing check clears an open one through T204's kind-taking `ops::api::acknowledge_cleared` (OPS-023, D-220). The in-process check covers the database and the worker only; an unreachable web process is UptimeRobot's alone (OPS-007). Raising at the second failure (about 5 minutes) lets T204's push fire when the alert is still open 10 minutes after it was raised. Tests in the new `tests/integration/tests/health_watch.rs` (TD-OPS-44's health-check cases, its row amended by D-4280), fake data only, the failing check planted by the test: two failed checks in a row raise one alert, one raises none, one passing check clears it; a second start-up in the same slot queues no second run; a run whose `now` is 1 second before its own slot's start still queues the next slot (its own slot plus 1); and TD-OPS-08's health case: failing at 0 and 5 minutes and passing at 10 gives no push (an auto-acknowledged alert), still failing at 15 gives the push. Update the `server` `NOTES.md` (including one line that `HEALTH_ALERT`'s doc comment in `app/ops/src/alerts.rs`, "raised by T518", now means T624) and `docs/decisions.md`. Shared worker cap (D-4280): `schedule_start` in the shared `app/server/src/bin/worker.rs` already counts about 47 of clippy's 50 body lines (`too_many_lines` is denied), so whichever task adds a seed first folds the new seeds into one helper (for example `schedule_checks(&mut conn, now)`, called once from `schedule_start`) instead of appending three more lines, and keeps every existing seed, its order and its dedupe key.
