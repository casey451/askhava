# T022: privacy: encrypted contact vault, blind index, audited plaintext reads

## Goal

`privacy` holds the contact vault: every homeowner contact field encrypted field by field with AES-256-GCM under `VAULT_KEY` with associated data and a key version, phone lookup by a per-purpose HMAC blind index, every plaintext read audit-logged with its reader and purpose, realm reads gated by session proof types, the key inventory and escrow recorded by T117, and an alert when reads exceed three times their baseline (PRIV-001 to PRIV-004, PRIV-024, SEC-046, SEC-047); its tests meet the 95% `app/privacy` floor T169 wrote into `tests/coverage_floor.json`, the first code that floor measures (D-491). This task also defines `ReleaseProof`, the non-Clone `ReleaseMint`, `release_mint()` (once per process) and the session capability types in `privacy::api` (D-481, D-488).

### 2. Principles (lines naming this task's requirements)
**P12. Blind-index lookups are equality-only and leak equality.** The phone lookup is HMAC-SHA-256 under `VAULT_INDEX_KEY` (Arch 8). A blind index "leaks that rows have the same value", open to frequency analysis on low-entropy fields (blind_index README); a btree on the hash column is right, a range or `LIKE` query is meaningless. Never index plaintext, never put a plaintext phone in a `WHERE` [inferred]. Serves PRIV-002, PRIV-004.
**P13. Disk encryption at the host is not the vault.** Railway staff: "All customer data within Railway projects is encrypted at rest" (community answer, https://station.railway.com/questions/are-databases-encrypted-at-rest-0e719d6c); Render's security page claims AES-256 at rest (quoted in https://community.render.com/t/encryption-at-rest/3609). Neither is first-party documentation of backups: **verify with host** in its security page or DPA.
