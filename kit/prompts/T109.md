## Goal

`recovery` makes the nightly encrypted export to separate storage under its own key, kept 30 days with versioning and object lock, runs the monthly test restore with a High alert on failure, and leaves the key inventory to T117; `recovery` records each backup and restore result in `recovery.backup_check` and as one `ops` audit entry (`ops::api::audit`), and `portals` reads the newest such entry through a new `ops::api::latest_audit(conn, action)` added to the shared `app/ops/src/api.rs` (`portals` may not call `recovery`, `kit/layers.json`): the restore result line in `digest_flags.rs` (T204's) and the last-backup figure in `health_page.rs` (T106's), both extended here (D-491, D-493) (OPS-013, PRIV-018, PRIV-024, PRIV-029). The export is `pg_dump -Fc`; every restore runs `scripts/bootstrap_roles.sql` first, then `pg_restore --single-transaction`, with the ownership and append-only grant check (OPS-051), and the storage provider is Backblaze B2 (PRIV-029) (D-492). The new `recovery` schema's default privileges give `askhava_app` SELECT and INSERT only, and a table that needs UPDATE or DELETE gets an explicit GRANT in its migration; T250's `schema_grants.rs` checks every schema's default (D-1520). Plan change D-3155: (a) TD-OPS-26's empty cluster: CI's one PostgreSQL already has `askhava_app` and `askhava_migrator` (`.github/workflows/ci.yml:76` to `:80`), so `tests/recovery/tests/export_restores.rs` makes a throwaway cluster with PostgreSQL 16's own `initdb` and `pg_ctl` (the GitHub runner image has them under `/usr/lib/postgresql/16/bin`) in a temporary folder on a free local port (`initdb` refuses root: the test runs it and `pg_ctl` as an unprivileged user, e.g. through `runuser` to a user it creates when it is root, as on CI runners it is not; the `/usr/lib/postgresql/16/bin` path holds while `ubuntu-latest` is Ubuntu 24.04, and the test names the path it looked in), restores into it without and then with `scripts/bootstrap_roles.sql`, and stops and removes it; missing binaries fail the test with a message (never a skip). (b) The runtime image has no `pg_dump` (`Dockerfile:44` to `:47`): this task adds PostgreSQL 16's client tools (`pg_dump`, `pg_restore`) to the runtime stage (Debian trixie ships only 17, so from the PostgreSQL apt repository with its signing key pinned by fingerprint), and the export refuses a `pg_dump` whose major version is not the server's. (c) The nightly export and monthly restore handlers need the storage and backup-key settings, so they register in `worker_registry` (the shared `app/server/src/lib.rs`), and each `*_KIND` is registered, as `tests/integration/tests/task_registry.rs` requires.
