# T599: Tests (harness): the PICK-046 email's no-amount check ignores the random link token (flaky test fix)

## Goal

Plan change D-4196 (a flaky test, not from the outside audit; it cost T479's attempt 1 on Nov 17, 2026; `BUILD_BRIEF.md:272`): `tests/integration/tests/pick_lapsed_email.rs:273` (T446, DONE; PICK-046) asserts `!plain.contains("190") && !plain.contains('$')` on an email body that also holds the homeowner's quote-page link `https://<domain>/q/<token>`, and the token is an HMAC-SHA256 in 64 hex characters over a random salt (`link_token`, `app/core/src/ids.rs:254`), so the check fails by chance whenever `190` turns up in it (62 places times 16 to the minus 3, about 1.5% of runs). Fix, keeping the check at least as strict: take the `/q/` token out of the body first (cut each `/q/` followed by 64 hex characters down to `/q/`; the test already checks the body starts with the link's prefix), then assert the rest holds no `190` and no `$`, so the fake quote's 190 dollars (19000 cents, `:119`) written anywhere in the words still fails the test, and assert the cut removed exactly one token, so the check cannot pass on a body whose link changed shape. Asserting only `$190` or `190.00` was rejected: it would let a bare `190` through. Sweep (D-4196): a grep of `tests/` and `app/` for negative `contains` checks of short digit or hex strings found no other check on a text with a random token: `tests/integration/tests/quote_texts.rs:239` (`list_texts` has no link), `tests/integration/tests/summary_step.rs:197` (a body compared whole just before), `tests/integration/tests/confirm_reminders.rs:289` (an empty link), `tests/integration/tests/open_cards_digest.rs:223` (fixed links), `tests/integration/tests/radius_matching.rs:282` (5 digits against an audit row's UUIDs, under 1 in 30,000), `app/core/src/tests/ids.rs:133` (a fixed redacted string), `app/portals/src/homeowner_portal.rs:467` and `:500` and `app/portals/src/job_release.rs:231` (pages and `Debug` output with no token); 7- and 8-character checks (phone numbers, `tests/integration/tests/task_registry.rs:479`) are below 1 in 10 million; the file's Spanish case (`:389` to `:391`) checks words, not digits. Repeat the sweep (`grep -rnE '!.{0,40}\.contains\("[0-9a-fA-F]{2,4}"\)' tests app` and short digit constants such as `LAST4`) and report any new case in the hand-in; this task changes only its one file. Nothing in the app changes.

Acceptance: `cargo test -p askhava-integration --test pick_lapsed_email` passes against PostgreSQL with every case; the no-amount check fails when the body is given a `190` outside the link (shown in the report by a temporary local edit, not committed) and passes for any token; the report lists the sweep's grep and its result.
