## Goal

Phase 2 war games (Casey, October 31, D-1154), part 1: `wargames/` (Python, standard library only) drives the Railway test site through its real entry points (signed inbound texts and status callbacks to the texting webhook, the web intake and web chat, signed inbound business email replies, the homeowner, business and owner portal pages) and, for faults the sandboxes cannot make, a local lane (`--target local`: the stand-ins and the test-control router, as `Ci`'s journeys run). A persona library (`wargames/personas.py`) holds both sides: ordinary, confused and vanishing homeowners; Spanish speakers; tenants; STOP and START mid-job; pranksters and AI-credit drainers (photo spam, bursts of requests, endless rambling intake, re-entry loops, opt-out and opt-in churn, one- and two-word messages); people posing as businesses; contractors gaming quotes (bounced contact details, edits, double picks, after-hours claims, never confirming). Chaos injectors (`wargames/chaos.py`): duplicate and replayed webhooks, out-of-order texts, the clock at the 8 a.m. and 8 p.m. quiet-hour edges and at the 24-hour and 4-business-hour timer edges (local lane), a vendor outage mid-flow and the AI returning junk (local lane, through the stand-ins' fault and plant headers). The campaign session plays personas live too, improvising beyond the library, and adds each new one to it. Fake data only (BUILD_BRIEF.md:66, PRIV-019): every persona's name, phone (555-0100 to 555-0199), email (example.com) and street comes from the fixture generator, and no real number, key or person is ever used; signing secrets and test keys are read the way T129's sandbox mode reads its credentials (from the build environment's secrets, never printed, logged or committed); an entry point whose secret this session cannot reach runs on the local lane only and the run log says so; timers on the test site are shortened only through settings, as T136 does, and each simulated business day is recorded with its wall-clock span. `wargames/anomalies.py` checks after every step, from outside effects only (docs/test-design.md section 1 rule 1): no duplicate outbound text, email or charge; consent text first on every path; an opt-out word stops every text; no text outside quiet hours; no homeowner contact detail outside the vault or on any text to a business; every status change has an audit row; and every anomaly is logged as one JSON line with the request, job and message IDs (`wargames/runs/<run>.jsonl`, fake IDs only). The tests under `tests/wargames/` run offline in `Ci` (no test site, no network, the stand-ins at most) and run logs `wargames/runs/*.jsonl` are git-ignored (`.gitignore`), so only the reports carry results; persona addresses use fake street names such as "1 Test Way", since `scripts/pii_scan.py` scans `wargames/`. On the test site the AI-008 switch is on during the money run and the rounds, so real Claude calls are made on fake data from the test project's Console key (T137's), and the campaign's AI spend is capped at $40 in all (a test-project daily AI-call cap, AI-021, of 600 calls, and the Console spend limit Casey set at the account checkpoint, whichever is lower); outbound texts use Twilio's test credentials and magic numbers only, so no real phone receives anything (BUILD_BRIEF.md:190). Latency (D-2038, from Casey's shared intake-latency review, November 8, 2026): every scenario step records, on fake data only, the time from a homeowner's web submit or inbound text to the next question shown on the page or sent as a text, measured from outside (the request the harness sent, the reply it saw), and, where the app or the stand-ins expose them, the AI call time and the database pool wait for that step (on the local lane the pool wait and statement count from T416's `GET /__test/perf/db` snapshot, D-3292) (otherwise the record says "not exposed", never a guess); a timing record holds the run, scenario, persona class, step kind, lane, fake request ID and milliseconds, and never a message body, name, phone, email or address; each run ends with a table of p50 and p95 (nearest rank) per scenario for each measure, with how many turns fell back on the AI budget (AI-023's reply budget ran out and the fixed question went instead), ready for the round's results in `docs/phase2/war-games.md`. The concurrency and overload scenario is T297's (D-2054): it imports this task's drivers, chaos injectors and latency recorder from `wargames/`, so each stays usable on its own (a driver per entry point, the recorder independent of any one scenario). `wargames/scenarios.py` maps each of the 38 cases of the pentest matrix (`docs/reviews/war-games-inputs/2026-11-09-pentest-matrix.md`) to a scenario or a stated skip with its reason, and `tests/wargames/test_wargames.py` fails when a case ID has neither (D-2350); every case runs in the isolated environment only, with synthetic accounts and no production key, outreach, real message or payment.

Acceptance: `python3 -m wargames run --target local --smoke` runs one scenario of every persona class and every chaos injector against the local lane and exits 0 with an anomaly log, and `--target test-site --smoke` does the same against the Railway test site (or records which entry points ran on the local lane only and why); `tests/wargames/test_wargames.py` proves each anomaly check fires on a planted defect (a duplicate send, a text at 20:00:00 Arizona time, a sentinel phone on a business text, a status change with no audit row) and stays quiet on a clean run; `scripts/pii_scan.py` passes on the persona library and the logs. The smoke runs' summaries hold the p50 and p95 latency table per scenario and the count of turns that fell back on the AI budget; `tests/wargames/test_wargames.py` proves the percentiles on planted timings (1 to 100 ms give p50 50 and p95 95) and fails a timing record that holds a planted homeowner message, name or phone.

## Output discipline

Every turn re-reads earlier tool output; large results cost tokens on every later turn (D-3305). Never omit failure lines to save tokens.

1. For a file over 200 lines (`wc -l`), never `cat` or `Read` it whole. Use `grep -n` with at most `-C` 3, then `sed -n 'A,Bp'` or Read with offset/limit: at most 120 lines, or 250 if one read replaces two. Don't re-read unchanged files or regions; use earlier output.
2. Log build, test and lint output; print only decisive lines. Example: `cargo test -p <crate> >/tmp/t.log 2>&1; echo exit=$?; grep -nE 'FAILED|panicked|^error|test result' /tmp/t.log | head -n 60; tail -n 15 /tmp/t.log`. Grep each tool's failure markers: cargo/clippy `^error|FAILED|panicked`, pytest `FAILED|ERROR`, tsc `error TS`, npm `ERR!`, playwright `✘|failed`. If needed, read further log line ranges, including failures cut by `head`.
3. Prehand-in: `bash scripts/prehandin.sh >/tmp/p.log 2>&1; echo exit=$?; tail -n 40 /tmp/p.log` (smoke per Start step 2). Then, in its own Bash call with timeout 600000 ms, Ally: `bash scripts/prehandin.sh --ally >/tmp/a.log 2>&1; echo exit=$?; tail -n 30 /tmp/a.log`; no changed page path prints `not needed` immediately, otherwise only failed tests (D-3837).
4. Batch foreseeable reads, greps and `wc -l` into one turn, via parallel calls or one Bash call with `;` (D-3530).
5. Run `git diff --stat` before a full diff; diff only needed files.
6. Limit each output to 4,000 characters (D-3444). Read additional log ranges for failures. No running commentary; report once at end.
7. Exception: `git commit` must be plain, alone in its Bash call: never `-q`, redirect or pipe. Its Git `[<branch> <abbrev>]` transcript line is required by `--after` for every commit (D-3728, D-4796).
