Following `scripts/split_crate_doc.py --verify` (D-3474) and `scripts/split_arch_notes.py --verify` (D-3620). (1) `scripts/check_doc_compaction.py --map FILE [--base REF]`, standard-library Python. The map records `base` (the SHA it was made against, the default REF). For every file the map names, each line present at the base and gone or changed now must be listed (by SHA-256) with targets `path:start-end` that exist now. Each fact token of the old line must appear inside those ranges, not merely somewhere in the file. Fact tokens are requirement, TD-, D- and task IDs, paths, backticked names, numbers and amounts, quoted text, and the words never, not, no, only, must, may, unless, except, before and after. A line with no fact tokens needs a target range sharing at least 60% of its content words. A removed line that is blank, or that occurs as a whole line, byte for byte, inside its target range, passes without the token or word test (so blank lines and byte-identical section moves pass); map entries are a list, so identical removed lines are each listed or share one entry with several targets (D-3892). A byte-identical move (`moves`: old path to new path) passes when the bytes match. A map entry for a line that was not removed fails. The map may carry a `left` list (work deferred to T142), which the check ignores; the script's docstring states the map schema (`base`, the removed-line entries, `moves`, `left`), because T507 to T514 do not read the script. Across the whole tree, any backticked `path:N` or `path:N-M` cited outside `docs/decisions.md` (spec `Source:` lines, `kit/tasks.json`, crate `CLAUDE.md`, `docs/test-design.md` and the rest) whose text at those lines differs from the base fails; a citation of a path listed in `moves` is compared at its new path, and a cited line missing at both the base and now is not a difference (stale citations past a file's end exist, for example `app/jobs/CLAUDE.md:44`, a 29-line file). ## Output discipline

Every turn re-reads earlier tool output; large results cost tokens on every later turn (D-3305). Never omit failure lines to save tokens.

1. For a file over 200 lines (`wc -l`), never `cat` or `Read` it whole. Use `grep -n` with at most `-C` 3, then `sed -n 'A,Bp'` or Read with offset/limit: at most 120 lines, or 250 if one read replaces two. Don't re-read unchanged files or regions; use earlier output.
2. Log build, test and lint output; print only decisive lines. Example: `cargo test -p <crate> >/tmp/t.log 2>&1; echo exit=$?; grep -nE 'FAILED|panicked|^error|test result' /tmp/t.log | head -n 60; tail -n 15 /tmp/t.log`. Grep each tool's failure markers: cargo/clippy `^error|FAILED|panicked`, pytest `FAILED|ERROR`, tsc `error TS`, npm `ERR!`, playwright `✘|failed`. If needed, read further log line ranges, including failures cut by `head`.
3. Prehand-in: `bash scripts/prehandin.sh >/tmp/p.log 2>&1; echo exit=$?; tail -n 40 /tmp/p.log` (smoke per Start step 2). 4. Batch foreseeable reads, greps and `wc -l` into one turn, via parallel calls or one Bash call with `;` (D-3530).
5. Run `git diff --stat` before a full diff; diff only needed files.
6. Limit each output to 4,000 characters (D-3444). Read additional log ranges for failures. No running commentary; report once at end.
7. Exception: `git commit` must be plain, alone in its Bash call: never `-q`, redirect or pipe. Its Git `[<branch> <abbrev>]` transcript line is required by `--after` for every commit (D-3728, D-4796).
