## Goal

Nov 11 vendor-double review batch 4, F10 (callers' half; D-2769; PICK-013, SEC-004, SEC-008, BIZ-002, TXT-038). A Verify resend within the code's 10-minute life reuses the pending verification and its check attempts, so after the app allows a new code's tries Twilio can answer a check with 60202 (HTTP 429, too many attempts), and a send with 60203; the app counts tries per code row (`CODE_TRIES`, `app/picks/src/rules.rs:13`; `app/portals/src/business_auth.rs:88`) and maps any check error to `PicksError::Verify` (`app/picks/src/service.rs:790`), so the homeowner or business sees an error, not "try again in 15 minutes". After T131 (whose adapter returns a typed too-many-tries error) and the queued owners of these files: each caller (`app/picks/src/service.rs` and `app/picks/src/email_code.rs` for the pick code, `app/businesses/src/identity.rs` for the identity code, `app/portals/src/business_auth.rs` for sign-in) maps that error to its own cooldown (`CodeCheck::CoolingDown(at + COOLDOWN)` for the pick code; the existing lock-out of the other two), which outlasts the 10-minute verification so the next send starts a fresh one; any other adapter error keeps today's answer. Tests in `tests/integration/tests/verify_max_tries.rs` against the served stand-in (T131's faithful attempts): three wrong tries, a resend, then two more wrong tries; the third check after the resend (Twilio's sixth attempt on that verification, 60202) answers the cooldown, not an error (fails before the fix), for each of the three flows. Update the `picks`, `businesses` and `portals` `CLAUDE.md` files and `docs/decisions.md`. Plan change D-3999: it follows T564, which also edits `app/picks/src/service.rs` and `app/picks/src/email_code.rs`. Plan change D-4338 (night spot review of the business side and quotes on `main` d662af7e5, confirmed in a second pass and re-verified on `main` 9aeca6f95): (quotes 3; SEC-014, D-2206) `notice_post` (`app/portals/src/business_auth.rs:633` to `:663`) sends a sign-in link with `send_one` and never runs `admit_sign_in_link` (per IP and per business), which only `server`'s `SignInMailer::admitted` (`app/server/src/business_signin.rs:230` to `:247`) calls for the sign-in form, so anyone holding a valid notice URL can send the member about 480 sign-in emails a day from the shared daily limit (only `LINKS_PER_LIFE`, `:779`, caps it).
