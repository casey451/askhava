## Goal

JOB-009 (an Open job moves to Quotes ready when its first quote arrives) and JOB-011's No quotes yet to Quotes ready are not built (D-1048, D-1517; `app/quotes/CLAUDE.md` lists "the first-quote move" as not here yet): nothing moves a job to `QuotesReady` on a quote, so a quoted job's Open wait (`JobStatus::wait`, 6 p.m. next day) moves it to No quotes yet with that text and then closes it, a "2 YES" text pick is refused (`app/picks/src/rules.rs` takes only Ready or Waiting, and Open is Collecting), and TXT-016's first-quote text (`quotes::api::first_quote_text`, template `first_quote`) has no sender. Build it: in `jobs` (the shared `app/jobs/src/api.rs` and `app/jobs/src/status.rs`) add `JobStatus::moves_on_first_quote` (Open, No quotes yet) and `jobs::api::first_quote(db, job, at)`, which, when the current status `moves_on_first_quote`, applies the move to Quotes ready with the homeowner-text template `first_quote` in the caller's transaction (on a lost race it re-reads, at most 3 times, then reports that nothing moved); any other status moves nothing and writes nothing. `quotes::intake::submit_quote` (`app/quotes/src/intake.rs`) calls it inside its transaction after the window, status and edit checks and before the quote row is written (the job lock before the quote row, the order D-1051 uses), for a quote confirmed at once (not `ai_read`); `confirm_quote` calls it when it confirms an AI-read quote. A second quote, an edit, and a quote in Quotes ready or Awaiting confirm move nothing and queue no text. The move bumps the version, so the old Open or No-quotes-yet wait applies nothing (JOB-006), and Quotes ready's 3-day wait counts from the move (JOB-012, JOB-025). `intake::job_texts` (`app/intake/src/job_texts.rs`) adds `first_quote` to `JOB_TEXT_TEMPLATES` and sends it by the existing steps (`text_due`, so a moved-on version drops it; the homeowner lookup; `may_text`; `send_window` for quiet hours and opt-out; the outbox), issuing a quote-page link for it as it does for `all_quotes_in` (SEC-037); no new template key (the English and Spanish `first_quote` templates exist, T047). No phone, name or amount is logged. `submit_quote` has no production caller yet (the business quote form is T148's), so the move must be right wherever a quote is stored. Tests in `tests/integration/tests/first_quote_move.rs` (TD-JOB-11): the move and its one text event in the quote's transaction (a failing quote insert rolls the move back), no second move or text, a No-quotes-yet job moving with its stale text dropped, the old wait applying nothing and the 3-day close from the move and after `restart_timer`, two first quotes at once (one move, one text, repeated runs), an AI-read quote moving only on confirm, and "2 YES" accepted after two quotes with no manual move (TD-PICK-40's path). Every existing test must still pass; if a done task's test breaks because a quote now moves its job, stop and report it (that is a plan change), never edit that test. Update `app/quotes/CLAUDE.md` (drop the "Not here yet" item), `app/jobs/CLAUDE.md` and `docs/architecture.md` section 10.

### 2. Principles that bind this codebase (lines naming this task's requirements)
**R11. Work that leaves the database is queued in the same transaction as the state change.** A state change and its `core.task` row commit together; never call a vendor inside the transaction that changes status. Brandur: enqueue mid-transaction and the job runs too early; enqueue after commit and a crash loses it ("Data is persisted, but the background work doesn't get done"). Here the queue is in the same database, so the insert is simply part of the transaction. Serves JOB-004, JOB-005, JOB-006, Arch 4 rule 2.
**R12. Claim with `SKIP LOCKED`, keep claim transactions short, hold a lease, re-check on run.** PostgreSQL: skipping locked rows "can be used to avoid lock contention with multiple consumers accessing a queue-like table" (select.sgml text, see postgres brain P9). Long transactions pin the vacuum horizon and degrade a hot queue (Brandur 2015; PlanetScale 2026). So: claim and commit, run the handler outside that transaction, finish with a fenced update. Handlers first re-check the current status (JOB-006). Serves JOB-006, Arch 5 task queue.
