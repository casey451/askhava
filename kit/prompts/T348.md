# T348: harness: the authorization matrix gets public, owner and action-link doors and an HTTP probe for every served realm route

Task T348 (harness, phase 1, stage 4). Slug: matrix-doors.

## Goal

Matrix doors before the serving tasks (D-2440; SEC-019, SEC-048, SEC-034, SEC-004 to SEC-008, SEC-026; D-1945, D-736, D-2429). T088's authorization matrix (`tests/security/tests/auth_matrix.rs`) gives every route of the generated route table a door and panics on a path it does not name (`:107`), and `td_sec_01_route_table_is_generated_and_every_path_has_a_door` fails on any served `/h` or `/b` route (`:527` to `:531`), because those realms are probed only through the guard function "since those routes are not served yet". So every queued task that serves a public page, an owner page, an email action link or a homeowner or business page would fail the matrix. Before any of them, extend the matrix; nothing in it is exempted, loosened or removed. (1) New doors in `door`, beside the existing ones: `Public` for `/healthz`, `/help` and every path below it, the legal pages (`/terms`, `/privacy`, `/sms-terms`, `/your-data`, `/business-data`) and any route the `site` module serves (the route table records the module of each `.route(` call; a site route outside this list is still public); `ActionLink` for `/b/a/` paths (T148's signed email action links, before the `/b` business arm); `Owner` for `/owner` and every path below it except the sign-in paths, which stay `SignIn`. `allowed`: `Public` admits every actor; `ActionLink` admits no session by itself (the link is the key); `Owner` admits only the owner. (2) `td_sec_01_route_table_is_generated_and_every_path_has_a_door` no longer fails on a served realm route; instead every served path of the `Homeowner`, `Business`, `Owner`, `ActionLink` and `Public` doors must have a row in `docs/architecture.md` section 13 reading `yes` (which `app/server/tests/route_wiring.rs` already proves served), so the HTTP probe below reaches it; a served one without that row fails naming it. With nothing served under those doors today the check passes. (3) `app/server/tests/door_matrix.rs` (new; a test crate may not depend on `askhava-server`, D-736, so the HTTP probe lives in the server crate): against `server::build_router` over a real test database, the same six actors as the matrix (anonymous, homeowners A and B, businesses X and Y, the owner, signed in the way `auth_matrix.rs` signs them in) send every method of every section 13 row reading `yes` whose path falls under those five doors (the same prefix rules, restated in the file): a `Homeowner` route admits A and B only, to their own records (A's page never names B's job or token), and gives anyone else a 4xx with a link to `/h/sign-in` and no detail; a `Business` route admits X and Y only, a `{pick}` or `{complaint}` of the other business is the one not-found answer, and anyone else gets a 4xx with a link to `/b/sign-in` and no homeowner detail; an `Owner` route admits only the owner and gives anyone else a 4xx with a link to `/owner/sign-in`; an `ActionLink` route opens only for the token minted for that kind, object and member (`portals::api` minting, as T148's tests do), a `GET` changes nothing (SEC-026), and a token for another kind, object or member, or none, is the one not-found answer; a `Public` route answers every actor's `GET` without a session and its body holds none of the fixtures' names, phones, addresses, tokens or job numbers. Every `Homeowner`, `Business`, `Owner` and `ActionLink` response is `no_store` (SEC-034), and every `POST` of any of the five doors, sent cross-site or with a wrong CSRF token, is a 403 with one `csrf_rejected` security event naming the route template (SEC-048). Path parameters are filled from fixtures: `{pick}`, `{complaint}`, `{kind}`, `{object}`, `{token}`; a row with any other parameter fails naming it, so the task that adds one takes the probe for that fill in a plan change. With no such row served today the probe passes with zero routes and starts probing each row as its serving task flips it to `yes`. (4) The matrix's module doc says where each door is probed. This is a harness task because it edits a DONE task's protected security test (T088's) and adds a cross-module security probe; Opus worker and reviewer. Update the `server` `CLAUDE.md`, `docs/architecture.md` section 10 and `docs/decisions.md`.

Acceptance: TD-SEC-61 passes on `main` with zero routes served under the new doors, and each existing test in `auth_matrix.rs` passes with no door, probe, row or assertion removed or loosened; the only replaced check is the served-realm failure, now a demand for a `yes` row that `door_matrix.rs` probes over HTTP.
