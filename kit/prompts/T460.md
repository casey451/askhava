## Goal

Plan change D-3676 (split from T302; BIZ-002, BIZ-026, SEC-034, SEC-048, SEC-019; D-288, D-2954, D-3602, D-3641): the identity steps of sign-up, in T302's `app/server/src/business_signup.rs`, each a `POST` without a session on its own route constant: `CODE_SEND_ROUTE` ("Send the code" and "Send a new code": the identity code by Verify to the masked record contact, TXT-038), `NUMBER_OLD_ROUTE` ("That number is old", D-288), `LETTER_ROUTE` ("Mail the letter") and `IDENTITY_CHECK_ROUTE` (the typed code checked with `businesses::api::check_code`, a refused or expired code showing `Screen::IdentityCode` with its `CodeProblem`, A11Y-030). Every later step reads the sign-up only from that verified cookie (T459's), never from a posted or path ID, and checks that the sign-up's stored state (its identity step, `businesses::api::Step`, code-sent and email-verified facts, read only through T485's `businesses::api::signup_progress`, D-3779) allows that step now, and that the business's stored status (`businesses::api::AccountStatus`) is `Pending` or `NeedsReview`; a missing or bad binding (a wrong or altered MAC, ID or salt), a step out of order or a business in any other status is refused like any refusal (the screen again, no detail), changes nothing, sends nothing and calls no Verify (D-3641). The identity code check is refused before `businesses::api::check_code` is called while `signup_progress` answers no step, so a step out of order uses no try (`check_code` takes one before it looks at the step, `app/businesses/src/identity.rs:267` to `:271`), and the step a screen shows comes from that reader, never from `RecordFound::masked()`, which cannot tell no step from the first (D-3779). The contact each step reads comes from `businesses::api::signup_record` in that request, as T459 reads it (the bound ROC number only; a number posted on any of these screens changes nothing), never stored, logged or put in an error; a screen holding a record contact is `no_store`; a cross-site or wrong-CSRF `POST` is refused, changes nothing and is a security event. The served part gains the Verify client these steps need, built from settings as `ServedSignIn::from_settings` builds its own. Each route's row in `docs/architecture.md` section 13 is marked `yes`. Tests: cases in `app/server/tests/business_signup_route.rs` (TD-SEC-45: each step with no cookie, an altered cookie (another sign-up's ID under this cookie's MAC) and a made-up cookie is refused and stores nothing; a step after a browser restart (a new pre-session cookie, the sign-up cookie kept) still works; in a browser with a business session the steps work the same way; a code send for one sign-up never reaches another's record contact; TD-BIZ-49: an R-37 sign-up's code goes to its fixture record's phone, shown masked first; a different ROC number posted on the identity screen changes nothing and writes no new check row). Update the `server` `CLAUDE.md` and `docs/decisions.md`.
