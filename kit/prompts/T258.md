# T258: adapters and payments: a refund is recorded as Stripe reports it (pending, succeeded, failed, canceled), never as done on a 200

## Goal

`PaymentsAdapter::create_refund` returns only the `re_…` ID (`app/adapters/src/payments.rs`), so `refunds::finish` treats any answer as `Refunded`, sets the row `succeeded` and appends the ledger `refund` entry, and `reconcile::own_refund` counts any answer as refunded, even when Stripe answered `pending`, `requires_action`, `failed` or `canceled` (external audit A03, D-1753; D-1545 (2) already recorded the ledger side). (1) The typed refund is additive for production callers (this task is a `harness` task because four DONE tasks' test fakes gain one trait impl each): `app/payments/src/refund_stripe.rs` defines a payments-owned trait `RefundStripe: PaymentsAdapter` (the `IntentStripe` and `ReconcileStripe` pattern) with `refund(idempotency, payment_intent) -> Refund` and `fetch_refund(id) -> Refund`, where `Refund { id, state, amount_cents, currency, payment_intent }` and `RefundState::{Pending, RequiresAction, Succeeded, Failed, Canceled}`; an unknown state string is an error, never a success, and the refund must name the PaymentIntent asked for. It is implemented for `StripeHttp` there, over two new inherent HTTP calls on `StripeHttp` in `app/adapters/src/payments.rs` (the `PaymentsAdapter` trait and its `create_refund` stay unchanged until T132 retires `create_refund`). `refunds::finish`, the retry and `reconcile::own_refund` take `&impl RefundStripe`, and so do the public functions that reach them: `request_refund`, `run_refund_retry` and `early_fraud_warning` (`app/payments/src/refunds.rs:78`–`:135`), `reconcile` and `run_reconcile` (`app/payments/src/reconcile.rs:125`, `:424`) and T064's `run_late_refund` (`app/payments/src/late.rs:112`). The fakes in `tests/integration/tests/disputes.rs`, `late_success.rs`, `reconcile.rs` and `ledger_1000_jobs.rs` each gain one `impl RefundStripe` whose `refund` answers `Succeeded` with the ID their `create_refund` already returns and whose `fetch_refund` answers the same; nothing else in those files changes (no blanket impl over `PaymentsAdapter`, which would conflict with the `StripeHttp` impl). (2) `migrations/0124_payments_refunds_and_events.sql`: the refund row's status gains `pending` and `canceled`, the ledger kind check gains `refund-reversal` (FEE-028 as changed by D-1753), and `payments.webhook_event` (Stripe event ID unique, type, received time; app role SELECT and INSERT) is created here for T259's dispatch, so T259 needs no migration of its own; `EntryKind::RefundReversal` joins the enum in `app/payments/src/ledger.rs:14` and the exhaustive match in `app/payments/src/models.rs:782`–`:795` (the money totals). (3) `refunds.rs`: a `succeeded` answer records the refund and appends the `refund` entry as now; `pending` or `requires_action` stores the `re_…` with status `pending`, appends nothing, and the 30-minute check asks Stripe again through `fetch_refund`; `failed` or `canceled` is the FEE-026 failure path (alert, hourly retry). `refund_succeeded(pool, re, now)`, `refund_failed` and `refund_canceled` (the webhook's, T259) move a `pending` row on; a `failed` or `canceled` after `succeeded` appends one `refund-reversal` entry of the same amount keyed by the `re_…`, append-only (no ledger row is updated or deleted), and the FEE-026 retry's next success appends a new `refund` entry keyed by its own `re_…`, so the ledger always nets to what Stripe holds. (4) `reconcile::own_refund` records by the same rule. Every customer-facing "refunded" text or notice goes out only on `succeeded`. Update `docs/architecture.md` section 7, the `payments` and `adapters` `CLAUDE.md` files and `docs/decisions.md`.

Acceptance: TD-FEE-42 passes against PostgreSQL with a fake `RefundStripe` answering each Stripe refund state; every existing TD-FEE-14, TD-FEE-15, dispute, late-success, reconcile and 1,000-job case passes with only the trait impl added to its fake, and no case's expected value changes; the five other test files with a `PaymentsAdapter` fake are untouched; the `app/payments/` 95% floor holds.
