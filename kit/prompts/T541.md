## Goal

Plan change D-3890 (Fable's pre-claim checks of the remaining stage-5 tasks, Nov 16, 2026): Split from T364. Cards are collected only by Stripe Elements on the Confirm page (FEE-014), so no other page takes a card and no form field carries a card's type, brand or last four. (1) A Confirm with the box ticked whose card will be stored (no saved card yet, or a SEC-038 step-up passed within 5 minutes; otherwise nothing is sent for saving) confirms with `setup_future_usage=off_session` (FEE-048: the FEE-015 authorization covers the PICK-048 auto-confirm charge, which charges the saved card off-session, `app/payments/src/off_session.rs:126`; on a $0 Confirm, `payments::api::SetupIntentRequest` with `usage=off_session`); the charge itself stays on-session (FEE-014); once the payment succeeds (or a $0 Confirm's card is set up, `confirm_pay.rs:14`), the server reads the PaymentMethod's type, brand and last four from Stripe through a new read in `app/adapters/src/payments.rs` (the `pm_` ID never shown or logged) and builds `SavedCard::new` from that answer only (`app/payments/src/models.rs:109` to `:123`), storing it with the FEE-015 authorization version and time. (2) A business that already has a saved card is changing it, so the save goes through `change_saved_card`, which needs T364's step-up within 5 minutes (SEC-038); without one the payment still goes through, the card is not saved, and the page says so with a link to the step-up page; that reply's link carries its own label (`link_label`, "Enter a code to save this card") in the owned `app/portals/static/confirm_pay.ts`, whose `sayWithLink` today labels every link "Go to your portal" (`:85` to `:93`), which the over-limit link keeps. (3) A bank debit or any non-card answer from Stripe stores nothing (FEE-014, D-073); a failed or unavailable Stripe read stores nothing and the page says the card was not saved; the `pm_` ID read is the one on the succeeded PaymentIntent (or the $0 Confirm's SetupIntent) as Stripe returns it, never one the request posts. Tests in `tests/integration/tests/saved_card.rs` (TD-SEC-70), fake data and the stand-in Stripe only. Update the `portals` and `payments` `NOTES.md` and `docs/decisions.md`. Plan change D-3892 (Opus pre-claim check, Nov 16, 2026): (4) Reach Stripe without touching another task's test: the save-flag confirm, the card read and the $0 save (create and confirm the `usage=off_session` SetupIntent from `payments::api::SetupIntentRequest::form`, `app/payments/src/models.rs:165` to `:183`, which no adapter posts yet; through `POST /v1/setup_intents`) are three new default-bodied methods on `ApprovalSecret` (`app/portals/src/confirm_pay.rs:637`; the default confirm calls `confirm_keeping_secret`, and the default read and the default $0 save answer unavailable, so nothing is saved), overridden by `StripeApproval` in the shared `app/server/src/lib.rs:211`; no new field on `ConfirmRoute`, `ConfirmSettings` or `PaymentIntent`, no new bound on the route's `S`, and no new required method on `PaymentsAdapter` or `IntentStripe` (`app/server/tests/confirm_route.rs:184`, `:226`, `:231` and dozens of other files build or implement them). The `pm_` ID is the `payment_method` of Stripe's confirm answer, read by the save-flag confirm in the owned `app/adapters/src/payments.rs` beside `ConfirmedIntent` (`:540` to `:561`; `ConfirmedIntent` is built only there, while `PaymentIntent` has no such field and gains none); the type, brand and last four come from its `latest_charge` (`app/adapters/src/payments.rs:65`) read with `GET /v1/charges/{id}` (`payment_method_details.type`, `card.brand`, `card.last4`), which the stand-in serves (`stand_ins/server.py:402`, `stand_ins/stripe.py:241`). (5) A payment that needs the bank's approval (3-D Secure) saves no card, since the page then only reads the attempt's state and a `GET` changes nothing (SEC-026); the page says the card was not saved.
