# T353: payments: a won dispute records the countering fee's return and the disputed amount's return, and the reconcile compares only disputes not won

## Goal

Nov 10 code review, payments F2 (D-2625; FEE-027 to FEE-030, FEE-050; D-1383, D-1753): `charge.dispute.closed` (`dispute_closed`, `app/payments/src/routes.rs:537`) only writes an audit row and a High alert; it never reads the event's `status` (`read_object` keeps only `/id`), and no code writes `EntryKind::CounteringFeeReturn` (`app/payments/src/ledger.rs:32`). So when Casey wins a $75 dispute whose evidence was submitted, the ledger keeps the `dispute` 9000 and the `countering-fee` 1500 as lost, `MoneyView::net()` understates by $90 for good, the money view keeps a dispute that was won, and the reconcile cannot see it because `MoneyTotals::of_stripe` counts a dispute whatever its status. D-1383 left "how a won dispute's returned amount is recorded" to the dispute tasks, and none took it. Fix: `dispute_closed` reads `status`; on `won`, in the event's transaction and once per dispute, it appends a `countering-fee-return` equal to the recorded countering fee (when one was recorded, FEE-050) and a `dispute-reversal` of the disputed amount (Stripe's $15 dispute fee itself stays a cost: `docs/brains/payments-stripe.md:102` returns only the countering fee on a win), the stored code made only by a `LedgerEntry` constructor and folded by every ledger reader as a negative dispute, as D-1753 did for `refund-reversal` (not an `EntryKind` variant, so `portals`' exhaustive statement match is untouched; `migrations/0184_payments_dispute_reversal.sql` adds the code to the ledger's `kind` check; FEE-028 lists it since D-2625); any other closing status changes nothing but the audit and alert as today. The `dispute-reversal` row carries the dispute's `dp_` ID as its Stripe ID. The reconcile compares the disputed amounts of disputes not won only, with no Stripe read: in its ledger read (`ledger_totals`, `app/payments/src/reconcile.rs:897` once T334 is on `main`) it also reads which of the listed `dp_` IDs already have a `dispute-reversal` row and leaves those disputes out of both sides (a won dispute is known from the webhook). `DisputeStripe` (`app/payments/src/disputes.rs:42`) has only `submit_evidence`, and carrying a status on `StripeCharge.dispute` (`app/payments/src/models.rs:643`) would break its literals in six files this task does not own, so neither changes (D-3134). Tests in `tests/integration/tests/dispute_won.rs` (TD-FEE-65), each failing on today's `main`: after a submitted dispute, a `won` closure leaves `MoneyView.dispute_fees` equal to the dispute fee only and the net disputed amount 0; the same event again appends nothing; a `lost` closure changes no ledger row; a won dispute with no countering fee appends no `countering-fee-return`; the reconcile over a won dispute raises no difference. Money: 95% branch floor; the overseer runs an independent money review of the hand-in. Update the `payments` `CLAUDE.md` and `docs/decisions.md`. The business statement's wording for a won dispute is T204's (it owns `app/portals/src/business_portal.rs`); this task only folds the new code in the ledger readers it owns.
