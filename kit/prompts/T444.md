# T444: intake (test): the job's ZIP is read only from a property in the job's own town

## Goal

Audit finding on T249 (D-3563 (b); CARD-024, INT-049, D-1521): `property_zip` (`app/intake/src/cards_out.rs:337`) reads the ZIP of the newest property of the request's homeowner `AND p.town = $2`, the town `models::property_town` read just before, so a property stored between the two reads in another town is never paired with the older town; no test fails if that condition is dropped. Both reads order the same way, so through the public API the condition matters only in that race, which no test can make happen on demand: the one change to `cards_out.rs` is `property_zip`'s visibility (`async fn` becomes `pub(crate) async fn`, its doc comment unchanged); nothing else in that file changes. New in-crate test `app/intake/src/tests/property_zip_town.rs` (one `mod` line in the shared `app/intake/src/tests/mod.rs`), `#[sqlx::test]` against PostgreSQL with fake data only (public market ZIPs, fake IDs, no names or phones), set up as `app/intake/src/tests/zip_step.rs` does: one homeowner request with an older property in one town with one ZIP and a newer property in another town with another ZIP; `crate::cards_out::property_zip(conn, conversation, <older town>)` returns the older property's ZIP, and with the newer town the newer one's; a town with no property gives `None`. Each case names CARD-024 and D-1521 in its doc comment (TD-INT-38 is the ZIP step's entry, cited only as related). Check by hand that deleting `AND p.town = $2` (and its bind) makes the first case fail, then restore it, and say so in the report. Update the `intake` `CLAUDE.md` tests note and `docs/decisions.md`.

Acceptance: `cargo test -p askhava-intake --lib tests::property_zip_town` passes against PostgreSQL; with `AND p.town = $2` removed from `property_zip` the older-town case fails (checked by hand, reported); the only change to `app/intake/src/cards_out.rs` is `property_zip`'s `pub(crate)`; every existing intake test passes unchanged.
