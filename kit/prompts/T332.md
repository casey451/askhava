## Goal

Fifth audit review fix round (D-2290; FEE-021, FEE-018, FEE-020, FEE-026; D-1547). Two preconditions of T328's `payments.late_success_refund` registration. (1) D-1547's tracked follow-up: `payments.refund.trigger`'s check (`migrations/0102_payments_refunds_disputes.sql:14`) has no late-success code, so `LATE_TRIGGER` stores a late-success refund as `charged-after-cancel` (`app/payments/src/late.rs:32`). `migrations/0177_payments_late_success_trigger.sql` replaces that check with one that also allows `late-success` (rows already stored keep their code); `app/payments/src/models.rs` (after T295) gains `RefundTrigger::LateSuccess` with code `late-success`, read back by the same parser; `late.rs`'s `LATE_TRIGGER` becomes it. `tests/integration/tests/late_success.rs` (T064's) changes only in the expected trigger, `charged-after-cancel` to `late-success`, as D-2290 records, and in one assertion of `td_fee_12_own_end_counts_once_the_check_records_the_success`, as D-2970 records: once the check round itself queues the late success (part (2) below), the report after it answers `Ok(LateSuccess::AlreadyQueued)`, not `Ok(LateSuccess::Queued)`; that test's `(1, 1)` alert and task count after the report stays; every other input, count, assertion and comment stays byte-identical. (2) A success on a pick that `payments` itself ended (`payments.pick_intent.ended_at` set by the FEE-018 four-hour end or the FEE-020 card-fix window) never reaches `late_success` today: `paid_release` stops at `ReleaseError::PickEnded` before the success is stored (`app/payments/src/release_proof.rs:304`), and the `CHECK_KIND` round that stores it later calls nothing (`app/payments/src/handlers.rs:371`; D-1547's known gap). Now: `paid_release`, on a verified success for an ended pick, stores the success and its evidence as the check round would and calls `late_success` in the same transaction, then answers `PickEnded` (nothing is released, no `ReleaseProof` is built); `run_charge_check`, when its round records a success on an ended pick, calls `late_success` in that round's transaction; a declined attempt ended by the card-fix window that later succeeds reaches the first path through the webhook. `late_success` already queues once per pick and alerts only on a new queue, so both paths together give exactly one refund and one `payments.late_success` alert. Tests in `tests/integration/tests/late_success_ended.rs` (TD-FEE-56). This is a harness task because `late_success.rs` is a DONE task's test. Money: 95% branch floor; the overseer runs an independent money review of the hand-in. Update the `payments` `CLAUDE.md` and `docs/decisions.md`.
