## Goal

Plan change D-4294 (spot review of auth, verified on `main` fde4fad3; SEC-043, SEC-020, SEC-014, SEC-040, D-480, D-492, D-1919, D-3962). (1) Step-up has no try limit: `step_up` (`app/server/src/owner_signin.rs:367` to `:393`) calls `require_owner` and then `owner_step_up` with the TOTP code and no `admit_*`; a wrong code is only an `auth_failed` event, so a holder of a live owner session cookie without the authenticator can guess codes for the session's life and open the 5-minute window for every SEC-043 action. Add `admit_owner_step_up` to `app/portals/src/limits.rs` (through `intake::api::admit`: 5 tries per owner session per hour by `Key::Record(session id)`, 10 per client IP per hour), called before the TOTP check; a refused try checks nothing, and a session past its limit is ended on the server (the 4xx with a link to `/owner/sign-in`, as an idle one). (2) The passkey path is hard-locked: every sign-in `POST`, a passkey answer included, runs `admit_owner_password` (`owner_signin.rs:306`), whose checks include the account-wide `OWNER_TRIES_ALL` (`limits.rs:36`, `:139` to `:143`), so 20 junk passwords an hour from four addresses lock the owner out of the passkey path too, against SEC-040; and `limits.rs:11` and `:128` still say the passkey path calls no limit. New order: every sign-in `POST` admits the per-IP bucket first; a post carrying a passkey answer has its assertion checked before the password (no argon2), and only a verified assertion goes on to the password check without the account bucket; an unverified one, and every post without a passkey answer, also admits `OWNER_TRIES_ALL` before any argon2, so argon2 still never runs past both limits (D-3962's fix-round test, `td_sec_46_password_tries_past_the_limit_are_refused_first`, passes unchanged). The doc lines in `limits.rs` say what the code does. (3) `POST /owner/sign-in/passkey` (`owner_signin.rs:323` to `:341`) calls no limiter and refuses with 429 once `MAX_LIVE_SIGN_IN_CHALLENGES` (20, `app/portals/src/owner_auth.rs:54`) are live, so 4 posts a minute from anyone keep passkey sign-in unavailable. Each challenge issue admits a new per-IP limit (`admit_owner_passkey_challenge`, 10 per client IP per hour), and the live cap becomes a table-size bound only (10,000; the 5-minute life and sweep stay), passed as today so `app/portals/src/models.rs` does not change. Tests, fake data only, in the new `app/server/tests/owner_auth_limits.rs` through the assembled router (TD-SEC-75); `app/server/tests/owner_signin_route.rs` (TD-SEC-46) passes unchanged. Update `app/portals/NOTES.md`, `app/server/NOTES.md`, `docs/threat-model.md` S5 if its text names the step-up limit, and `docs/decisions.md` (the entry also notes that D-3962's "the limit is per address only" was not what the code did). Budget 4 files, 400 lines.
