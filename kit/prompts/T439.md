## Goal

Enforce the re-review of fix rounds (D-3475; D-584, D-1328, D-2506, D-3444; BUILD_BRIEF.md:250): `--after` (`runner/__main__.py` `after`, `runner/github_env.py` `collect_result`) records the hand-in head as `reviewed_sha` whatever ran last; it checks only that the reviewer transcripts ran on the reviewer model (`cycle.py` line 501). Before D-3444, 3 of 4 sampled fix rounds merged with no reviewer run after the fix commit (T249, T372, T423), and in T423 the Sonnet main session committed itself. Evidence available at `--after`: the worker and reviewer subagent transcripts (`find_transcripts`, `~/.claude/projects/*/*/subagents/agent-<id>.jsonl`), whose lines hold the model, the assistant text and each tool result's text; git on the runner's checkout; the hand-off file. The reviewer today states no verdict and no head, so: (1) `.github/workflows/backup-runner.yml` step 4 (and 4c, 5b and 3c, which re-run it): the reviewer runs `git rev-parse HEAD` itself on the task branch before reading the diff and ends its report with exactly one line `REVIEW-VERDICT: APPROVED <40-hex head>` or `REVIEW-VERDICT: FINDINGS`; every worker and fix-round worker commits with plain `git commit` (no `-q`, output not filtered or redirected), so Git's `[<branch> <abbrev>]` line reaches its transcript; after any fix commit, including a worker redoing a commit after a (b) hold, the session runs a NEW reviewer that must approve the new head over the new head and passes every reviewer agent id to step 5. (2) New `runner/review_proof.py` (standard library; called from `collect_result` for outcome `submitted`, on the worker's head BEFORE `_hand_in_in_order`'s runner commit and the pre-hand-in gate). Rule (a), approval of the head: when the task has a reviewer (`cycle.reviewer_model`), some reviewer transcript must, counting only `subagents/agent-*.jsonl` paths from `--reviewer-agent`, never one also given by `--worker-agent` and never one holding a `[<branch> <abbrev>]` commit line (a reviewer that committed is no reviewer), in an assistant text block (never a tool result or a quoted prompt), have as its LAST verdict line `REVIEW-VERDICT: APPROVED H` with H the full hand-in head, must hold a tool result containing H (its own `git rev-parse`), and its own models must pass the same rule as `cycle._review_problems` (`runner/cycle.py:500-505`: `reviewer_model(task)` with `known_models`), so a D-2225 model-window or fallback reviewer passes; an approval of any earlier commit, a `FINDINGS` last verdict, or a verdict only in another role's transcript does not count. Since the approval names the exact head, any commit after the last reviewed one fails (a). Rule (b), who committed: for each commit in `git rev-list H ^<main base> ^<branch start>` (branch start: new hand-off field `branch_start`, the prepared branch's existing `base_sha` from `_prepare`, the local task branch tip at the claim; when it is missing, because `prepare_branch` returned `{}` (`runner/github_env.py:1966`, dry run or a git failure), (b) is skipped with a log line naming why (no `remote_at_start` fallback: it would judge the runner's own prepared merge); so the runner's own prepared merge and earlier attempts' commits are not judged), a non-merge commit needs a worker transcript (passed via `--worker-agent`, a `subagents/` path) whose tool result holds Git's commit summary line naming it (`[<branch> <abbrev>]`, abbrev at least 7 hex and a unique prefix of the full SHA); a merge commit passes when its second parent is on `origin/main` and its tree equals `git merge-tree --write-tree` of its parents (a clean, unedited merge adds no authored content), else it needs the same line. Commits made by the main session itself leave no line in any worker transcript, so they fail; this is the closest checkable rule: the evidence proves a worker subagent's tool ran the commit, not who asked for it, and transcripts are files on the runner's disk with the same trust as D-1328's model evidence. (3) Refusal: each rule may hold the hand-in once (`prehandin_holds` style, separate hand-off counters `review_holds_a` and `review_holds_b`, each at most 1), printing `runner: review_missing` with the unapproved or unproven commits, so the session runs a new reviewer (or has a worker redo the commit, after which a fresh reviewer must approve the new head, as the workflow text says) and `--after` again; a rule failing again after its hold fails the attempt as `tests_failed` with a log naming each commit (short SHA, subject) and the rule, nothing pushed, as any failed hand-in. A task without a reviewer skips (a) only. `collect_result`'s new parameter defaults to no check, so existing callers and tests keep their behaviour; `after()` always passes it. Failure drills and tests (new `tests/test_runner_review_proof.py`; no existing test changes, every existing runner test passes): T249's shape (fix commit after the approval) refused; T423's shape (a commit whose summary line is only in the main session's transcript) refused; approval of an earlier SHA refused; `FINDINGS` after an `APPROVED` refused; a verdict quoted in a tool result or in the worker's transcript ignored; a reviewer transcript on a non-reviewer model refused and a model-window or fallback reviewer accepted; a reviewer path also given as `--worker-agent` ignored; a reviewer transcript holding a commit line ignored; an approval without its `rev-parse` tool result refused; a clean main merge accepted and an edited merge without a summary line refused; an ambiguous or 6-hex abbrev refused; the decisions reorder commit and the runner's prepared merge not judged; no `base_sha` skipping (b) with its log line; (a) and (b) each holding once on their own counter, then `tests_failed`; the happy path (worker commit, fix commit, new reviewer approving the head) accepted and `reviewed_sha` set; the workflow step text. ## Output discipline

Every turn re-reads earlier tool output; large results cost tokens on every later turn (D-3305). Never omit failure lines to save tokens.

1. For a file over 200 lines (`wc -l`), never `cat` or `Read` it whole. Use `grep -n` with at most `-C` 3, then `sed -n 'A,Bp'` or Read with offset/limit: at most 120 lines, or 250 if one read replaces two. Don't re-read unchanged files or regions; use earlier output.
2. Log build, test and lint output; print only decisive lines. Example: `cargo test -p <crate> >/tmp/t.log 2>&1; echo exit=$?; grep -nE 'FAILED|panicked|^error|test result' /tmp/t.log | head -n 60; tail -n 15 /tmp/t.log`. Grep each tool's failure markers: cargo/clippy `^error|FAILED|panicked`, pytest `FAILED|ERROR`, tsc `error TS`, npm `ERR!`, playwright `✘|failed`. If needed, read further log line ranges, including failures cut by `head`.
3. Prehand-in: `bash scripts/prehandin.sh >/tmp/p.log 2>&1; echo exit=$?; tail -n 40 /tmp/p.log` (smoke per Start step 2). 4. Batch foreseeable reads, greps and `wc -l` into one turn, via parallel calls or one Bash call with `;` (D-3530).
5. Run `git diff --stat` before a full diff; diff only needed files.
6. Limit each output to 4,000 characters (D-3444). Read additional log ranges for failures. No running commentary; report once at end.
7. Exception: `git commit` must be plain, alone in its Bash call: never `-q`, redirect or pipe. Its Git `[<branch> <abbrev>]` transcript line is required by `--after` for every commit (D-3728, D-4796).
