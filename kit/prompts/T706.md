A stored attempt status cannot tell a verified event's success from a press's or the reconcile's (a press, `app/payments/src/charge.rs:234`, a late answer, `:659`, and a verified event's `store_success`, `app/payments/src/release_proof.rs:401`, all write through the same `handlers::record`, `app/payments/src/handlers.rs:118`), so for a paid pick `held_release` re-fetches the pick's stored intent from Stripe and runs `check_intent` (succeeded, mode, the server's fee, `metadata.pick_id`), as `paid_release` does (`release_proof.rs:206` to `:224`), with no connection held across the fetch; for a $0 pick it keeps `no_fee_release`'s ledger check (`release_proof.rs:243`). A pick ended in `payments` (`payments.pick_intent.ended_at`, read before the fetch and again after storing the success, as D-1478 does for `paid_release`) clears nothing, has its success stored and one late-success refund queued in one transaction (FEE-021, D-2290), and answers `ReleaseError::PickEnded`. The ended branch never upgrades a `FOR SHARE` lock: the refund-or-dispute read takes its `FOR SHARE OF` lock only in a transaction that writes nothing, and the ended-pick refund is written in its own transaction, as `ended_late` does (`release_proof.rs:390`), so no transaction takes `FOR SHARE` and then writes the same row. Nothing else makes a `Releasable` (SEC-030): `held_release` never calls T255's `Releasable::from_stored_success`, which re-clears only a pick whose proof was already spent (D-3358), and it mints no `ReleaseProof` (only `Minter::mint` does).
