## Goal

Plan change D-4418 (the attempt-1 plan gap of BLOCKED T563, verified on `main` c509877b): the daily consent sweep (T563) decides whether to clear a number's vault phone by a suppression check made before its per-number transaction, and `record` (`app/messaging/src/optout.rs:332` to `:349`, the one writer of `messaging.suppression` rows: `suppress` at `:321` for the help-email, email-reply, form, portal and owner paths, the texted STOP in `on_inbound_text` at `:162`, the carrier 21610 in `send_checked` at `:397`) takes no lock, so an opt-out that commits between that check and the clear leaves a listed number with no vault phone, which D-079 keeps so the opt-out stays honored (CON-022, CON-035). This task, run before T563, gives `messaging` a per-number opt-out lock and the two calls the sweep needs, all in `app/messaging/src/optout.rs`, the public ones re-exported through the shared `app/messaging/src/api.rs`. (1) A private helper (for example `lock_number(tx, digests)`) takes, for each distinct digest of the number (its homeowner-phone blind-index digests under every configured `VAULT_INDEX_KEY` version, the set `digests` at `:441` returns), `SELECT pg_advisory_xact_lock(hashtextextended(encode($1::bytea, 'hex'), 4418))`: the new seed 4418, used by no other advisory lock (seeds 0, 21, 43, 55, 76, 151, 274, 391 and 481 are taken in `app/`; `grep -rn pg_advisory app/` before you start and pick no taken one), one statement per digest in ascending byte order of the digest, so two transactions locking one number take its keys in the same order. The lock is transaction-scoped, so every caller runs inside a transaction. (2) `record` takes that lock as its first statement, before the opt-out event insert. Its three callers already call it inside a transaction (`suppress`'s own, `on_inbound_text`'s and `send_checked`'s 21610 transaction), and nothing else about them changes: `suppress`'s newly-listed answer, the event, the confirmation, the alert and the block stay as they are. START (`lift_suppression`) takes no lock: it only takes a number off the list, and a sweep that still sees the number listed keeps its phone. (3) `pub fn listing_key(vault, indexed: &[(u16, [u8; 32])]) -> Option<ListingKey>`, pure, no database and no vault plaintext read (D-4280 stands: the sweep never reads a phone): `indexed` is the contact's homeowner-phone digests as `privacy.contact_index` holds them (T563 reads them through `privacy::api`, D-4280). It answers `Some` only when exactly one homeowner-phone index key version is configured (`Vault::index_versions()`, T702's) and `indexed` holds a digest under that version; the key is then that one digest, which is exactly the set `record` and `send_checked` compute from the plaintext, since only one version exists. Otherwise (two or more versions configured, a rotation under way, or no digest under the only version) it answers `None` and the sweep keeps the phone that run. Why: `rotate_batch` (`app/privacy/src/vault.rs:767`) moves a contact's digest to the active version but nothing re-keys `messaging.suppression`, so while two versions are configured a number listed when only v1 existed has v1 rows only and a v2 contact digest the list does not hold; the plaintext would match it, but reading it would reverse D-4280 and add a daily burst of audited reads against SEC-047's hourly baseline (`docs/spec/security.md:51`, a High alert above three times it). `ListingKey` holds only the digest, with no public field or constructor and a `Debug` that prints no digest. (4) `pub async fn still_unlisted(tx, key: &ListingKey) -> Result<bool, OutboxError>` takes the lock of (1) for the key's digest, then, in a separate later statement (so under READ COMMITTED its snapshot is taken after the lock is granted and sees every opt-out committed before it), reads, in one statement, whether the number has a suppression row under it and whether any `messaging.suppression` row at all has an `index_version` other than the key's version, and answers `true` only when neither holds: while the list is not wholly on the key's version (a listing made under a version since retired, which nothing re-keys, D-4418), the sweep keeps every phone. The lock is held to the caller's commit. Its `///` doc says: call it inside a READ COMMITTED transaction, as that transaction's first statement, holding no other lock, and make no outside call in that transaction. What the lock does not close (D-4418, accepted): an opt-out whose caller resolved the number before the sweep's transaction (the portal's phone on file, a voice press-9, an inbound text matched to its contact) and whose `record` waits on the sweep's lock commits after the sweep cleared the phone; the number is then listed by digest under every configured version, as any listing is, and is still refused every text, but has no vault phone behind it. (5) Tests (TD-CON-37) in the new `tests/integration/tests/optout_number_lock.rs`, fake numbers only, against PostgreSQL: while a test transaction holds `still_unlisted`'s lock for a number, `suppress` of that number (portal channel) and a texted STOP through `on_inbound_text`, each on its own connection in a spawned task, are each seen waiting (a bounded poll of `pg_locks` for an ungranted `advisory` lock of that backend's pid, failing rather than hanging) and finish only after the test transaction commits, the number then listed; with `suppress` called inside an open outer transaction on one connection (its own `begin` is then a savepoint, so `record`'s lock is held to the outer commit), `still_unlisted` on another connection is seen waiting in `pg_locks` and, after the outer commit, answers `false` (this fails if the read is made before the lock is granted, in the same statement, or under REPEATABLE READ); a `suppress` committed before `still_unlisted` makes it answer `false`; a number never listed answers `true`; with one index version configured, `listing_key` of the contact's indexed digest is `Some` and writes no vault-read audit row; with v1 and v2 configured (the two-version `VAULT_INDEX_KEY` built with `tests/integration/tests/vault.rs`'s `key(version, byte)` helper, TD-PRIV-09) it is `None`, and so is a digest under a version not configured; a number listed while only v1 existed, whose contact digest `rotate_batch` then moved to v2, with only v2 then configured (v1 retired), makes `still_unlisted` answer `false` (its v1 row is not on the key's version), and so does any other number while that v1 row exists; the lock on one number does not hold up `suppress` of another. Every existing T029, T093, T321, T356 and T357 test passes unchanged. Privacy and consent work: an Opus worker, an Opus privacy, compliance and security review, and two review rounds.
