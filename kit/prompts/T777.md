# T777: businesses: a sign-in code is texted only to a line whose current number has its text consent and its approval

## Goal

Plan change D-5081 (external code review of Nov 20, 2026, finding F39; CON-019, BIZ-033, SEC-004; D-4039's known gap). `sign_in_lines` in `app/businesses/src/sign_in_lines.rs` lists a member's extra line when any text-consent row exists for it: its `EXISTS` does not require the consent's `number_version` to equal the line's, which `consent::may_text` does, and it does not require the line's `approved_at`, which `notice_recipients` does. So after a member changes that line's number (`team::set_number` keeps the line and raises `number_version`), the next sign-in code is texted to a number nobody ticked, and a number a non-owner linked is used before the owner approved it. The query now requires the same `number_version` match as `may_text` and the same approval condition as `notice_recipients`; a line that fails either is left out, so the code goes to the member's sign-in email as it does for a member with no texting phone. Its `.sqlx/` query file is regenerated. No other file changes: `business_signin.rs`, `consent.rs`, `team.rs` and `channel_preference.rs` are read. Tests in the new `tests/integration/tests/sign_in_number_change.rs`, PostgreSQL, fake data only: a ticked, approved line is listed; after `set_number` it is not, and it is listed again once the new number is ticked (and approved when a non-owner set it); a line waiting for the owner's approval is not listed; a tick by a removed member still does not count. Every existing sign-in test passes unchanged. Remove the known-gap line in `app/businesses/NOTES.md` and close the leftover in `docs/for-casey-review.md`; update `docs/decisions.md`.

Acceptance: `tests/integration/tests/sign_in_number_change.rs` passes against PostgreSQL with every listed case, the changed-number and unapproved cases failing on `main` before the change; every existing sign-in and consent test passes unchanged.
