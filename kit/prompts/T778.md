# T778: jobs, core and server: a dead Payment pending timer is revived, a task that died on its last try is reaped on a busy queue, and a slow queue read is not reported as the database being down

## Goal

Plan change D-5081 (external code review of Nov 20, 2026, finding s F32, F35 and F36; JOB-006, JOB-014, PRIV-007, OPS-004, OPS-007; D-2640, D-3144, D-4349). Three ways a stuck task is never found or is misreported. (1) F32: the daily backstop's `check_timer` (`app/jobs/src/timer_backstop.rs`) revives only a dead `jobs.timeout` task; a Payment pending job's wait is a `picks.payment_returned` task (`PAYMENT_RETURNED_KIND`, its key built in `payment_wait.rs`), and when that one is dead the job stays in Payment pending for good, never reaches a final status, and its PRIV-007 purge is never queued. `check_timer` now also runs `revive_dead` on that key when the job is in Payment pending and its own timer is alive, under the same `MOST_REVIVALS` cap, audit row and alert; `Revival::Missing` and `Revival::Alive` on that key do nothing (no task is queued: missing is the normal state before the timer fires); the key repeats `payment_wait.rs`'s format. (2) F35: `reap_expired` (`app/core/src/tasks.rs`) runs only on a poll that claimed nothing, so on a busy queue a task whose worker died on its last attempt is never dead-lettered, is invisible to the dead-letter alert, and `queue_health`'s oldest-waiting read (`app/core/src/queue_health.rs`), which has no `attempts < max_attempts` filter, counts it until `/healthz` answers 503. The reaper now runs on every poll that claimed fewer tasks than it asked for and at least once a minute whatever was claimed, and the oldest-waiting read leaves out a row no claim can take; `reap_expired`'s and `claim`'s signatures stay; `Worker` gains no field (it is built as a struct literal in `tests/integration/tests/task_queue.rs` and `app/server/src/bin/worker.rs`): the last-reap time is a local in `claim_loop` passed to `spawn_due`, and the minute is read from `self.clock`, so a test advances a `ManualClock`. (3) F36: `check` in `app/server/src/healthz.rs` reports a queue-read error or timeout as the database being down although its round trip has just passed; it now answers 503 as today, with `status` "down", `database` "up" and `worker` "unknown" (a new `HealthState` field, built only in `healthz.rs`; `healthy()` is false for it), the answer's keys unchanged. This task adds no migration: the two indexes for `queue_health`'s `max()` reads wait for a later plan change (see D-5081), and no row of `core.task` is deleted (a done row's dedupe key means once ever). Tests, fake data only: the new `tests/integration/tests/payment_returned_backstop.rs` (a dead `payment_returned` task on a Payment pending job is revived once and the job leaves Payment pending; after the cap, one High alert; one on a job that moved on is left alone) and `tests/integration/tests/stuck_task_health.rs` (a task at its last attempt with an expired lease, beside a steady supply of due tasks, is dead-lettered within a minute and counted by the dead-letter alert, and the probe never reports the worker down for it; a failed queue read answers 503 with database up and worker unknown). Every existing `timer_backstop`, task-queue and `healthz` test passes unchanged; if one pins the reaper to an empty poll, report it, do not change it. Plan change D-5163: `app/server/CLAUDE.md` is near the D-5080 threshold, so this task's notes go to `NOTES.md` only. Build notes go to the end of each crate's `NOTES.md`; update `docs/decisions.md`.

Acceptance: Both new test files pass against PostgreSQL with every listed case, the revival and the busy-queue cases failing on `main` before the change; no migration is added; every existing `timer_backstop`, task-queue and `healthz` test passes unchanged.
