## Goal

Plan change D-4292 (the D-4292 spot reviews, verified on `main` 67827d85; D-1250 named it on Nov 1 and no task took it): every page sends `Referrer-Policy: no-referrer` (`app/portals/src/security.rs:80`, SEC-012, SEC-026), and under that policy the Fetch standard's "append a request `Origin` header" sets the serialized origin of any non-`GET`/`HEAD` request whose mode is not `cors` (every HTML form post) to `null`, so a homeowner's, business's or owner's own form post arrives as `Sec-Fetch-Site: same-origin` with `Origin: null`; `is_cross_site` (`app/portals/src/security.rs:334` to `:347`) reads that `Origin` as cross-site, and `refuse_cross_site` and `business_signup::same_site` answer 403 with a `csrf_rejected` event: no pick, Confirm, feedback, check-in, quote close, business sign-in or sign-up step, notice setting, action-link button, owner sign-in or web-chat turn works in a real browser. The tests hid it: twelve Playwright specs re-send each `POST` with a forged `Origin: https://<host>`, and the Rust route tests and the door matrix (`app/server/tests/door_matrix.rs:372`) send that same forged header. (1) `is_cross_site` decides like this, and its doc says so with the Fetch rule: when `Sec-Fetch-Site` is present it alone decides (`same-origin` is not cross-site whatever `Origin` says, since a page cannot set that header; `same-site`, `cross-site`, `none` or anything else is cross-site); when it is absent (browsers before Fetch Metadata), `Origin: https://<Host>` is not cross-site, `Origin: null` is not refused by this check and is left to the route's token check, and any other `Origin`, or none, is cross-site as today. The `Origin: null` case is safe only because every route behind `refuse_cross_site` or `is_cross_site` also checks the CSRF token bound to the `__Host-` session or pre-session cookie (`CsrfForm`, `csrf_matches`), and that `SameSite=Lax` cookie is not sent on a cross-site `POST`, so an attacker page that sets its own `no-referrer` policy still fails the token; check that every caller does check it, and report a plan gap if one does not. `Referrer-Policy: no-referrer` stays on every response (SEC-012 and SEC-026 require it on every token page, and those pages are where the forms post), and the function's signature and `business_signup::same_site` stay unchanged. (2) `tests/security/tests/cookies_csrf.rs`: the test route gains the rows of TD-SEC-73 (browser shape `Sec-Fetch-Site: same-origin` with `Origin: null` and the right token is 200; `same-site` and `none` with the right token are 403; no `Sec-Fetch-Site` with `Origin: null` and the right token is 200, with no or a wrong token 403), every existing row keeping its answer, and the event and log-line counts following the new refusals. (3) `app/server/tests/door_matrix.rs` (D-2440): `request` sends what a browser sends, `Sec-Fetch-Site: same-origin` with `Origin: null`, for `Site::Own` and `Site::WrongToken`, and the cross row keeps `cross-site`; a new `Site` row sends a wrong token with no `Sec-Fetch-Site` and `Origin: null` and is judged by `judge_csrf` on every served `POST`: on the probed rows through `probe_csrf`, and on the `POST` rows `probed_rows` skips (`:243` to `:246`: `Door::SignIn` and `Door::Link`, sixteen today: the four `/q/*` posts, `/f`, `/c`, `/b/sign-in` and its token step, the eight sign-up steps, `/owner/sign-in` and `/owner/sign-in/passkey`) through a probe of their own using the fixture's links and tokens, so every served `POST` proves the token check backs the fallback. `judge_csrf` needs exactly one `csrf_rejected` event per refusal, and `admit_security_event` stores at most `SECURITY_EVENT_CAP_FLOOR` (50) events of one kind per route template per minute (and per client; the matrix sends no client header, so every probe is `0.0.0.0`) when nothing calls `configure_security_events`: count the refusals each template can get in one minute (today three rows for each of the six actors on a probed row, eighteen, and the new probe's on a skipped row), state the count in the test's doc, and if any template could reach 50, have the matrix fixture call `portals::api::configure_security_events` with a higher cap before it runs; and an own-site `POST` no longer passes on a fail-closed refusal: on the public door (`:446` to `:449`), an admitted realm `POST` (`:461` to `:465`) and `judge_opened`'s `POST` (`:483` to `:488`) it passes only when it is not a 403 and no `csrf_rejected` event was logged under its request ID (a route's own 4xx such as a 422 still passes, with no event), every other expectation staying as strict as it is (D-3706). With today's `is_cross_site` these rows fail, which is the planted proof. (4) `tests/e2e/pick_flow.spec.ts`, `tests/e2e/checkin.spec.ts` and `tests/e2e/feedback.spec.ts`: the `httpsOrigin` helper and its calls are removed, with the header comments that explain them, so each spec posts with the browser's own headers (`baseURL` is `http://127.0.0.1`, a potentially trustworthy origin, so Chromium sends `Sec-Fetch-Site`); any wait that relied on the re-send's `maxRedirects: 0` follows the browser's own redirect instead, and every assertion stays. T644 removes the re-send from the other specs. The removed lines move later lines up; T614's goal cites `tests/e2e/pick_flow.spec.ts:98` by line, and the code it means is unchanged.
