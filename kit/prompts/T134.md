# T134: License sources and object storage behind the adapters

Task T134 (harness, phase 2, stage 6). Slug: sandbox-license-storage.

## Goal

The real license-source and object-storage clients sit behind their adapters: daily lists and the throttled lookup work against the real sources for verification only, and the audit stream and exports land in the bucket through a write-only, prefix-scoped token (CARD-015, LIC-006, LIC-007, LIC-010, LIC-027, OPS-010, OPS-011, PRIV-029). The real store also implements T275's `StorageDelete` (D-1841). The `photos/` prefix uses its own key with read, list and delete; PRIV-029's write-only, prefix-scoped token, versioning and object lock stay in force for the audit-stream and export (backup) prefixes (D-1841). Plan change D-2954 (`sources/01_spec/Changes_Since_v9.3_AUTHORITATIVE.md:250`): the real client also implements T385's `LicenseRecords::lookup_record` and answers in T385's `RECORD_HEADER` format, one record per call, only for a signing-up business's own license, nothing kept (LIC-010): for `roc`, that license's row of the ROC's posted download list or, where that lacks the contact, the ROC's public detail of that one license (a script-built page keyed by an internal license ID, not the six-digit license number, so the client maps the number to it), mapping the ROC's six-digit number format to and from the normalised number; for `city`, that number's row of the latest city spreadsheet; a field the source does not publish (an email, the phone kind, a DBA, a street address) is left empty; a missing license is a 404.
