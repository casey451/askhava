## Goal

Plan change D-4418 (found by the Opus review of T563's plan fix, verified on `main` 954dd68): D-2208 and T321's goal rest on PRIV-024's rotation rebuilding the `messaging.suppression` digests from the vault plaintext (`docs/decisions.md` D-079, D-2208), but nothing does: `rotate_batch` (`app/privacy/src/vault.rs:767`) re-seals contacts and, through `index_phone` (`:483` to `:505`), replaces a contact's homeowner-phone digest with one under the active version only, and no code re-keys a suppression row. `record` lists a number under every version configured at that moment, so a number that opted out while only v1 existed has v1 rows only; once v1 is dropped from `VAULT_INDEX_KEY`, `send_checked` no longer matches it and the number would be texted again (CON-013, CON-035). The consent sweep (T563, through T701's `listing_key`) needs every contact's digest under every configured version, so it can match a listing under any of them without reading the phone. Until re-keying suppression is designed (open in D-4418; the price is that a leaked index key version cannot be retired meanwhile and every phone contact keeps a digest under it, `docs/threat-model.md:18`), PRIV-024 now says no index key version may be retired while a suppression row is held under it, and this task makes that a machine rule. (1) `Vault::index_versions(&self) -> Vec<u16>` in `app/privacy/src/vault.rs`: the configured `VAULT_INDEX_KEY` versions, ascending, read from the vault's own key map (no hashing of a dummy value), with its `///` doc and a unit test; re-exported needs nothing (it is a method of the exported `Vault`). (1b) The contact's homeowner-phone digest is kept under every configured `VAULT_INDEX_KEY` version (`privacy.contact_index`'s key is `(purpose, key_version, digest)`, `migrations/0036_privacy_vault.sql:36` to `:42`, so versions coexist; `find_by_phone` already matches any version): `index_phone` writes one row per configured version (the `blind_index` set) and deletes that contact's homeowner-phone rows under any other version; `rotate_batch` selects, besides contacts sealed under an older `VAULT_KEY`, every contact with a phone that lacks a homeowner-phone digest under a configured version or holds one under a version no longer configured, and re-seals it as today (its plaintext read audited as rotation, PRIV-003), so a batch run until it returns 0 leaves every phone contact with exactly one digest per configured version; `sender-dir` and `email` digests are unchanged. TD-PRIV-09's drill test in `tests/integration/tests/vault.rs` (T022's, taken over here, which makes this a harness task) asserts zero v1 digests after the rotation while v1 and v2 are both configured; that assertion changes, by this decision, to: with v1 and v2 configured each phone contact holds exactly one digest under each, and after a `rotate_batch` with only v2 configured none holds a v1 digest and every number is still found; the batch counts and every other assertion stay. The tests counting a contact's homeowner-phone rows (`retention_purge.rs`, `under_13_purge.rs`, `inbound_first_contact.rs`, `retention_purge_races.rs`) build one-version vaults and are unchanged. (2) New `app/messaging/src/suppression_versions.rs`: `pub async fn check_suppression_versions(conn, vault) -> Result<(), SuppressionVersionsError>` reads `SELECT DISTINCT index_version FROM messaging.suppression` (messaging's own table, static SQL) and fails with the held versions missing from `vault.index_versions()` (version numbers only, never a digest); re-exported through the shared `app/messaging/src/api.rs`. (3) The server and the worker each run it once, after building their `Vault` and connecting, before they serve a request or run a task (the server in `app/server/src/main.rs` after `vault_from_settings` at `:98`; the worker in `app/server/src/bin/worker.rs` at start, building its vault from the same two settings when both are set, as `app/server/src/lib.rs`'s `vault_from` (`:576`) does; `main.rs`, `lib.rs` and `bin/worker.rs` are shared paths), and refuse to start on a failure with a log line naming only the missing versions and D-4418; a start check that cannot read the table (the database unreachable) also refuses to start; a refused start fails closed (nothing is texted), and the host's health check keeps the previous release serving (verify with host: Railway's healthcheck gates a deploy and a failed one leaves the old deployment serving, `docs/brains/deploy-operations.md` O17 and its failure table); a process with no vault configured skips it. (4) Tests (TD-PRIV-31) in the new `tests/integration/tests/suppression_key_versions.rs`, fake numbers only, against PostgreSQL, keys built with `tests/integration/tests/vault.rs`'s `key(version, byte)` helper: an empty list passes with any key set; with v1 and v2 configured, a contact stored before v2 holds a v1 and a v2 digest after `rotate_batch`, one stored after holds both at once, and a phone change replaces both; a contact whose only digest is under a version no longer configured is picked by the next `rotate_batch` and left with exactly the configured ones; a number listed with only v1 configured passes with v1 and with v1 plus v2, and fails naming version 1 with only v2; a listing made with v1 and v2 configured passes with v1 plus v2 and fails with only v2 (its v1 row is held); `index_versions()` returns `[1, 2]` for a v1-plus-v2 key; the refusal text holds no digest. Update `app/messaging/CLAUDE.md` and `app/privacy/CLAUDE.md` with the rule. Plan change D-4473: for T645's web-chat opt-out (which has no vault and may read no phone), this task also adds `pub async fn phone_digests(conn, contact: Uuid) -> Result<Vec<(u16, [u8; 32])>, VaultError>` in `vault.rs`, re-exported through the shared `app/privacy/src/api.rs`: the contact's homeowner-phone digests as `privacy.contact_index` holds them, one per key version, in descending version order (so the first is the active one once rotated, as `blind_index` puts the active first), empty for a contact with no phone; static SQL, no plaintext read, no audit row, no row lock, and it runs inside a transaction (no `ensure_bare`): these are HMAC blind indexes, not contact values, so no vault-read grant applies (PRIV-002, as `find_by_phone` reads the same table). With (1b), a contact stored or rotated under the configured versions holds exactly the set `record` computes from the plaintext. T563 may read its digests through it instead of its own read in `consent_phone.rs` (D-4280 is unchanged either way). Its test, in `tests/integration/tests/suppression_key_versions.rs`: with v1 and v2 configured a stored contact's `phone_digests` equal, as a set, `blind_index` of its fake number, the highest version first; a contact with no phone gives an empty list; it works inside an open transaction. Plan change D-4473, review round 2: so that `phone_digests` (and T563's listing key) never carry a digest under a version that is no longer configured, the start step gains, in `vault.rs` and before `check_suppression_versions`, `pub async fn settle_index_versions(conn, vault) -> Result<(), IndexVersionsError>`, re-exported through the shared `app/privacy/src/api.rs` and run once by the server and the worker after building their `Vault` (same place, same refusal handling as (3); a process with no vault skips it): (a) prune: in one static-SQL statement, delete the homeowner-phone `privacy.contact_index` rows under a version not in `vault.index_versions()` for contacts that already hold a homeowner-phone digest under a configured version (no plaintext read; nothing else is deleted); (b) refuse: when any contact holds homeowner-phone rows and none under a configured version (a version dropped before `rotate_batch` finished under both, against PRIV-024's order: add the new version, rotate until 0, then drop the old), fail and refuse to start with a log line naming the configured versions and the count of such contacts only, never a contact ID or digest. Fail closed: nothing is texted. Rolling deploys: an old process still running with the old key set can write a row under the dropped version after a new process started; the next start prunes it under (a), or, if it is a `messaging.suppression` row, `check_suppression_versions` refuses the start (fails closed). TD-PRIV-31 gains both cases.
