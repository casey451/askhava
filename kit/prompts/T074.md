## Goal

The twin uses the app's fee, matching, quiet-hours and lifecycle rules through the rules_bridge binary (JSON in, JSON out), so Twin checks app/ (docs/test-design.md section 2, D-453). twin.yml installs the pinned Rust toolchain and runs `cargo build -p askhava-server --bin rules_bridge --locked` from the PR's commit before the gate, and a JSON-schema contract test covers the bridge on both sides (D-481). A planted 2-month recurring rule in `payments::rules` turns the twin red as well as a planted wrong fee (D-491). This task also writes `twin/__main__.py` with a `chaos` subcommand (`python3 -m twin chaos --baseline twin/chaos_baseline.json`, exit 1 on any problem not in the baseline) and commits `twin/chaos_baseline.json` from a chaos run through the app's rules, after T005 to T007 changed the twin; T126 runs it (D-491). Per the second trial (D-491): one long-lived process speaking JSON lines `{id, call, args}`; the schema is hand-written at `app/server/rules_bridge.schema.json`; the Rust contract test uses a small subset validator (no JSON-schema crate is allowed); `twin.yml` sets `SQLX_OFFLINE=true`; the measured cost is about 0.05 ms a call, so the budget is 1 ms.

Acceptance: `twin.yml` builds `rules_bridge` from the pull request's commit and the gate passes through it; the JSON-schema contract test passes on both sides; a planted wrong fee in `payments::rules` turns Twin red (shown in the task report).
