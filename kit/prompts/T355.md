## Goal

Nov 10 code review, privacy F3, as fixed by the plan review's H3 and its re-review (D-2627; PICK-022, PRIV-005, FEE-052): the release claim reads its target unlocked (`show`, `app/picks/src/release.rs:287`, through `release_target`) and `record` (`:428`) inserts `picks.release` with `ON CONFLICT (pick_id)` only, while `fraud_warning` (`app/picks/src/unreachable_refund.rs:533`) first calls `payments::api::early_fraud_warning` (`app/payments/src/refunds.rs:152`) with the caller's `released` snapshot, before any lock, so the refund is sent while a racing release can still commit and open the name and address: the business gets the refund and the details (FEE-052 refunds only a charge whose details were not yet released). Fix, all in `picks`: (1) the fraud path first runs one short transaction that takes `SELECT … FROM picks.pick WHERE id = $1 FOR UPDATE`, then, in a separate statement under that lock, reads whether a `picks.release` row exists; the pick counts as released when that row exists or the caller's `released` flag already says so (stricter only: a caller's `true` is never read as `false`, D-3118; the done `tests/integration/tests/unreachable_refund.rs` (T191, T282) passes `true` for a pick with no release row at `:487`, expects `Ok(false)` and, at `:500`, exactly one succeeded refund for that pick, from its later `false` call); if it counts as released the warning only alerts (the pick goes to Casey's decision list, as today); if none exists it inserts a durable marker, one `picks.fraud_hold` row for the pick (`migrations/0181_picks_fraud_hold.sql`: pick ID primary key, time; the app role may INSERT and SELECT only), idempotently (`ON CONFLICT (pick_id) DO NOTHING`, since the fraud path may run again for the same pick: the done `unreachable_refund.rs` calls it at `:489` to `:493` with a failing refund client and again at `:497` with a working one, which must then refund), and commits; only then does it call `early_fraud_warning` with `released` as decided under that lock (false here), so the refund goes out only for a pick that can no longer be released; the existing job move and `fraud_refunded` end follow as today once the refund is read as succeeded; (2) `record` takes the same `SELECT … FOR UPDATE` on the pick first in the claim's transaction, then, in a separate statement, checks that the pick still has the wanted status, no end and no `picks.fraud_hold` row, and answers `MovedOn` otherwise: on a regular job (`claim_then_read`, `:322`) that is before any vault read; an emergency job reads the vault before it claims (`read_then_claim`, `:340`, INT-029), so there the refused claim follows a read but shows and releases nothing; (3) `end_pick` (`:482`) keeps its status-only guard: `no_call_at_72_hours` (`:451`) and the other callers end released picks through it, and only the fraud path checks for a release row. This is a clarification consistent with FEE-052's order (alert; refund an unreleased charge at once; list a released one): "not yet released" is decided under the pick's lock and the release is then refused, never both. Tests in `tests/integration/tests/release_fraud_race.rs` (TD-PICK-59), two connections and row locks, no sleeps: (a) the claim locks the pick, inserts its release row and holds its transaction open; the fraud path blocks on the pick lock; the claim commits; the fraud path then finds the release row, writes no hold and sends no refund (the fake refund client is never called); (b) on a regular (non-emergency) job, the fraud path commits its hold first; the claim then answers `MovedOn`, writes no release row and no `vault_read.picks.release` audit row, and the refund is sent once; (c) `no_call_at_72_hours` still ends a released, paid pick as a no-show; the plain release and the plain fraud end behave as before. Update the `picks` `CLAUDE.md` and `docs/decisions.md`. Any test this task writes that builds an `adapters::api::PaymentIntent` (a fake `IntentStripe` or `PaymentsAdapter` answering an intent) builds it with `serde_json::from_value` (the type derives `Deserialize`), never a struct literal, and gives a succeeded intent a fake `ch_` `latest_charge`, so T352's new field (`#[serde(default)]`) breaks no file T352 does not own (D-3134).
