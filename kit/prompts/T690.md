## Goal

Plan change D-4361 (unwired sweep orphan 9, its second pass and the round-1 review, `main` 77a49d7cc; BIZ-026, BIZ-002; D-178, D-254, D-1699, D-1712, D-2954). A sign-up parked by "That number is old" never resumes: `resume_on_new_record` (`app/businesses/src/signup.rs:636`) has no caller (D-2954 logged it with no owner). The recorded ROC list stores no contacts (`licensing.agency_record`, `migrations/0050_licensing_imports.sql:22` to `:32`); a record's contacts come only from `licensing::api::read_own_record` (`app/licensing/src/own_record.rs:146`), one adapter lookup with nothing stored (D-1699). (1) The new `app/businesses/src/record_resume.rs`: a daily `businesses.record_resume` run (registered in the shared `app/server/src/lib.rs` with the license-record source, the Verify adapter `send_code_seen` takes (`app/businesses/src/identity.rs:170`) and the ID secret, scheduled in the shared `app/server/src/bin/worker.rs` after the ROC list's run hour) that, when a ROC list newer than the last one it acted on is recorded, queues one `businesses.record_resume_one` task per sign-up with `waiting_on_record_since` set, at most `RESUME_BATCH` (a setting, default 25) per list, the least recently looked up first (never looked up before any looked up; ties by the oldest wait), each sign-up's last lookup time read from T690's own finished `businesses.record_resume_one` rows in `core.task` (`done_at`, payload the sign-up ID only; finished rows are kept and nothing in `app/` deletes them), so no column or migration is added, deduped by sign-up and list date, so each waiting sign-up gets at most one lookup per new list and every one is reached in turn however many wait. Each task makes one `read_own_record` for the sign-up's license number (a failed or misread lookup does nothing and waits for the next list, LIC-008), builds `RecordSeen` from it in memory and calls `resume_on_new_record`. (2) Quiet hours (QH-001): `send_code_seen` sends a Verify text at once with no outbox hold, and the run starts after the ROC list's 6 a.m. run hour (`app/licensing/src/daily_lists.rs:100`), so the code (and the optional text) is sent only between 8 a.m. and 8 p.m. in the stricter of Arizona time and the record phone's area-code time (`messaging::api::decide`'s rule); the task checks Arizona time before the lookup and, outside 8 a.m. to 8 p.m. Arizona, re-queues itself for 8 a.m. without looking up; after the lookup it re-queues only when the record phone's area-code time is the later one (its payload carries no contact, so that one re-queued task looks up again); each re-queue uses its own dedupe key (`businesses.record_resume_one.held.<sign-up>.<list date>.<until>`, the target time included so a second hold of the same task is never dropped, as `business_notice` does with `.held.<id>`, `app/messaging/src/business_notices.rs:505`), since `core.task.dedupe_key` is unique and finished rows are kept; it resumes nothing until it sends, and an email or letter step is not held. On a resume it calls `identity::send_code_seen` with that `RecordSeen`, so the next code goes only to the new record contact, never the old one or a typed one (D-1712): a phone change resumes at the text step and gets the Verify text code; an email-only change resumes at the email step and gets the Verify email code, with no text; an address-only change resumes at the letter step and records it for the Lob mailing, with no text or email. The `signup_record_updated` text (`app/messaging/templates/en.json:432`) goes only on a text-step resume, to that new phone, and only if `messaging` can send to a number held in memory without storing it (PRIV-001, D-1699); otherwise only the code goes and the template stays unused, recorded in this task's decision entry. A contact that only disappeared does not resume. D-1712's open `send_code` key gap is checked at claim and recorded if still open. Tests in the new `tests/integration/tests/record_resume.rs` (TD-BIZ-56), PostgreSQL and the license-record stand-in, fake data only. Update `app/businesses/NOTES.md` and `docs/decisions.md`.

Acceptance: TD-BIZ-56 passes against PostgreSQL, failing on `main`; every sign-up, identity and daily-list test passes unchanged; no record contact is written anywhere.
