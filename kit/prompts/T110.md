## Goal

After a restore, replay rebuilds messages, charges and events from the off-database records and the vendors' records with IDs derived from what each identifies, so nothing replayed sends or charges twice (OPS-015 to OPS-017). Nov 11 vendor-double review batch 4, F5 (D-2764): Twilio stores no custom key on a message and its Messages list filters only by `To`, `From` and `DateSent`, so OPS-017's "nothing sent twice" check never asks the sent log for the app's derived key (the stand-in's `MessageKey` filter is test-only, T377): it lists the messages sent from Laftly's numbers to the row's recipient over the row's send window (`To`, `From`, `DateSent>`/`DateSent<`) and matches an outbox row to a listed message by recipient, sender, a SHA-256 digest of the body (a body Twilio already redacted matches on recipient, sender and send time within the window, and an ambiguous match is not resent but listed for Casey) and send time; a matched row is marked sent with that SID, never resent. A test shows a message whose outbox row was lost in the restore is found and not resent without any key filter. Plan change D-3155: no adapter can list Twilio's messages (`SmsAdapter` only sends, `SmsBodyDelete` only redacts, `app/adapters/src/sms.rs:23` to `:49`) and `TwilioHttp` has no `GET` (`app/adapters/src/base.rs:148`, its client and token private). New `app/adapters/src/sms_list.rs`: a separate trait `SmsSentLog: SmsAdapter` (the `SmsBodyDelete` pattern, D-1753, so no existing fake changes) with one method listing the messages from one sender to one recipient over a `DateSent` window (Twilio's `To`, `From`, `DateSent>`, `DateSent<` filters, following `next_page_uri`), implemented for `TwilioSms` through a new Basic-auth `GET` helper on `TwilioHttp` in `base.rs` (after T377); `sms_list` is declared in the shared `lib.rs` and exported through the shared `api.rs`. The stand-in's Messages list already honours those filters (T377), so no stand-in file changes; the replay test runs against the served stand-in.
