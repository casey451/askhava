# T090: privacy: photo checks by bytes, re-encode without EXIF or GPS, signed links

Task T090 (build, phase 1, stage 4). Slug: privacy-photos.
Branch: `claude/task/T090-privacy-photos`
Model: `claude-opus-5-5`, effort medium. Reviewer: `claude-opus-5-5` (areas: privacy, security).

## Goal

`privacy` checks each photo's type and size from its bytes, decodes it under explicit limits with HEIC refused, re-encodes it with all metadata stripped before anything else sees it, encrypts it under the vault key with its job and photo ID as associated data before object storage, and serves it only through short-lived links with the token in the path (PRIV-013, PRIV-014, PRIV-023, PRIV-025, PRIV-028); the photo-ask wording and deleting a picture text's media from the texting provider (PRIV-015) are T212's (D-491).

## What this task rests on

Requirements (each sentence as it stands in `docs/spec/`):

- **PRIV-013** Photos are optional, asked for as INT-044 says, with size and type limits checked from the file bytes rather than the name (D-432). (`docs/spec/privacy.md:17`)
- **PRIV-014** Every photo is re-encoded at upload with all metadata (EXIF, GPS, XMP, IPTC and maker notes) stripped before it is stored, screened by any check, sent to any AI step or placed on any card, the uploaded bytes with metadata are never stored (the vault copy, PRIV-001, is the stripped one), and photos are stored privately and served only by the app's own photo route through short-lived signed links, never a direct storage link (D-383, D-454). (`docs/spec/privacy.md:18`)
- **PRIV-023** Every photo is encrypted by the app with AES-GCM under the vault key, with associated data naming its job and photo ID, before it is written to object storage, so the storage bucket never holds a readable photo (D-454). (`docs/spec/privacy.md:27`)
- **PRIV-025** Photo decoding runs with explicit limits (8,000 px per side, 40 megapixels, 256 MiB) behind a decode semaphore and a timed `spawn_blocking`, with a per-route body limit; only the primary frame is kept and orientation is applied before metadata is stripped; HEIC is not decoded in the app at launch (a HEIC upload gets a plain reply asking for a JPEG or PNG, which phones send by default), so no native-code decoder runs in the process that holds the keys (D-480). (`docs/spec/privacy.md:29`)
- **PRIV-028** Contact fields deserialize straight into `Redacted<String>`, request tracing logs only the matched route template and never the URI, photo and action links carry their token in the path and never the query string, audit rows hold record IDs and never contact values (a homeowner's portal edit logs the field name only), and `intake.property` holds only the vault contact ID and the town, with a schema test (D-480). (`docs/spec/privacy.md:32`)
