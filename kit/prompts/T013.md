# T013: core: task queue with leases and SKIP LOCKED, rate-limit counters

Task T013 (build, phase 1, stage 2). Slug: core-task-queue.

## Goal

`core` has a database task queue that workers claim with `FOR UPDATE SKIP LOCKED` and leases, so timers survive a restart and two workers never run one task, and atomic rate-limit counters keyed on the client IP from `CF-Connecting-IP` only behind Cloudflare or the host proxy (JOB-006, SEC-040). Per the second trial (D-491): the claim, fenced finish/fail/renew, `release_leases` and `reap_expired` SQL as section 2 of the trial report shows; `lease_until` computed in Rust from the injected clock; `last_error` a fixed `&'static str`; `register_handlers()` returns the registry; tokio's `sync` feature; the claim loop goes into the shared `app/server/src/bin/worker.rs` (D-491); tests for exactly-once with 100 and 1000 tasks across two workers, lease reclaim with old-owner fencing, dedupe refusal, backoff then dead-letter.

From `docs/brains/postgres-operations.md` (cite its tags in the PR; read other sections only when a design choice needs them):

### 2. Principles (lines naming this task's requirements)
**P9. The queue table is hot: index it narrowly, keep transactions short, vacuum it harder.** PostgreSQL: skipping locked rows "provides an inconsistent view of the data, so this is not suitable for general purpose work, but can be used to avoid lock contention with multiple consumers accessing a queue-like table" (select.sgml text, commit https://forger.sitiv.fr/open-dsi/postgres/commit/df630b0dd5ea2de52972d456f5978a012436115e.diff). Dead tuples pile up when a long transaction holds back vacuum, and lock queries slow down scanning them (Brandur 2015); "A single transaction that takes 2 minutes to complete pins the horizon for the full 2 minutes" (PlanetScale). Autovacuum's defaults are threshold 50 and scale factor 0.2, overridable "for individual tables by changing table storage parameters" (autovacuum docs). So: a partial index `ON core.task (run_at) WHERE done_at IS NULL`, a unique index on `dedupe_key`, lower `autovacuum_vacuum_scale_factor` on `core.task`, delete finished rows in small batches if they are not kept [inferred]. Serves JOB-006, Arch 5 task queue.

From `docs/brains/rust-production.md` (cite its tags in the PR; read other sections only when a design choice needs them):

### 2. Principles that bind this codebase (lines naming this task's requirements)
**R11. Work that leaves the database is queued in the same transaction as the state change.** A state change and its `core.task` row commit together; never call a vendor inside the transaction that changes status. Brandur: enqueue mid-transaction and the job runs too early; enqueue after commit and a crash loses it ("Data is persisted, but the background work doesn't get done"). Here the queue is in the same database, so the insert is simply part of the transaction. Serves JOB-004, JOB-005, JOB-006, Arch 4 rule 2.
**R12. Claim with `SKIP LOCKED`, keep claim transactions short, hold a lease, re-check on run.** PostgreSQL: skipping locked rows "can be used to avoid lock contention with multiple consumers accessing a queue-like table" (select.sgml text, see postgres brain P9). Long transactions pin the vacuum horizon and degrade a hot queue (Brandur 2015; PlanetScale 2026). So: claim and commit, run the handler outside that transaction, finish with a fenced update. Handlers first re-check the current status (JOB-006). Serves JOB-006, Arch 5 task queue.
