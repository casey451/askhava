## Goal

Plan change D-3118 (FEE-050, FEE-027; D-2204; owner call). FEE-050 auto-submits a dispute's evidence only when the charge has a recorded release and a call attempt or a 3DS-authenticated payment, but nothing records whether a payment was 3DS-authenticated: `adapters::api::PaymentIntent` (`app/adapters/src/payments.rs:32`) has no such field and no table holds it. `PaymentIntent` is built by struct literal in ten done test files (`app/server/tests/release_recovery.rs:416`, `app/server/tests/request_timeout.rs:183`, `tests/integration/tests/auto_confirm.rs`, `charge_attempts.rs`, `confirm_and_pay.rs`, `fee_fixed_at_pick.rs`, `fee_limit_race.rs`, `late_success.rs`, `late_success_ended.rs`, `stripe_webhook_dispatch.rs`) and returned by the `PaymentsAdapter` trait that their fakes implement, so neither the struct nor the trait changes: the result is a separate read. (1) `app/adapters/src/payments.rs`: a new inherent method on `StripePayments` (`:195`), not on any trait, fetches `GET /v1/payment_intents/{id}?expand[]=latest_charge` through the existing vendor client and returns a new `ThreeDs` value from `latest_charge.payment_method_details.card.three_d_secure.result`: `Authenticated` only for `authenticated`; every other value (`attempt_acknowledged`, `exempted`, `failed`, `not_supported`, `processing_error`), a missing `three_d_secure`, a missing or unexpanded `latest_charge` or a card-less method is `NotAuthenticated`; a fetch error is an `AdapterError` as today. (2) The stand-in follows real Stripe: `stand_ins/stripe.py` stores, on each succeeded intent, `latest_charge` as a `ch_` ID string and a charge object under that ID with `payment_method_details.card.three_d_secure` (`result` `authenticated` after `authenticate(..., passed=True)` (`:235`), and none for a card that never asked for 3-D Secure); `stripe_fetch` (`stand_ins/server.py:250` to `:254`, which today returns the stored object whatever the query) expands `latest_charge` to that charge object only when the query asks `expand[]=latest_charge`, and otherwise returns the ID string, so a plain fetch keeps decoding and T352's later `latest_charge: Option<String>` (D-2623) reads the same stored ID; `tests/contract/test_stripe_three_ds.py` checks the plain fetch (a `ch_` string), the expanded fetch with and without `three_d_secure`, and the confirm answer (a string). (3) `migrations/0172_payments_three_ds.sql`: `payments.charge_three_ds` (pick ID primary key, `authenticated` boolean, recorded time; app role SELECT and INSERT only). (4) `app/payments/src/three_ds.rs`, through `payments::api`: `record_three_ds(conn, source, pick)` reads the pick's `stripe_intent_id` from `payments.charge_evidence`, asks a small trait the module defines (implemented for `StripePayments`, as `IntentStripe` is, `app/payments/src/intent_http.rs:15`, so tests can fake it) and inserts the row once (`ON CONFLICT DO NOTHING`); a pick with no charge evidence or a fetch error stores nothing and returns the error to the caller; `three_ds_authenticated(conn, pick)` is `true` only for a stored `true` row: no row, an unknown or a missing result reads as `false` (the rule FEE-050's check relies on). Callers: T314's dispute handler records it, then reads it. No card data, cardholder name or homeowner detail is stored or logged; only the pick ID and the boolean. Tests in `tests/integration/tests/three_ds_record.rs` (TD-FEE-69) with a fake source: an authenticated, an `attempt_acknowledged` and a no-3DS payment store true, false and false; a second record changes nothing; a pick with no row reads false; no charge evidence stores nothing. `payments` is money code: its 95% branch floor holds. Update the `payments` and `adapters` `CLAUDE.md` files, add this task's line to the `payments` module notes of `docs/architecture.md` (found by grep, never loaded whole; D-3079; section 3's `payments` row already names the table, D-3118) and `docs/decisions.md`. Harness (adapter and stand-in paths): an Opus review.

Acceptance: TD-FEE-69 passes against PostgreSQL and the stand-in contract test passes; a plain fetch of a succeeded intent from the stand-in returns `latest_charge` as a `ch_` string; every test that builds `PaymentIntent` or implements `PaymentsAdapter` compiles and passes unchanged, and every existing stand-in contract test passes unchanged; the `app/payments/` 95% floor holds.
