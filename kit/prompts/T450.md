This task adds only what T302 serves; it calls no `businesses::api` code check (T302's `server` route calls `check_code`, `start_signup_check`, `verified_by_link` and `confirm_mailbox`). (1) Route constants beside `SIGNUP_ROUTE`, one per sign-up `POST` step (the form, the identity code, the email code and its resend), each under `/b/signup/`, and every form's `action` taken from them. (2) Two screens: `Screen::IdentityCode` (after `Contact`: one code input with its label, `autocomplete="one-time-code"`, `inputmode="numeric"`, the masked contact it went to, a refused or expired code shown as an error beside the field, A11Y-030) and `Screen::EmailCode` (BIZ-040, BIZ-042: the code input, "No email? Check your Spam or Junk folder." and a resend button). (3) On the form, the notice-channel choice (BIZ-036): email preselected; text and both offered only while business texting is on (TXT-035), never preselected; while texting is on the text phone field (`type="tel"`, `autocomplete="tel"`) is always rendered, labelled as the number for job texts only, never shown or hidden by JavaScript (the page works without it, A11Y); the consent box stays unticked, after the choice, with its full CON-019 wording naming every channel it covers and "Laftly never places recorded or automated calls to you." ahead of any code being sent; `TEXT_PHONE_MISSING` shows beside the phone field. The wording is rendered on the server but the channel is chosen in the browser, so the form also carries, in hidden fields, the channels the shown wording named and a MAC over them, `businesses::api::CONSENT_VERSION` (`app/businesses/src/consent.rs:28`) and the page's pre-session CSRF token, made with `ID_SECRET` the way link tokens are: `askhava_core::api::link_token(&id_secret, LinkKind::Action, record, &salt)` (`app/core/src/ids.rs:254`; `IdSecret`'s HMAC-SHA256 `mac` at `:68` is private to `core`, so `link_token` is its public door), where `record` (`Uuid::from_bytes`) and `salt` (`LinkSalt::from_bytes`) are the two 16-byte halves of the SHA-256 (`sha2`, already a `portals` dependency) of the length-prefixed fields `signup-consent`, the channels in a fixed order, the version and the CSRF token; the token is compared in constant time (`subtle`, already a dependency). The server verifies it before anything else: a missing or bad MAC is handled as a mismatch, and a post is accepted only when the verified channels cover the chosen channels; on either, nothing is stored (no consent of either channel) and `FormAgain` comes back with `Entered.text_chosen` set, the wording now naming texts and the box unticked. The stored wording always comes from `businesses::api::consent_wording(verified channels)` (`consent.rs:126`) on the server, never from posted text, so a text consent is only ever stored for words she saw (CON-019). One box naming each channel is kept, as CON-019 words it, rather than a second text box. (4) A pure parser for the form's channel, shown-wording and phone fields giving `Entered.text_chosen`, the text phone (never logged) and the shown channels only when their MAC verifies (the caller passes the `IdSecret` and the CSRF token), so T302 builds `SignupConsent` from a post only when it did and otherwise shows `FormAgain`. English only: the Spanish page is T202's. Tests in the new `app/portals/src/tests/signup_code_screens.rs` (one `mod` line in the shared `tests/mod.rs`), fake data only: each screen renders its input, label, error and the route it posts to; text is not offered while texting is off (TD-BIZ-13) and the text phone field is rendered whenever it is on; choosing text without a phone gives `TEXT_PHONE_MISSING`; the consent wording names texts only when chosen (TD-CON-08); choosing text with a ticked box whose shown wording named email only gives no consent to store and `FormAgain` naming texts with the box unticked, so no Text consent is stored; a forged field naming texts with a bad or missing MAC (or one made for another CSRF token or version) stores nothing and gives `FormAgain`; every form posts to a route constant.
