## Goal

Performance track (D-3292, from Casey's performance review `docs/audit/performance-review-2026-11-12.md`), part 1: the database measurements the route benchmark (T417) and the war games (T234, T297) read, metrics only (PERF-004), and the national-size ZIP lookup measurement (PERF-003, measure only, no fix). Nothing here changes how a request behaves. (1) `app/core/src/db_metrics.rs`: a `tracing_subscriber` layer that keeps only numbers from sqlx 0.9's own events: each executed statement (target `sqlx::query`, turned on by `log_statements` on the app pool's connect options) adds one to a statement counter, and each pool acquire (target `sqlx::pool::acquire`, its `acquired_after_secs` field, turned on by `acquire_time_level`) adds to an acquire count, a wait sum, a wait maximum and fixed log-scale wait buckets from 0.1 ms to 5 s, so a reader can take a nearest-rank p95 from two snapshots' bucket differences. The layer never reads, stores or logs the SQL text, a bind value, the database URL or any field other than those numbers (SEC-001, PRIV-016); the statement and per-acquire events never reach the JSON log output, so the layer gets its own per-layer filter (a global filter would hide them from the layer too). A slow acquire over 250 ms (`acquire_slow_threshold`) logs one WARN line through the existing JSON layer holding only the wait seconds. (2) `app/core/src/db.rs` `app_pool` turns those on and registers the pool so a snapshot can read its size, idle count and maximum (`PgPool::size`, `num_idle`); `max_connections`, `ASKHAVA_DB_POOL_MAX` and `ACQUIRE_TIMEOUT` stay exactly as they are (no pool-size change). `app/core/src/logging.rs` installs the layer; `app/core/src/lib.rs` declares the module. (3) `GET /__test/perf/db` on the test-control router (`app/core/src/test_control.rs`, under the same feature, environment and bearer-secret rules as its other routes and the same 404 without them, SEC-035) answers a JSON snapshot: statements, acquires, wait sum, maximum and bucket counts in microseconds, pool size, idle and maximum, and `"acquire_timeouts": "not exposed"` (sqlx emits no event for a timed-out acquire; the benchmark's error rate covers it). A caller takes two snapshots and subtracts; with one request in flight the statement difference is that request's queries. Its tests sit with the other feature-gated test-control tests. (4) `tests/integration/tests/db_metrics.rs` against the CI Postgres: a known handful of statements moves the counter by exactly that many; with a pool of 1 and a held connection a second acquire's wait lands in the right bucket and the maximum; a slow-acquire WARN line and every log line written during the test hold no SQL text, no URL and no planted fake value (TD-OPS-41). (5) `tests/integration/tests/perf_zip_scale.rs` (PERF-003): builds a synthetic national-size markets file that passes `askhava_catalog::markets::parse_markets` (about 41,000 ZIP codes over about 30,000 towns, made-up codes and town names) and times `town_for_zip` for the first, middle and last ZIP and an unknown one over a fixed number of calls, printing one JSON line with p50 and p95 per lookup in microseconds; it fails only when a lookup returns the wrong town or a town for the unknown ZIP, never on time (the targets are goals, D-3292), and is `#[ignore]` so `Ci` stays fast (T417 runs it). Update the `core` `CLAUDE.md`, the performance-measurement note in `docs/architecture.md` (found by grep for D-3292, never loaded whole) and `docs/decisions.md`. A harness task so the measurement layer is reviewed by Opus before anything is tuned from it.

Acceptance: `tests/integration/tests/db_metrics.rs` passes on the CI Postgres; `cargo test -p askhava-integration --test perf_zip_scale -- --ignored` passes and prints its JSON line; the test-control tests prove `/__test/perf/db` answers 404 without the secret and in the test and live environments; every existing test passes unchanged and the pool's size and timeout are unchanged.
