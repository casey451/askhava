## Goal

Plan change D-3055 split the accepted-quote email and the quote page's accepted quote out to T388; this task keeps the Confirm review step's pieces (`confirm_pay.html`, `confirm_pay.rs`, T224's, extended here). No route serves the Confirm page yet: T261 serves `GET` and `POST /b/picks/{pick}/confirm` and calls what this task builds, so every case here is proved by calling the functions against PostgreSQL, never through a served route or a browser. (1) "Can't take it" (PICK-050): the Confirm page already links to `/b/picks/{pick}/cant-take` (`app/portals/templates/confirm_pay.html:37`, T224's) and T214 built that page and its action (`portals::api::cant_take_page`, `cant_take_pick`, `picks::api::cant_take`; D-2994); this task adds no second page or action and changes neither: it keeps the link on every Confirm page that has a form (not on the paused refusal) and proves it in the rendered page. (2) The first opening of the Confirm page (OPS-037): a function the route's `GET` calls, which finds the pick notice's row for that person among `messaging::api::notice_log(business, job)` and stamps it through `messaging::api::record_first_open` (T198's), once, exactly as `business_actions::open_quote_form` does for the Quote link (`app/portals/src/business_actions.rs:990`); opening changes nothing else. (3) The business-terms record (TERMS-033, TD-TERMS-11): business acceptances belong to `businesses`, not `intake` (`migrations/0054_intake_terms_acceptance.sql:9`; `intake.terms_acceptance` allows only `quote_page` and `text_pick` and requires a homeowner, `:14` to `:21`), and `businesses.terms_acceptance` allows only `business_signup` and has no pick column (`migrations/0119_businesses_signup_identity.sql:32` to `:43`, the channel at `:40`). `migrations/0159_businesses_confirm_terms.sql` widens its channel check to `business_signup` and `confirm_page`, adds a nullable `pick_id` (a picks record by ID only, no cross-schema foreign key) with a check that it is set exactly for `confirm_page`, and a unique index on `pick_id` where it is set; the table stays append-only for the app role and every existing row and the TD-TERMS-08 case (`tests/integration/tests/identity_chain.rs:421`) stay as they are. `app/businesses/src/confirm_terms.rs`, through `businesses::api`: `record_confirm_terms(conn, business, person, pick, terms)` stores one row with channel `confirm_page`, the pick ID, the confirming person, the business-terms version, the SHA-256 of its published text, the language and the assent line the page shows ("You're agreeing to business terms version <n>."), in the caller's transaction; a second press for the same pick (after a decline, or a repeat) stores nothing (the unique index), and a page load stores nothing. T261 calls it in the press's transaction. (4) SEC-027's Confirm-page check (moved from T199, D-493): with "This inbox is shared" on (`portals::api::inbox_shared`, T199's) a Confirm inside a live session needs a fresh Verify code to that person's own phone, by T199's rule `action_links::fresh_code_needed`; this task adds the Confirm page's code step (the field and its error in `confirm_pay.html`, A11Y-011 and A11Y-012 as the pick code form) and the check `confirm_pay.rs` exposes for the route, with the code tries counted under SEC-014's limits through T272's `portals::api::admit_code_try` and `portals.code_try` reservations; without the switch nothing changes. Tests in `tests/integration/tests/confirm_terms.rs`: the rendered page holds the link (TD-PICK-43's Confirm half; the pick-notice half is T214's and T386's); the first opening is stamped once; a press stores one `confirm_page` row with the pick ID and a second stores none (TD-TERMS-11); a shared inbox needs a fresh code and too many wrong codes hit the SEC-014 limits (TD-SEC-32). The served halves (the route, the reload in a browser) are T261's (`app/server/tests/confirm_route.rs`, `tests/e2e/confirm_served.spec.ts`). Update the `portals` and `businesses` `CLAUDE.md` files, `docs/architecture.md` section 3 (the new column) and `docs/decisions.md`. (D-493)
