## Goal

Plan change D-4051 (Casey's outside code audit, item B15, Nov 16, 2026): the safety call's `Gather` action (`app/server/src/voice_status.rs:76` to `:94`) runs `calls::api::safety_key_once` and, when it fails (a pool or database error), only logs the error and still answers 200 with hang-up TwiML, so the homeowner's "press 9" opt-out (CON-035: every way she revokes consent feeds the suppression list at once) is lost, and Twilio has nothing to retry. The safety call is off until T407 turns it on, which is why T407 now depends on this task. This task makes the key durable: when the key step fails, the route queues a `calls.safety_key_retry` core task (`askhava_core::api::enqueue`, in the new `app/calls/src/safety_key_retry.rs`, exported by one line in the shared `app/calls/src/api.rs` and registered in the shared `app/server/src/lib.rs` inside `register_safety_call` (`:1208`, beside `SAFETY_CALL_KIND`, using `SafetyParts`' vault; `register_handlers` at `:648` has no vault), the kind constant named `*_KIND` and the give-up alert `*_ALERT`, since TD-OPS-36 (`tests/integration/tests/task_registry.rs`) scans every `*_KIND` constant) carrying the whole `SafetyCall` that `safety_key_once` needs (alert, message, contact and arrival: IDs and a timestamp only) and the digits, no phone and no body (PRIV-016), whose handler re-runs `safety_key_once` (it takes the key once per call, so a repeat changes nothing) until it succeeds, with the core queue's retries, and raises one High `ops` alert (no phone) when it gives up (it knows its last attempt from `Claimed.attempts` against the maximum it set, as `alert_if_last` in `app/privacy/src/purge.rs:347` does); Before choosing, the worker checks in the Twilio stand-in and the vendor notes what a non-2xx answer to a `Gather` action does (a voice action is not retried like a status callback; Twilio speaks an error or calls a fallback URL) and writes the finding in the module doc. The likeliest failure, a pool acquire that fails, also fails the enqueue, and a non-2xx answer makes Twilio speak an error, not retry; so when both the key step and the enqueue fail, the route answers 200 with a bounded `<Redirect>` back to the same action URL, optionally after a short `<Pause>` of a few seconds before each redirect (method POST, carrying `Digits` and an attempt count in the query, at most 3 attempts), so Twilio posts the key again, and after the last attempt it says "To stop texts, reply STOP to any message from us." before hanging up, with one High `ops` alert if one can be raised; the worker may pick the redirect, the spoken line or both after checking the stand-in, and tests what it picks. (D-4064, the Opus pre-claim check) `SafetyCall::from_query` (`app/calls/src/voice.rs:297` to `:309`, not owned and not changed) accepts exactly its four fields, and a `<Redirect>` POST carries no `Digits` form field, so `voice_status.rs` strips the redirect's added `attempt` and `Digits` fields from the query before `SafetyCall::from_query` and reads `Digits` from the query when the form has none; the redirect URL's `&` is written `&amp;` in the TwiML. The Twilio stand-in (`stand_ins/twilio.py`) models no `Gather` or `Redirect` (D-2763), so the tests inspect the returned TwiML. `tests/integration/tests/voice_call_plan.rs:46` compiles `voice_status.rs` by `#[path]` with only `inbound_text` beside it and no dead-code allow, so `voice_status.rs` imports only `crate::inbound_text` and crates, and every new item in it is reached from `routes`, or clippy's dead-code lint fails that test crate. Hang-up TwiML is still returned whenever the key was taken or queued. Tests in the new `tests/integration/tests/safety_key_retry.rs`, against PostgreSQL with the stand-in, fake data only: a "9" whose first `safety_key_once` fails with a database error is queued (the failure is made in the test only, for example a test-created trigger on the suppression-list insert that raises once for the fake number, dropped at the end, so the step fails while the enqueue succeeds), the queued task lists the number on the suppression list, and a second run changes nothing; a key whose step succeeds queues nothing; a redirected post whose `Digits` is only in the query (with `attempt` added) lists the number; when the step and the enqueue both fail (the pool closed in the test) the answer is the redirect (or the spoken line) and the attempt count stops at the bound; no log line or alert holds the phone. `tests/integration/tests/voice_call_plan.rs` (TD-CALL-22) passes unchanged. Update the `calls` `CLAUDE.md`, `app/server/NOTES.md` (`app/server/CLAUDE.md` is at its 8,192-byte cap, `scripts/check_code_docs.py`) and `docs/decisions.md`.
