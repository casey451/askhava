# T646: site and server: the web chat's new-request limit counts the client IP the edge reports, not the proxy's

## Goal

Plan change D-4292 (spot review, verified on `main` 67827d85): `site::chat::post` takes the IP for intake's new-request limit from the socket peer (`ConnectInfo<SocketAddr>`, `app/site/src/chat.rs:296`), but `intake::limits::Key::Ip` is documented as the client IP `core::api::ClientIpPolicy::client_ip` reads (SEC-040, `app/intake/src/limits.rs:109`), and every other server route uses `portals::api::security_event_client`. Behind the host's edge every peer is the edge, so after `REQUESTS_PER_IP` (10) verified web-chat requests in an hour from all visitors together every new web chat is refused, and one abusive client is never told apart. (1) In `app/server/src/chat_codes.rs`, the layer that already reads `security_event_client` for its refusals puts that IP in the request's extensions as a `site` type (as it does `ChatCsrf`), and `site::chat::post` reads it in place of `ConnectInfo`; with no such extension (a test router built without the layer) the limit gets no IP, as today with no connect info. `site` does not depend on `portals` (`kit/layers.json`). (2) Tests, fake data only, in `app/server/tests/web_chat_client_ip.rs` through the assembled router served with one connect-info peer, with its client-IP policy as the app sets it (process-wide: `server`'s `main` reads `ASKHAVA_CLIENT_IP_HEADER` into `portals::api::configure_security_events`, `app/server/src/main.rs:44`, and `security_event_client` falls back to the default policy when that was never called, `app/portals/src/security.rs:137`; the router holds no policy of its own), each request carrying its client in the header that setting names (the default `x-real-ip`, `app/core/src/rate_limit.rs:44`): every case of TD-SEC-74. Update `docs/architecture.md`, `app/site/CLAUDE.md`, `app/server/NOTES.md` and `docs/decisions.md`. Plan change D-4880: `carry` (same file) passes `post` the new extension in place of `ConnectInfo`. The layer inserts the extension only when `security_event_client` gives an address that is not unspecified (`0.0.0.0` or `::`), so requests with no peer get no IP, never one shared bucket.
