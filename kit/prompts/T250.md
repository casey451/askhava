From `docs/brains/postgres-operations.md` (cite its tags in the PR; read other sections only when a design choice needs them):

### 2. Principles (lines naming this task's requirements)
**P3. Two roles; the app role never owns anything.** Roles are created outside migrations by the host or a bootstrap script (D-481). The migration role owns every schema and table; the app role (`askhava_app`) used by `web` and `worker` gets only `USAGE` and table privileges. Why: "The right to modify or destroy an object is inherent in being the object's owner, and cannot be granted or revoked in itself" (PostgreSQL privileges docs), so an app role that owned a table could always rewrite it. Serves D-092, threat T6, SEC-029.
**P5. Append-only is a missing privilege, tested as the app role.** Append-only tables (`ops.audit_log`, `payments.ledger_entry`, `payments.charge_evidence`, the consent and opt-out event tables) get `SELECT, INSERT` only. `TRUNCATE` is its own privilege, separate from `DELETE` (docs), so never grant it to the app role. Default privileges granted `UPDATE, DELETE` broadly until T245 (`payments`, D-1495) and T250 (every other schema, D-1520) narrowed every schema's default to `SELECT, INSERT`; from then a table that needs `UPDATE` or `DELETE` gets an explicit `GRANT` in its own migration, and an append-only table still gets its explicit `REVOKE UPDATE, DELETE` right after `CREATE TABLE` [inferred from P4]. Tests `SET ROLE askhava_app` and expect the `UPDATE` to fail (D-481). The off-database audit stream is the second copy (OPS-010, OPS-011). Serves D-092, OPS-010, FEE-029.
**P6. Lock down `public`.** PostgreSQL 15 removed `PUBLIC` create permission on the `public` schema for new databases, but "Upgrading a cluster or restoring a database dump will preserve `public`'s existing permissions" (PG 15 release notes). A bootstrap or first migration should `REVOKE CREATE ON SCHEMA public FROM PUBLIC` anyway; it is idempotent. Serves SEC-029 (one schema per module, D-091).
