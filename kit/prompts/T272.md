# T272: portals: the sign-in link cap and the code-try cap are atomic admissions, so concurrent requests cannot pass them

Task T272 (build, phase 1, stage 4). Slug: signin-admission.
Branch: `claude/task/T272-signin-admission`
Model: `claude-opus-5-5`, effort high. Reviewer: `claude-opus-5-5` (areas: security).

## Goal

D-1725 allows at most 5 sign-in links per member in 15 minutes and D-1777 at most 5 failed code checks per link, but both are check-then-act: `send_one` counts links (`models::links_since`, `app/portals/src/models.rs`) and then inserts and sends, and `check_once` counts `auth_failed` events, calls Verify and records the failure afterwards (`app/portals/src/business_auth.rs:444`, `:652`), so simultaneous requests that all see 4 all go through (second external audit B01, D-1837). (1) Links: the count and the insert of the new `portals.login_link` row happen in one short transaction under a per-member transaction-scoped lock (`pg_advisory_xact_lock` on the member's ID under a `portals` key namespace), committed before the email is sent; no transaction is held across the mail call. (2) Code tries: `migrations/0167_portals_code_tries.sql` adds `portals.code_try` (link ID, try number 1 to 5 unique per link, reserved time, outcome `pending`, `right`, `wrong` or `abandoned`; app role SELECT, INSERT and UPDATE of the outcome only); a check first reserves the next try number in its own short transaction (the unique key and the check constraint refuse a sixth), then calls Verify with no transaction open, then records the outcome; a reservation left `pending` (a crash or a Verify timeout) counts as a used try, so a restart never gives a try back; the fifth used try uses the link up and shows the "stopped working" screen as today; a right code consumes the link once (the existing guarded `UPDATE`), and a concurrent right code and wrong code never both sign in. Each wrong or failed check still writes its `auth_failed` security event (SEC-048). T089's per-IP and per-business limits sit in front of these and never re-count links or tries (D-1837). Tests in `tests/security/tests/signin_admission.rs` with 20 simultaneous requests over several pooled connections. Update the `portals` `CLAUDE.md`, `docs/architecture.md` section 10 and `docs/decisions.md`. Pentest PT-04 and PT-03's business half (D-2349): `send_once` (`app/portals/src/business_auth.rs:630`) holds a transaction across `codes.verify.send`, and `check_once` (:664) never requires that a code was sent for its link. This sets aside only D-1776's held transaction. (3) The same migration adds `portals.code_send` (link ID primary key, reserved at, outcome `pending`, `sent` or `failed`); a press reserves the link's one send in a short committed transaction (a new row, or a `failed` one, or a `pending` one older than the adapter's 15-second timeout plus a minute, which a crash left), calls Verify with no transaction open, then records `sent` or `failed`, so a failed send can be pressed again and two presses at once send once; it replaces the `code-sent:<link>` marker row. (4) `check_once` refuses a link whose send is not `sent` before any try is reserved or Verify is called. Tests in `signin_admission.rs` (TD-SEC-38): a failed send can be retried; 20 simultaneous presses send once; a check with no sent code reaches Verify zero times; with a fake Verify that hangs, no transaction is open during the wait. (5) No pooled connection is held across a Verify call either (PT-04's availability side, D-2349): `device_step`, `send_once` and `check_once` take the handler's `&PgPool` (`state.pool`, already in this file) in place of `&mut PgConnection` and acquire a connection only for each short database step, releasing it before the send or the check; with a fake Verify that hangs, 30 concurrent presses and checks leave a pool of 5 connections able to serve another request (the matrix's AVAIL-01, TD-SEC-38). Nov 10 code review batch 2, portals F4 (D-2635; D-1725): `links_since` (`app/portals/src/models.rs:62`) counts every `portals.login_link` row of the last 15 minutes, including the row `remember_device` (`business_auth.rs`) inserts on a new-device sign-in with `created_at` now, so a member who signs in on a new device loses one of the 5 links; the count (which this task rewrites) leaves out remembered-device rows. TD-SEC-38 gains the case: a new-device sign-in, then 5 link requests, all 5 send.

Acceptance: TD-SEC-38 passes against PostgreSQL; every T084, T194, T253 and T269 sign-in case still passes unchanged.
