## Goal

Plan change D-4293 (split from T109; OPS-013, OPS-051, D-232, D-492): `recovery`'s monthly test restore, in the new `app/recovery/src/restore.rs` (declared in the shared `lib.rs` and exported through the shared `api.rs`). Each run takes a fresh `pg_dump -Fc` stream through T109's `ASKHAVA_BACKUP_DATABASE_URL` and T109's path helper (before any encryption), and restores it on a separate throwaway PostgreSQL 16 service, never the live database: it connects through a new `ASKHAVA_RESTORE_ADMIN_URL` (that service's admin role; a `SecretString`, never logged; it joins `KEYS` in the shared `app/core/src/settings.rs`; a missing key fails the run closed in dev and stops start-up in test and live), creates its own database there under a name it makes, runs `scripts/bootstrap_roles.sql` first (embedded with `include_str!`, since the runtime image holds no `scripts/`, `Dockerfile` runtime stage; with no role passwords set, so every role stays `NOLOGIN`), then `pg_restore --single-transaction`, then the ownership and append-only grant check (every restored object owned by `askhava_migrator`; `askhava_app` holding no `UPDATE` or `DELETE` on an append-only table), and drops the database whatever happened. It then checks the latest nightly export from its record, not its object: the newest `recovery.backup_check` row of kind `export` (T109's migration 0198: `ok`, `object_bytes`, `object_sha256`) is `ok`, finished within the last 26 hours, and has its size and hash recorded; a missing, failed, stale or incomplete row fails the check (D-4835: PRIV-029 keeps the export prefix's storage key write-only, `app/adapters/src/storage.rs:39` to `:44`, so the object cannot be read back, and an x25519 `age` header does not name its recipient; no private key on the host, PRIV-024). Each result is one `recovery.backup_check` row of kind restore (T109's migration 0198) and one `ops::api::audit` entry, which T524's digest reads through `ops::api::latest_audit`; a failed restore raises one High alert (`ops::api::raise_alert`) that starts no safe mode, even unacknowledged for 48 hours (TD-OPS-22). The handler registers in `worker_registry` (the shared `app/server/src/lib.rs`; `tests/integration/tests/task_registry.rs`), and the first run is queued by one line in `schedule_start` (the shared `app/server/src/bin/worker.rs`) under a dedupe key, each run queuing the next a month on, through this task's own monthly scheduler in `restore.rs` with its own dedupe key; the first run is queued for after the next nightly export (its due time later than that export's), so a fresh environment never raises the High alert before any export row exists (T109's `schedule_export`, `app/recovery/src/backup.rs:315`, is fixed to the export kind and is not reused). `tests/recovery/tests/export_restores.rs` (TD-OPS-26): CI's one PostgreSQL already has the roles (`.github/workflows/ci.yml:80` to `:86`), so the test makes a throwaway cluster with PostgreSQL 16's own `initdb` and `pg_ctl` (found by name on `PATH` through T109's path helper, which accepts only a binary whose `--version` major is 16; on `Ci` T724's preflight puts `/usr/lib/postgresql/16/bin` on `PATH` of the `ubuntu-24.04` jobs, D-4708; the test names no PostgreSQL directory itself) in a temporary folder on a free local port (`initdb` refuses root: the test runs it and `pg_ctl` as an unprivileged user, e.g. through `runuser` to a user it creates when it is root), points `ASKHAVA_RESTORE_ADMIN_URL` at it, restores without and then with `scripts/bootstrap_roles.sql` (without: fails and leaves no object), plants an object owned by another role and an `UPDATE` grant to the app role on an append-only table (each fails the check), checks a job number texted out is never reused after the restore (TD-JOB-06), and stops and removes the cluster; missing binaries fail the test with a message, never a skip. ## Output discipline

Every turn re-reads earlier tool output; large results cost tokens on every later turn (D-3305). Never omit failure lines to save tokens.

1. For a file over 200 lines (`wc -l`), never `cat` or `Read` it whole. Use `grep -n` with at most `-C` 3, then `sed -n 'A,Bp'` or Read with offset/limit: at most 120 lines, or 250 if one read replaces two. Don't re-read unchanged files or regions; use earlier output.
2. Log build, test and lint output; print only decisive lines. Example: `cargo test -p <crate> >/tmp/t.log 2>&1; echo exit=$?; grep -nE 'FAILED|panicked|^error|test result' /tmp/t.log | head -n 60; tail -n 15 /tmp/t.log`. Grep each tool's failure markers: cargo/clippy `^error|FAILED|panicked`, pytest `FAILED|ERROR`, tsc `error TS`, npm `ERR!`, playwright `✘|failed`. If needed, read further log line ranges, including failures cut by `head`.
3. Prehand-in: `bash scripts/prehandin.sh >/tmp/p.log 2>&1; echo exit=$?; tail -n 40 /tmp/p.log` (smoke per Start step 2). Then, in its own Bash call with timeout 600000 ms, Ally: `bash scripts/prehandin.sh --ally >/tmp/a.log 2>&1; echo exit=$?; tail -n 30 /tmp/a.log`; no changed page path prints `not needed` immediately, otherwise only failed tests (D-3837).
4. Batch foreseeable reads, greps and `wc -l` into one turn, via parallel calls or one Bash call with `;` (D-3530).
5. Run `git diff --stat` before a full diff; diff only needed files.
6. Limit each output to 4,000 characters (D-3444). Read additional log ranges for failures. No running commentary; report once at end.
7. Exception: `git commit` must be plain, alone in its Bash call: never `-q`, redirect or pipe. Its Git `[<branch> <abbrev>]` transcript line is required by `--after` for every commit (D-3728, D-4796).
