# T354: privacy: key rotation re-seals stored photos too, so dropping the old vault key never makes a photo unreadable

Task T354 (build, phase 1, stage 4). Slug: photo-reseal-on-rotation.

## Goal

Nov 10 code review, privacy F2 (D-2626; PRIV-023, PRIV-024): `rotate_batch` (`app/privacy/src/vault.rs:668`) moves `privacy.contact` and `privacy.stated_name` to the newest key, but no code re-seals `privacy.photo` (only the INSERT at `app/privacy/src/photos.rs:358`; the app role has no UPDATE on it), and `PhotoSeal::open` needs the row's `key_version` in its key map. The documented drill (`app/privacy/CLAUDE.md`: run `rotate_batch` until it returns 0, then drop `1:`) therefore makes every photo sealed under v1 fail with `PhotoError::Sealed` (not even `LinkDead`) for the rest of its life (job close plus 30 days, longer under a dispute hold), or forces the old key to stay live, which defeats a rotation after a key leak. Fix: `rotate_photos(db, seal, storage, limit)` in `photos.rs` re-seals, in bounded batches, each photo whose `key_version` is below the active one: it reads the object, opens it under its version and AAD, seals it under the active version and AAD, writes it as a new object, then moves the row to the new object and version in one statement that matches the row only while it still holds the old `key_version` and `storage_key` it read (a row moved meanwhile is left alone and its new object becomes an orphan for the sweep) and deletes the old object only after that commits (a crash at any step leaves a readable photo and at most one orphan, which the orphan sweep removes, D-1793); `migrations/0180_privacy_photo_reseal.sql` grants the app role UPDATE on exactly those columns of `privacy.photo`. The drill in the crate doc becomes: run `rotate_batch` and `rotate_photos` until both return 0, then drop the old key. No plaintext is logged or kept; open audits are not written for a re-seal (it returns nothing to a reader). Tests in `tests/integration/tests/photo_key_rotation.rs` (TD-PRIV-24), each failing on today's `main` where noted: a photo stored under v1, then the drill with `2:K2,1:K1`, then `VAULT_KEY=2:K2` alone: `open_link` still returns the same bytes (fails today); a run over no old photos returns 0; a re-seal interrupted after the new object is written leaves the photo readable under the old row; the row's version and the AAD bind the new object. `the_rotation_drill_moves_every_row_to_v2` passes unchanged. Update the `privacy` `CLAUDE.md`, the key-rotation runbook line it cites, and `docs/decisions.md`.
