## Goal

The Confirm route (T261) needs an `IntentStripe` outside tests: today only `tests/integration/tests/confirm_and_pay.rs` implements it, the adapter has no confirm call and the Stripe stand-in charges at creation (D-1424, D-1480 (a), D-1740 (1); external audit A08, D-1754). (1) `stand_ins/stripe.py` and its route table in `stand_ins/server.py`: `POST /v1/payment_intents` with `confirm=false` makes an unconfirmed intent (status `requires_payment_method`, a `client_secret`); `POST /v1/payment_intents/{id}/confirm` with a `payment_method` and an idempotency key succeeds, declines on the published decline test card numbers, or answers `requires_action` with a `client_secret` for the published 3-D Secure test card, which a stand-in-only `POST /v1/payment_intents/{id}/stand_in_authenticate` (pass or fail) then settles, emitting the matching signed event; the same key answers the same result. (2) `app/adapters/src/payments.rs`: `create_unconfirmed_intent` and `confirm_payment_intent` HTTP calls on `StripeHttp`, typed answers, the client secret held as a `SecretString`. (3) `app/payments/src/intent_http.rs`: `impl IntentStripe for StripeHttp`. Contract cases in `tests/contract/test_stripe_confirm.py`. The live and sandbox shapes stay T132's to check against Stripe test mode.

Acceptance: TD-FEE-44 passes (`python3 -m pytest tests/contract/test_stripe_confirm.py` and the adapter's Rust tests); `tests/contract/test_stripe_contract.py` passes unchanged.
