# T373: businesses: changing a phone's number ends that phone's texting consent until the box is ticked again for the new number

## Goal

Nov 11 code review batch 3, F2 (D-2707; CON-019, BIZ-036, D-191): business texting consent is per number, but `change_phone` (`app/businesses/src/team.rs:503`) keeps the line's ID and `may_text` (`app/businesses/src/consent.rs:243`) looks consent up by line ID only, so after a number change job-card texts go to a number nobody consented for (the reviewer's probe: `may_text` true after `change_phone`); and the consent index (`migrations/0121_businesses_consent.sql`, one row per business, member, channel, line and wording version) would refuse a second box for the same line, so the new number could not consent either. Fix: the line keeps its ID (done tests link, change and unlink by it), and `migrations/0199_businesses_consent_per_number.sql` records which number setting a consent row was given for (a per-line number version, raised by `change_phone` in its transaction, and the same version on each text consent row, the unique index including it; existing rows keep version 1; the app role still cannot update or delete consent rows); `may_text` counts only a box ticked for the line's current version; `record_consent` gains a form that takes the phone version the box was shown for and refuses a mismatch (the number changed while the page was open), while the existing form, used by done tests, records against the current version; `change_phone` and `record_consent` both lock the `staff_phone` row (`FOR UPDATE`) before reading or raising the version; after a number change a business whose channel preference is text only gets its job cards and notices by email until the new number consents (BIZ-036's email default); nothing else about consent changes, and the old rows stay as history. Tests in `tests/integration/tests/phone_change_consent.rs` (TD-CON-35), each failing on today's `main`, fake numbers in the 555-01xx block: a consented line gives `may_text` true; after `change_phone` false; after `record_consent` for the new number true again; a box shown for the old version and posted after the change is refused; `change_phone` and `record_consent` racing on one line leave either the old consent ended or the new one recorded for the new version, never a consent for the old number counted on the new one; a text-only business's job card after the change goes by email; a change by a member without the right is refused and leaves consent as it was; the email channel is untouched. Every TD-BIZ and TD-CON case passes unchanged. Stage 5: it runs after T361 only so its migration number follows the serial order (V9, R-42). Update the `businesses` `CLAUDE.md`, `docs/architecture.md` (schema) and `docs/decisions.md`.
