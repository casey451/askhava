## Goal

Plan change D-4098 (Casey's outside code audit, finding F-03, verified on `main` 78bc4c55 on Nov 17, 2026 and re-checked before planning): every anonymous `GET /` (and the old `/categories` and `/events` paths, which answer with the home page, WEB-012) reads WEB-028's numbers through `intake::api::home_numbers` and `quotes::api::home_numbers` (`app/quotes/src/home_numbers.rs:42`), which loads every job that ever had a card sent and, once 50 have (`ASKHAVA_HOME_NUMBERS_MIN_JOBS`), runs one `jobs::api::job_facts` query per job to count the trades (`:63` to `:69`): 1 + N statements, N growing with every job. `home_html` (`app/site/src/pages.rs:173` to `:181`) also takes one pooled connection for the banner and then another for the numbers. Site pages have no rate limit and the pool holds 10 connections per process (`ASKHAVA_DB_POOL_MAX`). (1) `jobs`: a new `categories_of(conn, &[Uuid]) -> Result<BTreeSet<String>, FactsError>` in `app/jobs/src/job_facts.rs`, re-exported by one line in the shared `app/jobs/src/api.rs`: one statement reading each listed job's latest facts row (`SELECT DISTINCT ON (job_id) category FROM jobs.job_facts WHERE job_id = ANY($1) ORDER BY job_id, seq DESC`); a job with no row adds nothing, as `job_facts`' `None` does today. (2) `quotes`: `home_numbers` calls it once in place of the loop, so it makes 2 statements however many jobs exist (1 below the threshold, as today); `HomeNumbers`, its rounding and its errors are unchanged. (3) `site`: the shown numbers (public aggregates only, no business or homeowner detail) are kept for 60 seconds, a named constant whose comment gives the reason (it is not a spec value, so not a setting), in a cache held in the page router's state, never a process-wide static, so routers built for separate tests or pools never share figures. Within the window a `GET /` makes no numbers statement; a `None` (below the threshold) is kept like a value; a failed read is not kept (the page shows no numbers, as today, and the next request reads again). The cache holds the numbers only, never rendered HTML, since a page may carry a per-visitor token. `home_html` keeps its signature and reads uncached, so T102's `tests/integration/tests/home_numbers.rs` passes unchanged; the served route goes through the cache. A request reads the banner and, on a miss, the numbers on one pooled connection (one acquire, not two): `app/site/src/routes.rs` gains a connection form of `banner_shown` with the same fail-closed rule (R5; F-04 stays as decided: WEB-007's banner announces a texting outage, not a database one). WEB-028 holds unchanged: no hand-typed number, nothing below the threshold. Tests in the new `tests/integration/tests/home_numbers_queries.rs`, fake data only, on PostgreSQL: (a) `categories_of` returns each job's latest category when a job has several facts rows (the highest `seq` wins), skips a job with none and answers an empty set for an empty list; (b) for 60 fake jobs across 3 trades with mixed confirmed and unconfirmed quotes, `home_numbers` equals the figures the test computes the old way (one `job_facts` read per job for the trade count); (c) with the threshold at 1, `home_numbers` makes exactly 2 statements for 1 job and for 2,000 jobs, counted with T416's `DbMetrics` statement counter installed as `tests/integration/tests/db_metrics.rs` installs it (`app_pool`, `log_subscriber`); (d) through the page router, a cold `GET /` makes at most 3 statements and a second `GET /` inside the window only the banner's, and after the window (shortened through the cache's constructor in the test) the numbers are read again.

Acceptance: `tests/integration/tests/home_numbers_queries.rs` passes against PostgreSQL with every listed case, the 2,000-job statement count and the warm-page case failing on `main` before the change; T102's `tests/integration/tests/home_numbers.rs` (TD-JOB-04's WEB-028 cases), `tests/integration/tests/job_facts.rs` and `tests/e2e/site_pages.spec.ts` pass unchanged.
