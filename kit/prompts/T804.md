## Goal

Plan change D-5281 (Fable's decision for Casey under D-305; PRIV-031 as reworded; SEC-014, SEC-034), as narrowed by D-5332 and D-5339 (outside review job 10 and its round 1, Fable deciding for Casey). On the signed-in portal data-request route (`data_request` in `app/server/src/homeowner_portal.rs`), when her number is on the suppression list, the request is confirmed by a single-use link (15 minutes) emailed to her confirmed update address (T729's, `confirmed_at` set) through T816's `messaging::api::queue_data_request_link`, and no Verify code is sent; when that answers `NoConfirmedAddress` (none, or unconfirmed), the answer tells her to email help@ from her own address, which opens a help request for Casey (OPS-036). The help form is not changed (D-5339: its answer must not show whether a number is listed or has an address, TD-SEC-51, TD-PRIV-16, D-4293). The link is issued only after the same send limits the code path runs (`admit_code_send`, as `admitted_send` does); a second request of the same kind while her earlier link is live (unused, within 15 minutes) answers as sent and queues nothing new (T816 keys the email on the request, D-5340). Tokens: SEC-037's `core::api::link_token` with `LinkKind::Action` over the request's subject UUID (`request_subject`) and a `LinkSalt` stored with it. There is no data-request table (a request's ID is its received audit row's, `DataRequest.id` in `app/portals/src/data_download.rs`) and `portals.code_challenge` holds no salt, so this task owns the new `migrations/0217_portals_data_request_link.sql` (after T812's `0216` in the runner's serial order, D-5341; if a merged migration already uses `0217` at claim time, report a plan gap): `portals.data_request_link` (`request_id bigint PRIMARY KEY`, the audit row's ID with no foreign key, as no key crosses schemas; `salt bytea NOT NULL CHECK (octet_length(salt) = 16)`; `sent_at timestamptz NOT NULL`; `used_at timestamptz`; IDs and times only) with `migrations/0176_portals_code_challenge.sql`'s grants: UPDATE, DELETE and TRUNCATE revoked from `askhava_app`, then SELECT and INSERT, and UPDATE on `used_at` alone. This task owns `app/portals/src/data_download.rs` (its owners are DONE): `act`'s body after the challenge (the confirmed audit row through `audit_once`, then for a delete `delete_her_data`) becomes one shared function the code path and the link path both call, so a link and a code together act once; a link-path sibling of `open_request` writes the received row and sends no Verify; every existing public function keeps its signature and behaviour, and no action string or subject kind is repeated elsewhere. The new `app/portals/src/data_request_link.rs` (exported through the shared `api.rs`) issues the link (stores the salt, builds the token) and confirms it: in one transaction it sets `used_at` with one guarded UPDATE (unused, `sent_at` within 15 minutes) and calls the shared act. The link is `/help/my-data/{object}/{token}` (`{object}` the request's subject UUID), under the help prefix so a person not signed in can use it (the public door of `tests/security/tests/auth_matrix.rs` and `app/server/tests/door_matrix.rs`, which are not edited); both path parts are taken as strings and parsed (`LinkToken::parse`), the token recomputed from the stored salt and compared in constant time. Opening it (`GET`) only shows a `no_store` confirm page and uses nothing up (SEC-026, TD-SEC-61); an unknown, malformed, used or expired link's `GET` answers 200 with one generic page ("This link has expired or was already used." and the homeowner sign-in link), as the door matrix's public probe expects every public `GET` to (`app/server/tests/door_matrix.rs`, `Door::Public`); the page's `POST` carries the CSRF token (SEC-009, SEC-042, the pre-session CSRF cookie the site help form uses; a cross-site or wrong-token `POST` is refused, a valid one with a bad link answers under 500 and is never a CSRF refusal) and acts on the request as a typed code does and uses the link up: a copy records the confirmation and answers "Your copy is ready. Sign in to download it." with the homeowner sign-in link and no data (D-5340: the link only proves the inbox, so her file is served only to her session, by `GET /h/my-data`), a delete the PRIV-011 sentence; a repeat `POST` of the link it used, within its 15 minutes, answers the same result and acts nothing again (SEC-026). Both routes are served from the owned `server::homeowner_portal` router, each with its `docs/architecture.md` section 13 row (added as `T804`, marked `yes` in the pull request); the page is the new `app/portals/templates/data_request_link.html`; the `GET` gets one `PAGE_ENTRIES` entry (its states join `PAGE_STATES`) in the shared `tests/a11y/page_states.ts` with two states, the confirm page and the generic page, its seed storing a request and its link with fake data and computing the token in TypeScript from `keyedIdSecret()` (`tests/e2e/keyed.ts`), not from `tokenSeed`. Tests in the new `tests/integration/tests/data_request_opted_out.rs`, PostgreSQL, fake data only (TD-PRIV-32): a listed number with a confirmed update address gets the email link and no Verify send; an unconfirmed address gets no link and the help-email answer; opening the link changes nothing; its `POST` acts once and uses it up; the link's `POST` for a copy returns no data; a repeat `POST` answers the same result; a used, expired, unknown or malformed link's `GET` shows the generic page and acts nothing; a cross-site `POST` is refused; no confirmed address gets the help-email answer; an unlisted number is unchanged; the help form's answer is unchanged.
