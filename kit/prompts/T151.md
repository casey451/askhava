# T151: ops and messaging: HELP requests with one owner notification each and the plain-word auto-answers

## Goal

Each HELP request produces one owner notification by alert email within the hourly and daily limits, its body scrubbed of contact details, inbound help emails arrive only through the signed webhook into `privacy`, and plain-word questions after HELP get the fixed auto-answers (CON-034, OPS-036, PRIV-026, PRIV-030). The `ops.help_request` and `ops.help_message` tables of architecture section 3 are created by this task's migration in the `ops` schema and written only through `app/ops/src/help_requests.rs` and `ops::api`; the owner's reply box and its link are T200's (TD-OPS-23); the HELP lines with their due dates are added to the digest's `digest_flags.rs` (T204's, extended here) (D-491). `messaging` cannot read `jobs`, `quotes` or `intake`, so `intake`'s inbound handler (`app/intake/src/handlers.rs`, T048's, extended here) puts the job fields the help texts and notification need (status, the LIST line from `quotes::api`, the quote-page link, trade, town, urgency) into the HELP event, and `messaging` composes from the event only. A business's "Ask about a charge" (T148) arrives as the `core.task` event `help_request_opened`, which this task's handler turns into one help request (D-492). It also corrects the module doc of `app/intake/src/handlers.rs` (lines 13 to 20), which says `answer_list` has no caller although T241's `receive_reply` calls it, and names `queue_call_back`'s callers as they now stand (fourth external audit F17, D-2206). Plan change D-3155: (a) no file this task owned saw a HELP text: `app/server/src/inbound_text.rs` answers HELP with `messaging::api::reply_to_help` and then halts (`Halt::Ends("help")`, `:492` to `:501`) before intake, and plain follow-ups reach `intake::api::receive_reply` (`app/intake/src/replies.rs:43` to `:66`), never `handlers.rs`. So it also owns those two files (after T241, T277, T336, T357, T391 and T435, before T402 and T407): after `reply_to_help` answers, `inbound_text.rs` calls one new `intake::api` function in `handlers.rs` that gathers the job fields and opens or joins the help request (`ops::api`, notification by `messaging`, as above); a business text ("why was I charged?") takes the same call; and `receive_reply` first asks a new `handlers.rs` function whether the number's HELP was answered in the last 24 hours and, for a plain-word question (TD-CON-17), sends the fixed auto-answer and returns, the rest following today's path. (b) The opt-out half of TD-CON-17 (help email, quote-email reply, help-form "no more texts", owner-recorded request) is tested at `messaging::api::suppress` with `RevokeChannel::Email`, `EmailReply`, `HelpForm` and `Owner`: listed at once, channel and time logged, no text queued; the help form's detector and on-screen confirmation are T200's, the owner's record T108's, and the inbound-email route T133's (stage 6), which hands each email `privacy` has read to this task's entry point; until then the email cases (TD-OPS-11's automatic reply, TD-PRIV-11's sentinel body) run on `privacy::api::read_inbound_email`'s output, not over HTTP. (c) TD-OPS-20's notification half is this task's; its docs half (the Gate C checklist) is T122's. (d) The migration is `0192_help_requests.sql` (T321 needs two numbers before T109's 0195; moved up one by D-3262 and one more by D-3263).
