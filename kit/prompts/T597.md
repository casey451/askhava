## Goal

Plan change D-4180, choice (5) (merge-line lag; evidence in D-4180): when a task merges, the next turn holder of the D-3418 merge line gets its update merge only inside some lane's session cycle, after the cache, warm-up and smoke steps; the early `--resolve-merges` step (D-3141; `.github/workflows/backup-runner.yml` "Close merged tasks before the smoke (D-3141)", `runner/cycle.py` `resolve_merged`) marks the merged task DONE but pushes no update. Measured on November 17: T572 merged 14:16:07Z, the early step marked it DONE at 14:23:05Z, and a lane's cycle pushed T202's update merge only at 14:29:16Z; the median lag from `main` moving to the next update merge was 7 minutes (0 to 18). Make the early step push that update as soon as it closes the merge (T572: about 14:23Z instead of 14:29:16Z; the early close itself may lag the merge). (1) `cycle.resolve_merged`: when it closed at least one merged task (it would return `MERGES_RESOLVED`), it then runs the cycle's own merge-line pass, `_resolve_merges(state, env, cfg, now)`, on the resolved state, and pushes the one resulting state with a single `push_state` against the state it read. The pass acts only on MERGE_PENDING tasks whose `_current_pr` is open (not merged); a task with a merged pull request or none (a cleanup task waiting for its stage proof, a merged head git cannot place yet, an absent PR or an empty hand-in) is left to the cycle exactly as D-3141 says (`resolve_merged`'s skips, `docs/architecture.md:506`), for example through a filter on the tasks `_resolve_merges` takes (such tasks never hold the turn). So the turn and its order are exactly the cycle's: `_merge_line` (FIX-MAIN first, then hand-in order, then task id), `_line_place`, `_mark_turn`, the late tasks taken last, the red-`main` guard (only FIX-MAIN moves while `main` is red), and every open-PR rule of `_open_pr_step` and `_update_step` (the update merge is `env.update_branch`, built by `_built_update` and pushed only after `UpdateMerge.is_update_merge` proves it is exactly the reviewed head plus `main`, union-aware, a fast-forward never forced, refused as "moved" when the branch tip is not the reviewed head; a conflict goes to a resync, D-891; push failures and waits count as today; auto-merge already on stays on, but the early pass never turns it on, see (2)). Each outcome goes through `_lane_outcome` as in the cycle. Nothing else changes (apart from the merged-or-absent tasks above, left as read, and auto-merge, left to the session's cycle): with nothing merged to close it still returns `NO_MERGED` and writes nothing, touches no update merge, inbox, smoke or claim; a lost race still changes nothing in the state (an update merge already pushed is then adopted by the cycle's existing `update_merge_of` path as "adopted", D-584/D-620); the result string stays `MERGES_RESOLVED` so `runner/__main__.py`'s early-row and refill logic (D-3141) is unchanged. No lease is taken or needed: `_update_step` checks no lease today (verified, `runner/cycle.py:846`), any lane's cycle updates any task's branch, and auto-pr's lane-lease rule (`verify.auto_merge_reason`) is unchanged. Keep `resolve_merged` and each helper under 50 lines (split as needed). (2) Workflow: the step's comment ("Nothing else: open pull requests ... stay the session's") now says it also pushes the merge line's next update merge (D-4180). Confirm, at that point of the job, that `RUNNER_PUSH_TOKEN` (already in the step's env), git's identity and fetch of `main` and the task branch are what `GitHubEnv.update_branch` needs (the cycle's later steps run it today) and add only what is missing; keep `continue-on-error: true` (a failure leaves the update to the session's cycle, as before) and keep `timeout-minutes: 5` unless the report shows an update merge needs longer. `enable_auto_merge` runs `gh pr merge --auto` first with `RUNNER_PUSH_TOKEN` (D-519); if that is refused, `run_command` retries with `GH_TOKEN`, which in this step is `github.token`, not the Claude App's token the session has (D-502). A merge whose auto-merge the job token turned on starts no workflow (D-500, `BUILD_BRIEF.md:265`, D-505). So the early pass never turns auto-merge on: where the cycle would call `_auto_merge`, it leaves `auto_merge` as read for the session's cycle. (3) Tests in `tests/test_runner_merge_early.py`: after a merge, the early step pushes the update merge of the new turn holder (the first in hand-in order), and only of it, with exactly one state push; FIX-MAIN pending takes the turn first; while `main` is red no update merge is pushed for any other task; a turn holder whose branch is already current pushes nothing and leaves auto-merge, and turning it on, to the session's cycle; a pushed update merge on a PR without auto-merge calls no `_auto_merge`; with one merge closed, a merged cleanup task without its proof and a merged head git cannot place stay exactly as read, while the open turn holder's update is pushed; a conflict sends the turn holder to a resync exactly as the cycle does; a lost race leaves the state as read and the cycle then adopts the pushed update merge; nothing merged still writes nothing and pushes no update. The one pinned assertion that changes is `tests/test_runner_merge_early.py:135` (`assert not env.updates  # the open one's update merge stays the cycle's`): it becomes `env.updates == [(T002's branch, T002's reviewed head)]`, because the open T002 is now the turn holder and gets the cycle's own update merge earlier; this is not a weakening, as the update obeys every rule the cycle's does and the assertion stays exact. `:56` (one merged task, nothing else pending: `not env.updates`) and `:101` (nothing merged) stay unchanged. `tests/test_runner_merge_line.py` (no task owns it) passes unchanged. Update `docs/architecture.md`'s merge-line or early-close text with D-4180. ## Output discipline

Every turn re-reads earlier tool output; large results cost tokens on every later turn (D-3305). Never omit failure lines to save tokens.

1. For a file over 200 lines (`wc -l`), never `cat` or `Read` it whole. Use `grep -n` with at most `-C` 3, then `sed -n 'A,Bp'` or Read with offset/limit: at most 120 lines, or 250 if one read replaces two. Don't re-read unchanged files or regions; use earlier output.
2. Log build, test and lint output; print only decisive lines. Example: `cargo test -p <crate> >/tmp/t.log 2>&1; echo exit=$?; grep -nE 'FAILED|panicked|^error|test result' /tmp/t.log | head -n 60; tail -n 15 /tmp/t.log`. Grep each tool's failure markers: cargo/clippy `^error|FAILED|panicked`, pytest `FAILED|ERROR`, tsc `error TS`, npm `ERR!`, playwright `✘|failed`. If needed, read further log line ranges, including failures cut by `head`.
3. Prehand-in: `bash scripts/prehandin.sh >/tmp/p.log 2>&1; echo exit=$?; tail -n 40 /tmp/p.log` (smoke per Start step 2). Then, in its own Bash call with timeout 600000 ms, Ally: `bash scripts/prehandin.sh --ally >/tmp/a.log 2>&1; echo exit=$?; tail -n 30 /tmp/a.log`; no changed page path prints `not needed` immediately, otherwise only failed tests (D-3837).
4. Batch foreseeable reads, greps and `wc -l` into one turn, via parallel calls or one Bash call with `;` (D-3530).
5. Run `git diff --stat` before a full diff; diff only needed files.
6. Limit each output to 4,000 characters (D-3444). Read additional log ranges for failures. No running commentary; report once at end.
7. Exception: `git commit` must be plain, alone in its Bash call: never `-q`, redirect or pipe. Its Git `[<branch> <abbrev>]` transcript line is required by `--after` for every commit (D-3728, D-4796).
