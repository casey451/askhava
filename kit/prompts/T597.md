## Goal

Plan change D-4180, choice (5) (merge-line lag; evidence in D-4180): when a task merges, the next turn holder of the D-3418 merge line gets its update merge only inside some lane's session cycle, after the cache, warm-up and smoke steps; the early `--resolve-merges` step (D-3141; `.github/workflows/backup-runner.yml` "Close merged tasks before the smoke (D-3141)", `runner/cycle.py` `resolve_merged`) marks the merged task DONE but pushes no update. Measured on November 17: T572 merged 14:16:07Z, the early step marked it DONE at 14:23:05Z, and a lane's cycle pushed T202's update merge only at 14:29:16Z; the median lag from `main` moving to the next update merge was 7 minutes (0 to 18). Make the early step push that update as soon as it closes the merge (T572: about 14:23Z instead of 14:29:16Z; the early close itself may lag the merge). (1) `cycle.resolve_merged`: when it closed at least one merged task (it would return `MERGES_RESOLVED`), it then runs the cycle's own merge-line pass, `_resolve_merges(state, env, cfg, now)`, on the resolved state, and pushes the one resulting state with a single `push_state` against the state it read. The pass acts only on MERGE_PENDING tasks whose `_current_pr` is open (not merged); a task with a merged pull request or none (a cleanup task waiting for its stage proof, a merged head git cannot place yet, an absent PR or an empty hand-in) is left to the cycle exactly as D-3141 says (`resolve_merged`'s skips, `docs/architecture.md:506`), for example through a filter on the tasks `_resolve_merges` takes (such tasks never hold the turn). So the turn and its order are exactly the cycle's: `_merge_line` (FIX-MAIN first, then hand-in order, then task id), `_line_place`, `_mark_turn`, the late tasks taken last, the red-`main` guard (only FIX-MAIN moves while `main` is red), and every open-PR rule of `_open_pr_step` and `_update_step` (the update merge is `env.update_branch`, built by `_built_update` and pushed only after `UpdateMerge.is_update_merge` proves it is exactly the reviewed head plus `main`, union-aware, a fast-forward never forced, refused as "moved" when the branch tip is not the reviewed head; a conflict goes to a resync, D-891; push failures and waits count as today; auto-merge already on stays on, but the early pass never turns it on, see (2)). Each outcome goes through `_lane_outcome` as in the cycle. Nothing else changes (apart from the merged-or-absent tasks above, left as read, and auto-merge, left to the session's cycle): with nothing merged to close it still returns `NO_MERGED` and writes nothing, touches no update merge, inbox, smoke or claim; a lost race still changes nothing in the state (an update merge already pushed is then adopted by the cycle's existing `update_merge_of` path as "adopted", D-584/D-620); the result string stays `MERGES_RESOLVED` so `runner/__main__.py`'s early-row and refill logic (D-3141) is unchanged. Every turn re-reads all earlier tool output, so a large result is paid for again on each later turn (D-3305). Never cut a failure line to save tokens.

1. Never `cat` or `Read` all of a file over 200 lines (`wc -l`): `grep -n` (context `-C` 3 at most), then `sed -n 'A,Bp'` or Read with offset/limit, at most 120 lines per read, or up to 250 when one read then covers what would take two. Do not re-read a file, or a region of one, you already read unless it changed since: use your earlier output.
2. Build, test and lint output goes to a log, and you print only what decides: `cargo test -p <crate> >/tmp/t.log 2>&1; echo exit=$?; grep -nE 'FAILED|panicked|^error|test result' /tmp/t.log | head -n 60; tail -n 15 /tmp/t.log`. Grep each tool's own failure markers: cargo and clippy `^error|FAILED|panicked`, pytest `FAILED|ERROR`, tsc `error TS`, npm `ERR!`, playwright `✘|failed`. 3. Prehand-in: `bash scripts/prehandin.sh >/tmp/p.log 2>&1; echo exit=$?; tail -n 40 /tmp/p.log` (the smoke test as in Start step 2).
