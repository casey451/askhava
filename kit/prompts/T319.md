# T319: portals and server: security-event rows are capped per address, webhook refusals are security events, and expired sessions are swept

## Goal

Fourth external audit F14, F5 and F7 (D-2207; SEC-048, SEC-016, SEC-004): (1) `portals::security`'s refusal (`app/portals/src/security.rs:96`) takes a pool connection and writes a security-event row before any limit, so a flood of cross-site or bad-CSRF requests turns each into a database write. An in-process counter, checked before the pool is touched, writes at most N rows per (event kind, client address as SEC-040 takes it, route) per minute and only counts the rest, logged as one line per minute with the count and no address; the 403 answer is unchanged. N is a setting in the shared `app/core/src/settings.rs` whose default is `EVENTS_PER_HOUR_ALERT` (50, `app/portals/src/security.rs:59`) and which is clamped up to it (a lower value is raised to it and logged at start-up), because the burst alert counts stored rows over the last hour (`security.rs:318`), so a cap below the threshold would stop it from ever firing. Until T135 proves that the edge overwrites the client-address header, a forged header must not buy a fresh cap: the counter also keeps a per-(kind, route) ceiling of N rows per minute across all addresses, so a flood with a new forged address on each request still writes at most N rows a minute per kind and route (the burst alert fires from those). (2) The Stripe, Twilio text and Twilio voice webhook routes answer a source or signature refusal 403 with a log line and record no security event, so SEC-048's hourly alert never sees them and a rotated Stripe address list fails silently. `app/server/src/webhook_refusals.rs` is a layer the shared `app/server/src/lib.rs` puts on those three routers only: each 403 they answer records one `webhook_signature_failed` event (route and request ID, no actor) through `portals::api::record_security_event`, under the same cap; first check that those routes answer 403 for nothing else, and if one does, tell the cases apart without reading the body. (3) Expired sessions are never removed (`app/portals/src/session.rs:165` deletes only a replaced cookie's row): a daily `portals.session_sweep` task, registered in the shared `app/server/src/lib.rs` and queued once a day like the purge sweep, deletes `portals.session` rows expired more than a day earlier, in batches. (4) Sixth audit U-08 (D-2306; SEC-014, SEC-040): `core.rate_limit` rows are never deleted (`prune`, `app/core/src/rate_limit.rs:230`, has no production caller) and their bucket names hold client addresses. A daily `core.rate_limit_prune` task, registered in the shared `app/server/src/lib.rs` and seeded in `worker.rs`'s `schedule_start` under a per-day dedupe key, deletes rows whose window started more than the longest configured window plus one day ago, in batches of at most 5,000 rows each in its own short statement (`prune_batch`, added to `rate_limit.rs`); it is registered, not deferred, in T327's registry. No index is added: once pruned daily the table holds a few days of windows. Tests in `tests/security/tests/security_event_cap.rs` (TD-SEC-53) and `tests/integration/tests/session_sweep.rs` (TD-SEC-54, TD-SEC-58); every existing security-event and session test passes unchanged. Update the `portals` and `server` `CLAUDE.md` files and `docs/decisions.md`.
