# T319: portals and server: security-event rows are capped per address, and webhook refusals are security events

## Goal

Plan change D-3445 split T319 in two: this task caps security-event rows and makes webhook refusals security events; T436 adds the daily session sweep and the rate-limit prune. Fourth external audit F14 and F5 (D-2207; SEC-048, SEC-016): (1) `portals::security`'s refusal (`app/portals/src/security.rs:96`) takes a pool connection and writes a security-event row before any limit, so a flood of cross-site or bad-CSRF requests turns each into a database write. An in-process counter, checked before the pool is touched, writes at most N rows per (event kind, client address as SEC-040 takes it, route) per minute and only counts the rest, logged as one line per minute with the count and no address; the 403 answer is unchanged. N is a setting in the shared `app/core/src/settings.rs` whose default is `EVENTS_PER_HOUR_ALERT` (50, `app/portals/src/security.rs:59`) and which is clamped up to it (a lower value is raised to it and logged at start-up), because the burst alert counts stored rows over the last hour (`security.rs:318`), so a cap below the threshold would stop it from ever firing. `WebSecurity::new(pool, clock)` is called in seven files this task does not own (`feedback.rs`, `pick_flow.rs`, `checkin.rs`, `quote_page.rs`, `business_auth.rs` in `app/portals/src/`, and `tests/security/tests/link_scanners.rs`, `cookies_csrf.rs`), so its signature does not change: N reaches the counter through a process-wide setter in `security.rs` called once from the shared `app/server/src/main.rs` at start-up, the default holding when it is never called (tests) (D-3134). Until T135 proves that the edge overwrites the client-address header, a forged header must not buy a fresh cap: the counter also keeps a per-(kind, route) ceiling of N rows per minute across all addresses, so a flood with a new forged address on each request still writes at most N rows a minute per kind and route (the burst alert fires from those). (2) The Stripe, Twilio text and Twilio voice webhook routes answer a source or signature refusal 403 with a log line and record no security event, so SEC-048's hourly alert never sees them and a rotated Stripe address list fails silently. `app/server/src/webhook_refusals.rs` is a layer the shared `app/server/src/lib.rs` puts on those three routers only: each 403 they answer records one `webhook_signature_failed` event (route and request ID, no actor) through `portals::api::record_security_event`, under the same cap; first check that those routes answer 403 for nothing else, and if one does, tell the cases apart without reading the body. Tests in `tests/security/tests/security_event_cap.rs` (TD-SEC-53); every existing security-event test passes unchanged. Update the `portals` and `server` `CLAUDE.md` files and `docs/decisions.md`.
