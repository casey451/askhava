# T430: payments: a Confirm needs the current card-authorization wording accepted, and the version a Confirm needs is never below the wording's

## Goal

Brand rename prep (D-3347; FEE-007, FEE-015, D-072). A Confirm is allowed only when the business's highest accepted `payments.card_authorization.version` is at least `payments.fee_terms.authorization_version` (`service.rs` `may_confirm`, about line 363); a fee-mode switch raises that stored number by one (`rules.rs` `FeeTerms::switched`, `service.rs` `switch_fee_mode`); saving a card stores `AUTHORIZATION_VERSION` with `AUTHORIZATION_TEXT` (`insert_card`), and `accept_authorization` stores the terms' version with the text it is given. One number therefore stands for two things, the fee mode and the wording, and a version check alone misses a wording change: with the wording at version 2, a mode switch to 3 and then a wording change to 3, every business that accepted the switch already holds 3, so nobody accepts the new wording. Each acceptance row stores its `text`, so the wording is checked by its text, with no migration or schema change. (1) `pick_fee.rs` gains `pub const fn required_version(stored: i32) -> i32`, the larger of `stored` and `AUTHORIZATION_VERSION`; `fee_terms_in_force`, its `FOR SHARE` twin and `switch_fee_mode` build `FeeTerms` with it before use and before `switched`, so a mode switch always lands above every version a card save has stored (a migration raising the row cannot be numbered at T428's serial position, V9, D-3347). This keeps the mode-switch rule. (2) The wording rule: a pure function `authorized(accepted: &[(i32, &str)], required: i32, current_text: &str) -> bool` in `pick_fee.rs` is true only when the business's highest accepted version is at least `required` and at least one accepted row's text equals `current_text` byte for byte; `may_confirm` reads the business's `(version, text)` rows (one query, `payments.card_authorization`, its own rows only) and calls it with `AUTHORIZATION_TEXT`, returning `ConfirmError::NewAuthorizationNeeded` exactly where it does today plus when the current wording was never accepted. Every other path of `may_confirm` and every error stays. (3) `app/payments/src/tests/authorization_floor.rs` (unit, no database): `required_version` below, at and above `AUTHORIZATION_VERSION` returns the larger, and `i32::MAX` gives `i32::MAX` with `switched` returning none; `switched` after `required_version(stored)` is above `AUTHORIZATION_VERSION` for every stored number from 1 to it; and the sequence the plan review found, played through `authorized` with explicit texts and versions: the business accepts wording W2 at version 2 (authorized at required 2); a mode switch makes required 3 (not authorized), it accepts at 3 with W2 (authorized); the wording changes to W3 at version 3, required still 3: not authorized until a row with W3 is accepted, then authorized; a row with W3 at a version below required is not enough. Under today's constants every existing test passes unchanged, `tests/integration/tests/fee_fixed_at_pick.rs` included (its businesses accept `AUTHORIZATION_TEXT` first); if one does not, stop and report the file. Money code: branch coverage stays at or above 95% (BUILD_BRIEF.md:481). Update `app/payments/CLAUDE.md` and `docs/decisions.md`.

Acceptance: `cargo test -p askhava-payments` and `cargo test -p askhava-integration --test fee_fixed_at_pick` pass with no existing test changed; `authorization_floor.rs` holds the cases in the goal, including the wording 2, mode switch 3, wording 3 sequence, which is not authorized until the new wording's text is accepted; `may_confirm` refuses a business whose rows never hold the current `AUTHORIZATION_TEXT`; payments branch coverage stays at or above 95%; no file outside the owned list changes except `app/payments/CLAUDE.md`, `app/payments/src/tests/mod.rs`, `app/payments/src/api.rs` and `docs/decisions.md`.
