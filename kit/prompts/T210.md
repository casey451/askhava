## Goal

Plan change D-3445 split T210 in two: this task is the `payments` half (the money view's figures, the expenses table and its migration); T434 builds the portals pages (the money view page with its expense-entry `POST`, and the monthly intake report). The money view shows the 8.6% sales-tax set-aside and Casey's manual expenses beside the ledger totals, never entering the ledger (FEE-046). The manual expenses list is its own table `payments.expense` (this task's migration `0198_payments_expenses.sql`; architecture section 3 names it, D-491). A new `payments` table gets SELECT and INSERT only from the schema default (D-1495, T245): any wider privilege this task's code needs is an explicit `GRANT ... ON payments.<table> TO askhava_app` in its own migration, which T245's `tests/integration/tests/payments_grants.rs` reads and checks (TD-SEC-33). `app/payments/src/money_view.rs` computes the figures behind `payments::api` (`payments::api::money_view` (T067's) gains the `set_aside`, `expenses` and `left` lines; `payments::api::add_expense(&pool, &NewExpense, now)` stores one expense; `payments::api::money_view_csv(&pool, month)` returns the monthly CSV): the set-aside line is 8.6% (a setting) of fees collected, to the cent, until the ADOR ruling is filed; an expense entered through `add_expense` (the call T434's expense-entry `POST` makes) is stored in `payments.expense` and never becomes a ledger entry; collected, set aside, expenses and left add up; the monthly CSV rows carry those columns; the ledger lines, dispute and processing fee lines come only from the ledger as T067's `MoneyView` does (FEE-050 to FEE-052); the Stripe reconcile (FEE-030) is unchanged (D-410, D-444). Tests in `app/payments/src/tests/money_view.rs`, real PostgreSQL and fake data only (TD-FEE-29; TD-FEE-16's and TD-FEE-33's money-view cases). No portals file, page or route is this task's. Update the `payments` `CLAUDE.md` and `docs/decisions.md`.
