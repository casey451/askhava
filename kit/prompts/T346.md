## Goal

Pentest PT-03 and the PT-02 gap beyond the report (D-2348; SEC-055, SEC-008, PRIV-031). One Twilio Verify service serves every purpose and `VerifyAdapter::check_code(to, code)` (`app/adapters/src/verify.rs:50`, :86) is not bound to one, so `confirm_request` (`app/portals/src/data_download.rs:210`) acts on any of her open requests (up to 30 days old) after any passing code for her phone, the sign-in code included, and homeowner sign-in (`finish_sign_in`, `app/portals/src/homeowner_portal.rs:164`) keeps no local challenge; neither has an app-side try cap. Build: (1) `migrations/0176_portals_code_challenge.sql` adds `portals.code_challenge` (ID, purpose `homeowner_signin`, `data_copy` or `data_delete`, subject ID (her contact for sign-in, the request for copy and delete), sent at, used at, tries; app role SELECT, INSERT and UPDATE of `tries` and `used_at` only). (2) `app/portals/src/code_challenge.rs`: the rule (SEC-055): a challenge lives as long as the Verify code (10 minutes from its first send, the `SEND_WINDOW_SECONDS` both files use); a send (`send_sign_in_code`, `open_request` and a new `resend_request_code` for an open request) made while an unused challenge of that purpose and subject is still alive reuses it and does not reset its tries or its send time, because Twilio keeps one pending code per number for its life, so the cap is truly 5 per code; a send after the newest challenge expired or was used opens a new one; each is written in a short committed transaction before Verify is called. A check is refused before Verify is called unless the newest unused, unexpired challenge of that purpose and subject exists; it reserves a try against that challenge by one atomic `UPDATE ... SET tries = tries + 1 WHERE id = $1 AND used_at IS NULL AND tries < CODE_TRIES RETURNING`, committed before the Verify call (the cap is `business_auth::CODE_TRIES`, the same constant as T272; a reservation never comes back, so a crash or a timeout uses a try); a right code then uses the challenge with a conditional `UPDATE ... SET used_at = $2 WHERE id = $1 AND used_at IS NULL` in the same transaction as the action it confirms (the session start, or the confirmed audit row with the copy or the delete), and when no row changes (a second right check got there first) the action rolls back and nothing is done twice. No pooled connection, transaction or reservation is held across the Verify await (pentest PT-04's availability side, D-2349): `send_sign_in_code`, `finish_sign_in`, `open_request`, `confirm_request` and `resend_request_code` take `&PgPool` in place of `&mut PgConnection` and acquire a connection only for each short database step, releasing it before Verify is called; T307 calls them with the router's pool. Picks' codes and business sign-in keep their own rows (T272 binds the business code to its sent challenge). (3) No change to `stand_ins/twilio.py`: it keys a verification by `to` only, which is the shared-service model these tests need. Tests in `tests/security/tests/code_purpose.rs` (TD-SEC-60): a code sent for one purpose is refused for another before Verify is called (a sign-in code cannot confirm a delete whose own challenge expired or was used; a pick code cannot sign in); 20 simultaneous wrong checks reach Verify at most 5 times and the sixth is refused; a used challenge is refused; a right code and the action commit together; a re-send inside the code's life reuses the challenge and gives no more tries, and one after expiry or use opens a new one; two simultaneous right checks act once; with a fake Verify that hangs, 30 concurrent sends and checks leave a pool of 5 connections able to serve another request (the matrix's AVAIL-01). Update the `portals` `CLAUDE.md` and `docs/decisions.md`, and add this task's line to the off-database records and recovery notes of `docs/architecture.md` (found by grep, never loaded whole; D-3079, D-3286).
