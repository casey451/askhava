# T346: portals: every homeowner Verify code is bound to its purpose by a local challenge with a try cap

## Goal

Pentest PT-03 and the PT-02 gap beyond the report (D-2348; SEC-055, SEC-008, PRIV-031). One Twilio Verify service serves every purpose and `VerifyAdapter::check_code(to, code)` (`app/adapters/src/verify.rs:50`, :86) is not bound to one, so `confirm_request` (`app/portals/src/data_download.rs:210`) acts on any of her open requests (up to 30 days old) after any passing code for her phone, the sign-in code included, and homeowner sign-in (`finish_sign_in`, `app/portals/src/homeowner_portal.rs:164`) keeps no local challenge; neither has an app-side try cap. Build: (1) `migrations/0176_portals_code_challenge.sql` adds `portals.code_challenge` (ID, purpose `homeowner_signin`, `data_copy` or `data_delete`, subject ID (her contact for sign-in, the request for copy and delete), sent at, used at, tries; app role SELECT, INSERT and UPDATE of `tries` and `used_at` only). (2) `app/portals/src/code_challenge.rs`: every send (`send_sign_in_code`, `open_request` and a new `resend_request_code` for an open request) writes a challenge for its purpose and subject in a short committed transaction before calling Verify; a check is refused before Verify is called unless an unused challenge of that purpose and subject sent within the Verify code's life (10 minutes, the `SEND_WINDOW_SECONDS` both files use) exists; the try is reserved first by one atomic `UPDATE ... SET tries = tries + 1 WHERE tries < CODE_TRIES` committed before the Verify call (the cap is `business_auth::CODE_TRIES`, the same constant as T272; a reservation never comes back, so a crash or a timeout uses a try); a right code sets `used_at` in the same transaction as the action it confirms (the session start, or the confirmed audit row with the copy or the delete); no transaction or reservation is held across the Verify await. The signatures the server calls stay as they are, beside the new `resend_request_code` (T307 serves it). Picks' codes and business sign-in keep their own rows (T272 binds the business code to its sent challenge). (3) No change to `stand_ins/twilio.py`: it keys a verification by `to` only, which is the shared-service model these tests need. Tests in `tests/security/tests/code_purpose.rs` (TD-SEC-60): a code sent for one purpose is refused for another before Verify is called (a sign-in code cannot confirm a delete whose own challenge expired or was used; a pick code cannot sign in); 20 simultaneous wrong checks reach Verify at most 5 times and the sixth is refused; a used challenge is refused; a right code and the action commit together. Update the `portals` `CLAUDE.md`, `docs/architecture.md` section 10 and `docs/decisions.md`.
