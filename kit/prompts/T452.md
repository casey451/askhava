## Goal

Plan change D-3674 (T300 plan gap; A11Y-002, SEC-004, PRIV-002; D-1311, D-1516, D-1788, D-2029): the suite's web binary (`tests/e2e/webserver.ts`, `appEnv`, :52 to :70) runs in `ci` with no Twilio settings and no vault keys, so `app/server/src/business_signin.rs:129` falls back to `NoVerify` and `vault_from` (`app/server/src/lib.rs:321`) gives no vault: no page that sends a Verify code, reads the vault or seals a contact can run in a browser. And the Ally fixture opens each page state with a bare `page.goto` of the path a seed returns (`tests/a11y/fixtures.ts:126` to `:130`), so no page behind a session can be axe-checked. Giving the suite's own binaries the keys is not safe: `tests/a11y/j1_keyboard.spec.ts` and `tests/e2e/j1_reduced.spec.ts` rely on it serving no page pick (D-1516), and a worker holding vault keys would run the outbox sender over rows that `tests/e2e/j1_homeowner.spec.ts`'s own binary sealed under other keys. So, as `j1_homeowner.spec.ts` does for itself (D-2029): (1) `tests/e2e/webserver.ts`'s setup also starts a second web binary (no second worker), the keyed binary, from the same build on `webPort() + 19`, with the suite's environment plus fake values made at run time: `ASKHAVA_TWILIO_ACCOUNT_SID` (`AC` and 32 zeros, the stand-in's account), `ASKHAVA_TWILIO_AUTH_TOKEN`, `ASKHAVA_TWILIO_VERIFY_SERVICE_SID`, `ASKHAVA_TWILIO_VERIFY_BASE_URL` on the stand-in, `ASKHAVA_MASKED_POOL_SIZE` 1 and `ASKHAVA_MASKED_NUMBERS` (`TwilioConfig::from_settings` needs the pool, `app/adapters/src/config.rs:230`), its own `ASKHAVA_ID_SECRET`, and `VAULT_KEY` and `VAULT_INDEX_KEY` (`1:` and the base64 of 32 random bytes); the same test-control secret and clock file as the suite's binaries; no `ASKHAVA_PUBLIC_BASE_URL`, so it serves no webhook. The setup waits for it like the first binary and the teardown stops it. The suite's own web binary and worker keep exactly the environment they have. The keyed values reach the test processes the way `controlSecret()` does (set in the Playwright main process's environment before the workers start), under names that do not start with `ASKHAVA_`, so `appEnv` never passes them on. (2) A new `tests/e2e/keyed.ts` exports the keyed binary's base URL and ID secret, and `seal(table, column, id, plain)` and `blindIndex(purpose, value)` in the vault's own formats (`app/privacy/src/vault.rs`: AES-256-GCM under the run's `VAULT_KEY` version 1 with a random 96-bit nonce, stored as the 2-byte big-endian version, the nonce, then the ciphertext with its tag, associated data `<table>|<column>|<id>|v1`; the index HMAC-SHA256 under the key HMAC(`VAULT_INDEX_KEY`, `<purpose>|v1`)), with node's `crypto` only. (3) `tests/a11y/fixtures.ts`: a seed may return `{ url, cookies }` instead of a path: an absolute URL on the keyed binary or a path, and cookies (name and value) that `open` adds to the page's context for that URL's origin (`Secure`, `HttpOnly`, `SameSite=Lax`, host-only, path `/`, as a `__Host-` cookie needs) before `page.goto`; `PageEntry.seed`'s type in the shared `tests/a11y/page_states.ts` widens to match and every existing entry stays as it is; `open` keeps its 200 check and its token masking. `NOT_PAGES` gains `/b/billing/statement.csv` (T300's CSV statement, a download checked through `/b/billing`). No other check, tag, width, state or route rule changes. (4) `tests/e2e/keyed_server.spec.ts` proves it: a fake active business whose owner has a texting staff phone (555-01xx) sealed with `seal` into `privacy.staff_phone` (`privacy.staff_phone|number|<line>|v1`, `migrations/0188_privacy_business_contacts.sql`) and a `portals.login_link` row for a token the spec chose, seeded through `psql` on `DATABASE_URL` as `tests/e2e/j1_reduced.spec.ts` seeds; opening `/b/sign-in/{token}` on the keyed binary and pressing Sign in sends a Verify code to that phone (the stand-in's `/_stand_in/twilio/code?to=` hook answers for it) and typing it signs the browser in; and a cookie a seed returns reaches the keyed binary on the next request (read from that request's `Cookie` header). Fake data only; no key or value is printed or logged. Update `docs/decisions.md`.

Acceptance: `tests/e2e/keyed_server.spec.ts` passes in the e2e suite against the stand-ins; the e2e and Ally suites pass with the keyed binary running and every existing spec, page state and check unchanged; the suite's own web binary and worker start with exactly the environment they had.
