# T287: payments and picks: the fee fixed at the pick is stored by payments, a press must match it, and a fee-mode switch after the pick is refused before any charge

Task T287 (harness, phase 1, stage 4). Slug: fee-fixed-at-pick.

## Goal

No code stores the fee fixed at the pick: `picks`' `new_pick` (`app/picks/src/service.rs:340`) says "No fee ... here", `payments`' `fee_at_pick` (`app/payments/src/rules.rs:496`) is a pure function nothing outside tests calls, and `open_intent` and `confirm_and_pay` (`app/payments/src/charge.rs:91`, `:146`) charge whatever `Press::amount_cents` the caller passes (`app/payments/src/models.rs:325`), checking only that it is not 0 (third external audit, D-1871). And the fee-mode check runs only after Stripe has charged: `record_fee_at_confirm` (`app/payments/src/service.rs:344`) refuses with `ConfirmError::Mismatch` when the mode changed, so a switch between the pick and Confirm leaves money moved with no ledger entry until the reconcile; and nothing stores the fee terms in force: `switch_fee_mode` (`app/payments/src/service.rs:207`) only returns them and every caller passes its own `FeeTerms`. (1) `migrations/0155_payments_fee_terms_pick_fee.sql`: `payments.fee_terms`, one row (mode and authorization version), seeded with `tiers` and `AUTHORIZATION_VERSION`, the app role SELECT and UPDATE only; and `payments.pick_fee` (`pick_id` primary key, `business_id`, `job_id`, `mode` `tiers` or `flat`, `kind` `charged` or `fee_free`, `amount_cents` at or above 0 and above 0 only for `charged`, `terms_version`, `fixed_at`), the app role SELECT and INSERT only. `switch_fee_mode` writes the new terms to `payments.fee_terms` in its own transaction with its audit row (T108's owner switch calls it and stores nothing else), and `payments::api::fee_terms_in_force(conn)` reads them; `picks` and T261 read the terms only through it. (2) `app/payments/src/pick_fee.rs`: `payments::api::fix_fee_at_pick(tx, pick, business, job, &PickedFee, at)` writes it once (a repeat with the same values is a no-op, different values an error) and `pick_fee(conn, pick)` reads it. (3) `new_pick` computes the fee with `fee_at_pick` from the chosen quote (its amounts and period), the job's category and job type facts and `fee_terms_in_force`, through the modules' `api`s (FEE-005's inputs only, D-1415), and calls `fix_fee_at_pick` in the pick's own transaction; a pick whose fee can't be fixed is not stored. (4) `open_intent` and `confirm_and_pay` read `pick_fee` before anything else: no row, a different business or job, a $0 fee, or `amount_cents` other than the stored one is the new `ChargeError::FeeMismatch`, and Stripe is not called; an existing `pick_intent` whose amount differs from the stored fee is the same refusal. (5) The mode check moves before the charge: `may_confirm` takes the pick, reads `fee_terms_in_force` itself and refuses with the new `ConfirmError::FeeModeChanged` when the stored `mode` differs from them, before any PaymentIntent is opened or confirmed; `record_fee_at_confirm` takes the pick and writes the stored fee, comparing the gate's `Authorized` (whose mode matched the pick's at the gate) with the stored mode, so a switch that commits after the gate changes nothing for this pick and the post-charge write can no longer fail for a mode switch. D-072 still applies to every pick made after a switch. Tests in `tests/integration/tests/fee_fixed_at_pick.rs`. This is a harness task because it changes tests of DONE tasks (T060's `fee_mode_switch.rs` and `fee_at_pick.rs`, T062's `charge_attempts.rs`, T189's `confirm_and_pay.rs`) and T263's `fee_limit_race.rs`: each fixture only gains the stored fee terms and the stored pick fee its presses now need (and `may_confirm` the pick), and no expected value changes. Update the `payments` and `picks` `CLAUDE.md` files and `docs/decisions.md` (`docs/architecture.md` section 3 already lists the new table, D-1871).

Acceptance: TD-FEE-48 passes against PostgreSQL with a fake `IntentStripe` that records every call; every case in `fee_mode_switch.rs`, `fee_at_pick.rs`, `charge_attempts.rs`, `confirm_and_pay.rs` and `fee_limit_race.rs` passes with its fixture given only the stored fee terms and pick fee, and no expected value changes.
