## Goal

Nov 10 code review, payments F1 and F5, first half (D-2623; FEE-042, SEC-030): no code on the payment-success path has the Stripe charge (`ch_…`) ID, because the adapter's `PaymentIntent` (`app/adapters/src/payments.rs:32`) has no `latest_charge` and the stand-in returns none; T359 needs it to write the charge ledger entry and the evidence. This harness task adds `latest_charge: Option<String>` (`#[serde(default)]`, so a body without it still decodes; the release check that requires it on a succeeded intent is T359's) and makes `stand_ins/stripe.py` return a `ch_` ID on every succeeded intent (the confirm answer and the fetch; D-3118: T405, before this task, already stores `latest_charge` as a `ch_` ID string and `stand_ins/server.py` expands it to the charge object only on `expand[]=latest_charge`, so this task keeps that stored ID and that expand behaviour and only checks the ID reaches the adapter), checked by `tests/contract/test_stripe_latest_charge.py` (TD-FEE-66).
