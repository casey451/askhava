## Goal

Plan change D-5191 (a flaky test; it cost T615 attempts 1 and 2 on Nov 21, 2026, Ci run 44880845069; `BUILD_BRIEF.md:272`; precedent D-4196, T599). `tests/integration/tests/intake_order_card.rs:268` (T673, DONE; TD-INT-47, INT-041, CARD-007) asserts that none of `CONTACT` (`:46`: "Testa", "Sample Ave", "555", "@") is in a long card's text, and that text also holds her quote-page link `https://<domain>/q/<token>`, whose token is 64 random hex characters (`app/jobs/src/quote_token.rs:47`, `link_token`), so "555" turns up in it by chance in about 1.5% of runs (62 places times 16 to the minus 3). Fix, keeping the check at least as strict: in `td_int_47_a_long_card_is_shown_by_link`, cut each `/q/` followed by 64 hex characters down to `/q/` and assert the cut removed exactly one token (so a link that changes shape fails the test), then assert that no `CONTACT` item is in the rest of the text, so her fake name, street, a 555 number or an `@` anywhere in the words still fails. Narrowing "555" to a longer fragment for every check was rejected: it would weaken the three checks on texts with no link (`:199`, `:206`, `:299`), which stay unchanged. Sweep: grep `tests/` and `app/` for other negative `contains` checks of 3- or 4-character digit or hex strings on a text holding a random token, and report any new case in the hand-in; this task changes only its one file. Nothing in the app changes.

Acceptance: `cargo test -p askhava-integration --test intake_order_card` passes against PostgreSQL with every case; the long-card check still fails when a `CONTACT` item is put in the text outside the link (shown in the report by a temporary local edit, not committed) and passes for any token; the other `CONTACT` checks are unchanged; the report lists the sweep's grep and its result.
