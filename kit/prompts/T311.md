# T311: calls and server: a voice read-back confirm connects only the line that was read back

Task T311 (build, phase 1, stage 4). Slug: voice-confirm-bound-line.

## Goal

Fourth external audit F39 (D-2201; CALL-005, CALL-002): after two bad PINs from a business's linked phone the read-back names the homeowner of one line (`calls::routing` answers `Answer::ReadBack(line, words)`, `app/calls/src/routing.rs:406`), but `pins::reply` drops the line (`app/calls/src/pins.rs:299`), the voice route's confirm URL carries only the try number (`app/server/src/inbound_voice.rs:206`), and `voice_confirm` connects whichever open line of the caller's business is newest at the press (`pins.rs:335`), so a line opened, closed or moved between the read-back and the press bridges the caller to a homeowner who was never read back. (1) The line read back is bound to its try: `migrations/0174_calls_readback_line.sql` adds a nullable `readback_line` (the line's ID) to the try's `calls.pin_call` row, inserted with the row: `Step::ReadBack(line)` is known in `judged_count` before `count_once` writes the row, so the line goes in that insert, in that transaction, and no `UPDATE` grant is added. Twilio's resend of the read-back turn returns early in `judged_count` (the row exists) and today `answer_for` recomputes from the live pool; the repeat reads back the bound line from the row instead, never a newly chosen one; the confirm URL stays `?confirm=<try>`, so nothing about the line goes to Twilio or the caller. (2) `voice_confirm` reads the bound line and connects it only when the press confirms, the try is the recorded A-attested read-back try (as today), and that line is still open on the call's pool number and still belongs to the caller's linked business; otherwise it answers as for an unconfirmed press today (ask for the PIN again, or hang up) and never connects another line; the newest-line lookup is removed. (3) Tests in `app/server/tests/voice_confirm_line.rs` through the served voice route with signed fake requests (TD-CALL-17): a second line B opened for the same business between the read-back and the press connects A and never B; the read-back line A closed while B is open, or A no longer the caller's business, connects nobody; a confirm on a try other than the read-back try (a row with no `readback_line`) connects nobody; a resend of the read-back turn reads back the bound line; the unchanged case connects exactly the line read back, and a repeated identical confirm connects it again and writes no second `call_start`. Every existing `app/server/tests/inbound_voice.rs` and `tests/integration/tests/call_pins.rs` case passes unchanged. The overseer runs an independent security review of the hand-in (D-2201). Update the `calls` and `server` `CLAUDE.md` files and `docs/decisions.md`. (4) PIN draws that fail for no reason (D-2451; CALL-003, CALL-017, D-1755): `os_number` (`app/calls/src/pins.rs:53`) rejects two-byte values of 60,000 or more and gives up after 4 tries, so about 1 call in 19,600 it returns `None` although the OS source works (8.4% rejection, 0.0845⁴ ≈ 5.1e-5), and `draw_pin` (`:46`) uses `map_while`, so that one `None` ends all 8 draws; `allocate_pin` then gives none, `assign_number` (`app/calls/src/service.rs:137`) calls `refuse_line` (`:162`), which raises a false High `calls.pool_exhausted` alert and refuses the line with `NoFreePin` (the masked-line assignments at `app/picks/src/release.rs:236` and `app/picks/src/settle.rs:148`; T254's one `picks.line_retry` hides most of them). Fix: `os_number` returns `None` only when the OS source fails, by drawing again until a value below the largest multiple of 10,000 the width holds, with a cap so large it is never the reason (for example 64 two-byte draws, about 2e-69), the bytes coming from an injectable fill function so the rejection step can be tested; `draw_pin` uses `filter_map`, so a failed draw costs one of the 8 draws, not all of them. Unit tests beside the existing ones in `pins.rs`: a source that fails once and then gives a free PIN succeeds; an injected byte source that gives values of 60,000 or more several times and then one below gives that value modulo 10,000; an injected source that fails gives `None`. The two existing unit tests and TD-CALL-13's 500-line integration test (`tests/integration/tests/call_pins.rs`) pass unchanged.
