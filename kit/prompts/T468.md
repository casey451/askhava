## Goal

Plan change D-3743 (the T461 plan gap a scout found; BIZ-040, SEC-004, SEC-018, SEC-025, SEC-026, PRIV-016; D-1725, D-1837, D-3186, D-3262, D-3676): T461 must email the sign-up's email code (BIZ-040: verified "by a single-use link or 6-digit code sent to it") and, on activation, the owner's normal sign-in link, but neither has a public path. A link is minted, stored and emailed only inside `portals` (`send_one` is private, `app/portals/src/business_auth.rs:694`; `models::new_link_token` and `admit_link` are `pub(crate)`, `app/portals/src/models.rs:28`, `:71`), and `SignInMail::send_link` (`business_auth.rs:138`) only emails a link it is handed. `start_signup_check` returns the code and emails nothing (`app/businesses/src/email_verification.rs:134`), `businesses::api` has no reader for the sign-up's mailbox ID, which `confirm_mailbox` (`:363`) needs, and nothing in the app emails a mailbox code. This task adds three thin public paths over code that exists; T461 composes them. (1) `app/portals/src/business_auth.rs`: `pub async fn send_sign_in_link<M: SignInMail>(db, mail: &M, to: SignInAddress, now) -> Result<(), PortalsError>` (one `pub use` line in the shared `app/portals/src/api.rs`). The body of `send_one` moves into a private function that takes the mailer instead of the `SignIn` state; `send_one` and the new function both call it, the new one with no next job: the same current-member check (nothing sent for a mailbox that is not a current member of `to.business`), the same `LINKS_PER_LIFE` cap under the member's lock (`admit_link`, D-1725, D-1837) and the same `{site()}/b/sign-in/<token>` link through `M::send_link`; its `///` comment says that `M` delivers the link only to `to.mailbox`'s own address, never to another (SEC-004). No other behaviour of `business_auth.rs` changes. (2) `app/businesses/src/email_verification.rs`: `pub async fn signup_mailbox(conn, business) -> Result<Uuid, EmailCheckError>` (one name in the shared `app/businesses/src/api.rs` export), the `businesses.signup` row's `mailbox_id` as `start_signup_check` reads it, `EmailCheckError::Database` for an unknown sign-up; `start_signup_check` and `confirm` keep their signatures. (3) `app/messaging/src/mailbox_code_mail.rs`: `MailboxCodeSender<E>`, built as T280's `SignInLinkSender` is (`app/messaging/src/signin_mail.rs`: the key secret, the provider, the checked postal line and the `DailyLimit`), whose `send(db, (mailbox, address), code, now)` queues one business email through `queue_account_email` from a new template `business_mailbox_code` (English, and Spanish marked draft, in the shared `app/messaging/templates/en.json` and `es.json`: the subject "<brand short name>: Your email code", the 6-digit code, that it works for the next 30 minutes (`CODE_LIFE`), and that a person who did not sign up can ignore it) and sends it at once with `send_email`. The code is a credential, so the stored row holds `CODE_MARK` (`[email code]`) in its place and the code goes in only on the way to the provider, through a wrapper like `signin_mail.rs`' `WithLink`; the row's key is the account-email key over the template, the mailbox and one ID keyed from the code and the send time (a repeat of one send is one email, SEC-018; a resend is a new one); the code is never logged. The sender counts nothing itself: its `///` comment says the caller admits every send first under SEC-014's per-IP and per-business limits (T461 does, where the client IP is known). `MailboxCodeSender`, `CODE_MARK` and the template ID are exported through the shared `app/messaging/src/api.rs` and `lib.rs`. The caller opens the address (`server`, under `privacy::api::BusinessPurpose::AccountEmail`, on a bare connection), as T280's sender is handed it; this task names no vault read. Tests, fake data only, in `tests/integration/tests/signup_mail_paths.rs` against PostgreSQL: `send_sign_in_link` stores one link for the owner and hands a recording `SignInMail` one `/b/sign-in/` link on the brand's site for that `SignInAddress`, sends nothing for a mailbox that is not a current member, and sends no more once `LINKS_PER_LIFE` links went in `LINK_LIFE`; `signup_mailbox` answers the mailbox `sign_up` stored and refuses an unknown business; `MailboxCodeSender::send` gives a recording `EmailAdapter` one email to the address whose text and HTML hold the code, a refusing provider leaves the stored row holding `CODE_MARK` and never the code, and a repeat of the same send queues and sends nothing more. Update the `portals`, `businesses` and `messaging` `CLAUDE.md` files and `docs/decisions.md`.

Acceptance: `tests/integration/tests/signup_mail_paths.rs` passes against PostgreSQL: `send_sign_in_link` sends one stored link to the owner's `SignInAddress`, none to a mailbox that is not a current member and none past `LINKS_PER_LIFE`; `signup_mailbox` answers the sign-up's mailbox; `MailboxCodeSender` sends one email holding the code while the stored row holds only `CODE_MARK`, and a repeat sends nothing more; `app/server/tests/business_signin_route.rs`, `tests/security/tests/business_signin.rs`, `tests/integration/tests/notice_signin_link.rs` and `tests/integration/tests/email_verification.rs` pass unchanged; `check_copy.py` and `check_ai_smell.py` report 0 problems on the new template.
