# T273: privacy: a photo's plaintext is returned only after its open audit has committed on its own

Task T273 (build, phase 1, stage 4). Slug: photo-open-audit.

Model: `claude-opus-5-5`, effort high. Reviewer: `claude-opus-5-5` (areas: privacy, security).

## Goal

`privacy::api::open_link` (`app/privacy/src/photos.rs:427`) decrypts the photo, writes its `privacy.photo_opened` audit row on the caller's connection and returns the bytes, so a caller inside a transaction (an SQLx transaction or a raw `BEGIN`) can hold the plaintext and roll the audit back (second external audit B02, D-1838). The contact vault already refuses this with `ensure_bare` (`app/privacy/src/vault.rs:475`, D-753). `open_link` refuses a connection inside a transaction with the same probe (moved to a `pub(crate)` helper both files use, so there is one copy) and a new `PhotoError::InTransaction` (the enum is in `app/privacy/src/models.rs:418`, owned here for that variant only, D-3118), and returns plaintext only after the audit row has committed by itself; an audit-write failure returns no bytes. Link expiry, AES-GCM under the vault key, `no_store` and the `LinkDead` 404 stay as they are; no route is added (D-1791 leaves the photo route to the first task that shows a photo). Tests in `tests/integration/tests/photo_open_audit.rs`. Update the `privacy` `CLAUDE.md` and `docs/decisions.md`.

Acceptance: TD-PRIV-17 passes against PostgreSQL; every TD-PRIV-04 and vault-reader case still passes; `tests/security/tests/vault_readers.rs` passes unchanged; the `app/privacy/` 95% floor holds.
