## Goal

Dynamic SQL hides schema references from TD-SEC-10 (D-1677): `schema_refs` in `tests/integration/tests/architecture_migrations.rs` lexes dollar-quoted bodies as SQL but cannot see a schema name built while a migration runs, so a migration such as `DO $x$ BEGIN EXECUTE format('ALTER DEFAULT PRIVILEGES IN SCHEMA %I REVOKE ...', nsp); END $x$;` names no schema literally and passes (seen in T250's third attempt, PR #293, not merged). In that test (T226's, then T250's, taken over here after T250 merges) add a dynamic-SQL rule over each migration's lexed tokens (the tokens `schema_refs` reads, so comments and `'...'` strings never count). A file gives one finding, `migrations/<file>: dynamic SQL (`<construct>`) hides schema references from this check`, naming the first construct found, when it holds: a `DO` statement (the token `do` first in a statement, at the start of the file or after `;`, so `ON CONFLICT DO NOTHING` and a rule's `DO INSTEAD` never count); an `execute` token not followed by `function`, `procedure`, `on` or `,` (the PL/pgSQL dynamic statement, including inside a `CREATE FUNCTION` or `CREATE PROCEDURE` body, `RETURN QUERY EXECUTE` and a cursor's `FOR EXECUTE`; a trigger's `EXECUTE FUNCTION` and `GRANT`/`REVOKE EXECUTE ON FUNCTION` are not dynamic); or a call of `format`, `quote_ident`, `quote_literal` or `quote_nullable` (the name followed by `(`). The SQL of each query macro and `query_file*` file under `app/` gets the same finding for `DO` and `execute` (a `format(` there only formats a value). A file is exempt only when its path is in a new constant `DYNAMIC_SQL_ALLOWED: [(&str, &str); N]` (path, one-line reason); it starts with one entry, `migrations/0019_core_db_migrations.sql`, whose `DO $guard$` block only raises an error when the role `askhava_app` is missing and builds no SQL (T012). An entry whose file is missing or no longer holds dynamic SQL is itself one finding, so the list cannot go stale. The checks take the allow list as a parameter: `td_sec_10_migrations_and_sql_obey_the_rules` passes the constant and each plant passes its own, so a planted path never enters the real list. Planted cases giving exactly one finding each: a `DO` block, an `EXECUTE` in a `CREATE FUNCTION ... LANGUAGE plpgsql` body, a `format()`-built statement, a query macro holding `EXECUTE`, and a stale allow-list entry; planted cases giving none: an allow-listed file holding a `DO` block, an `INSERT ... ON CONFLICT DO NOTHING`, a `CREATE TRIGGER ... EXECUTE FUNCTION` and a `GRANT EXECUTE ON FUNCTION`. Every earlier case, T250's included, still gives exactly its one finding: each T250 case whose plant holds a `DO` block (those proving a `DO` block voids the REVOKE exception, such as a REVOKE beside a `DO` block and a REVOKE inside one) runs with its planted file on its own allow list, so it still proves only its own rule. If another migration on `main` holds dynamic SQL when this task starts, list it only when it builds no schema name at run time, with its reason; otherwise stop and report. Update the test's `//!` header to name the rule, and the `migrations/` entry of `docs/architecture.md` section 2 (T226's paragraph on this test) to name it too (section 4 rule 3 already states it, D-1677).

From `docs/brains/postgres-operations.md` (cite its tags in the PR; read other sections only when a design choice needs them):

### 2. Principles (lines naming this task's requirements)
**P3. Two roles; the app role never owns anything.** Roles are created outside migrations by the host or a bootstrap script (D-481). The migration role owns every schema and table; the app role (`askhava_app`) used by `web` and `worker` gets only `USAGE` and table privileges. Why: "The right to modify or destroy an object is inherent in being the object's owner, and cannot be granted or revoked in itself" (PostgreSQL privileges docs), so an app role that owned a table could always rewrite it. Serves D-092, threat T6, SEC-029.
**P6. Lock down `public`.** PostgreSQL 15 removed `PUBLIC` create permission on the `public` schema for new databases, but "Upgrading a cluster or restoring a database dump will preserve `public`'s existing permissions" (PG 15 release notes). A bootstrap or first migration should `REVOKE CREATE ON SCHEMA public FROM PUBLIC` anyway; it is idempotent. Serves SEC-029 (one schema per module, D-091).
### 4. Checklist
1. The migration is new, numbered, forward-only, and its first comment names module, purpose and requirement IDs (P1).
2. It touches only its own module's schema; no cross-schema foreign key (Arch 4 rule 3 and its exceptions, D-1632); no `DO` block, `EXECUTE` of a string or `format()`-built SQL, which hides a schema name from the check (D-1677).

4. Grants and default privileges are present and idempotent; nothing is owned by `askhava_app` (P3, P4).
5. Append-only tables revoke `UPDATE`, `DELETE`, `TRUNCATE` from the app role, and a `SET ROLE` test proves it (P5).
6. Every instant is `timestamptz`; no `BETWEEN` on times; no `serial` (P7, P11).
7. Queue and lookup queries are served by a narrow index (partial, unique dedupe, blind-index hash) (P9, P12).
