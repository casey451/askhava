# T656: site: a failed submit on the /request chat shows a focused error summary first, marks the field and keeps what she typed

## Goal

Plan change D-4326 (night accessibility spot review of `main` e64d06e02, re-verified on `main` d662af7e5; A11Y-030, A11Y-035, TD-A11Y-02). A failed submit on the `/request` chat breaks A11Y-030: the notice (`#chat-notice`, `app/site/templates/request.html:28` to `:30`) comes after the h1, both consent texts, the 18-or-older line and the transcript, with no `tabindex` or `autofocus`; no field gets `aria-invalid`; `answer` clears the typed number on every step but the code step (`app/site/src/chat.rs:398` to `:400`) and the job-words textarea is never refilled, so after `FAILED` (`:298`, `:308`) her words are gone; and `NO_CODES`, `OPTED_OUT`, `TOO_MANY` and `TRY_LATER` (`chat.rs:96` to `:113`) refuse her answer with `error` false, so the title has no "Error: " and the line sits in a `role="status"` region filled at first render, which is not announced. (1) Whenever the page shows a notice that refuses her answer or sends her back a step (`EMPTY`, `BAD_NUMBER`, `WRONG_CODE`, `FAILED` and the four above), it renders an error summary as the first element in `main`, before the h1: `<div id="chat-notice" role="alert" tabindex="-1" autofocus>` holding the line as a link to the field it is about (`#chat-words`, `#chat-number` or `#chat-code`), and the title begins "Error: ". A notice that reports progress (`OPEN`, `TEXTED`) stays where it is, in its `role="status"` region, with no "Error: ". The id `chat-notice` and every notice's words are unchanged, so `tests/e2e/web_chat.spec.ts` passes unchanged. (2) The field the error is about carries `aria-invalid="true"` beside its `aria-describedby`, which keeps `chat-notice`. (3) Every entered value is kept: after a refused or failed message step the textarea shows her words again; after a refused number step the number field shows the typed number again (the page is `no-store`, and D-4044 already round-trips the number in the code form's hidden field); a code is never refilled. Refilled words and numbers are only echoed, autoescaped, into this response's form: never stored in the session, logged or added to the `said` transcript. (4) No announcement of new chat lines after a successful turn: A11Y-035 asks for one question per page with the conversation above it, which the page already does, and no script is added to a site page (WEB-029). (5) Tests, fake data only: `tests/e2e/web_chat_errors.spec.ts` (TD-A11Y-04) drives the chat without JavaScript at 320 and 1280 px through an empty message, a bad number ("92855501") and a wrong code; for each it checks the title starts "Error: ", the summary is the first child of `main` and is focused (`document.activeElement`), its link targets the field, the field has `aria-invalid="true"`, the typed words or number are back in the field, and `axeScan` (`tests/a11y/fixtures.ts`) reports no violation; it also scans the number step and the code step with no error. Unit tests in `chat.rs`'s test module render each refusing notice and each progress notice and check the order, attributes and refilled values. `tests/a11y/page_states.ts` opens each state by GET from its seed, so it cannot open these POST answers; the e2e spec scans them. Ordered after T593 and T609 (both own `request.html`) and T649 (owns `chat.rs`, after T646); T299, the other queued owner of `chat.rs`, runs after this task. Update `app/site/NOTES.md` and `docs/decisions.md`.

Acceptance: TD-A11Y-04 passes; `tests/e2e/web_chat.spec.ts`, `web_chat_route.rs`, the site crate's tests and the Ally suite pass unchanged; no script is added to the page.
