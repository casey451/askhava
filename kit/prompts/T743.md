# T743: messaging and privacy: opt-out listings are re-keyed to the active index key version, and a version is retired only once every listing under it is re-keyed

## Goal

Plan change D-4748 (Fable's decision (2), Nov 19, 2026; designs D-4418's open item; PRIV-024, CON-035, CON-013). PRIV-024 (`docs/spec/privacy.md:28`, reworded by D-4748) lets a `VAULT_INDEX_KEY` version be retired only once every opt-out listed under it is also listed under the active version. Today `record` (`app/messaging/src/optout.rs:332`) lists a number under the versions configured at that moment and nothing re-keys a listing, so T702's start check (`app/messaging/src/suppression_versions.rs:39`) keeps every held version configured for good and a leaked version can never be retired. This task, in the new `app/messaging/src/suppression_rekey.rs` (public calls re-exported through the shared `messaging::api`): (1) `rekey_suppression_batch(db, vault, limit) -> Result<usize, _>` takes up to `limit` numbers listed under an older version with no row under the active one, finds each one's kept vault phone (D-079 keeps it while the number is listed) through a new `privacy::api::phone_for_index(conn, vault, (version, digest))` in the new `app/privacy/src/suppression_phone.rs` (re-exported through the shared `privacy::api`; it matches the contact's stored homeowner-phone digest under that version, reads the phone under `Purpose::Rotation` (`app/privacy/src/models.rs:148`), audits the read as `rotate_batch` does (PRIV-003) and returns a `SecretString`, never logged or put in an error), and, holding T701's per-number lock (`lock_number`, `optout.rs:455`) in the same transaction, adds the missing rows under every configured version with the channel, method and time of the row it copies; it returns how many numbers moved and is run beside `rotate_batch` (`app/privacy/src/vault.rs:767`) until both return 0. A listing whose phone no contact holds is counted and left, never guessed. (2) `retire_index_version(db, vault, version)` refuses (naming counts and version numbers only, never a digest) when `version` is the active one or while any number listed under it lacks its row under the active version; otherwise it deletes the rows under `version` in one transaction with one audit row, after which the operator drops the version from `VAULT_INDEX_KEY` and T702's start check passes. T702's start check and its test are unchanged. (3) The order (add the new version, run both batches to 0, retire, then drop) goes in the `messaging` and `privacy` notes and `docs/architecture.md`; `docs/runbook.md` is not this task's file. Tests in the new `tests/integration/tests/suppression_rekey.rs`, PostgreSQL, fake 555-01xx numbers only: a v1-only opt-out gains its v2 rows and `send_checked` still refuses the number after v1 is retired and dropped; retiring refuses while one listing lacks its v2 row, and for the active version; an opt-out arriving during the run on a second connection leaves exactly one listing per version (the lock); no log line, error or audit row holds a phone or a digest. Integration-closure row IC-98 (privacy, open) names this task: Gate C's `--ask` (T395, D-3080) stays unmet until a plan change closes it with this task's merge evidence. Opus worker, Opus security and privacy review, two review rounds (the second on the head the first round's fixes produce, D-3753). Update the `messaging` and `privacy` notes, `docs/architecture.md` and `docs/decisions.md`.

Acceptance: `tests/integration/tests/suppression_rekey.rs` passes against PostgreSQL with every listed case; `tests/integration/tests/suppression_key_versions.rs` and `tests/integration/tests/optout_number_lock.rs` pass unchanged; no log line, error or audit row holds a phone or a digest.
