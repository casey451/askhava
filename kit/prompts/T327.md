## Goal

Fifth external audit AH-001 (D-2285; JOB-006, OPS-004; IC-27, D-1428): production code queues `core.task` kinds that no handler in the production worker runs (`server::register_handlers`, `app/server/src/lib.rs:339`, and `app/server/src/bin/worker.rs:50`), such as `payments.charge_check`, `payments.pay_timer`, `payments.refund_retry`, `payments.reconcile` and `calls.safety_call`; such a task fails with `NO_HANDLER` (`app/core/src/tasks.rs:395`) and is dead-lettered after its attempts with nothing raised, and IC-27's owners (T140, T237) never had the duty in their goals. (1) `tests/integration/tests/task_registry.rs` builds the registry exactly as the production worker does (`register_handlers` plus every registration `worker.rs` adds, with stand-in settings so the conditional ones such as `picks.line_retry` and `jobs.homeowner_text` are present) and collects every kind the app can queue: each `const *_KIND: &str` in non-test code under `app/` and each string literal passed to `NewTask::new`, less a fixed list of constants that are not task kinds (subject kinds such as `calls.number_pool`, `privacy.contact`, `payments.fee_mode`, each with its reason). The scan has a floor: it must find known kinds (at least `payments.charge_check`, `payments.reconcile`, `intake.no_reply` and `calls.safety_call`), so a scan that finds nothing fails instead of passing; a kind held in a constant not named `*_KIND` and passed through a helper is outside the scan (stated in the module docs, and each such constant found is renamed or added to the scan list). The test fails when a kind is neither registered nor listed in `tests/task_kinds_deferred.json`, or when a deferred entry lacks its owner task ID and reason; a deferred kind that is registered passes and is printed as stale. The deferred list starts as D-2285 names it (each kind with its owner: T313, T281, T255, T251, T268, T151, T328, T329, T330) and only shrinks: an entry is removed in the plan change after its owner merges; adding one needs a harness task, since the file is this task's test. (2) `app/server/src/no_handler_alert.rs`: an hourly worker task (registered in the shared `app/server/src/lib.rs`, first run seeded in `worker.rs`'s `schedule_start`, idempotent by its dedupe key) raises, in the test and live environments only, one High `core.task_no_handler` alert per kind that has a dead-lettered task whose last error is `NO_HANDLER`, at most once per kind (it checks for that kind's open alert first), naming the kind and the count, never a payload. `core` stays as it is (it may not call `ops`). Tests: TD-OPS-36 and TD-OPS-37. IC-27 now names this task. Update `app/server/CLAUDE.md`, `docs/architecture.md` section 10 and `docs/decisions.md`.

### 2. Principles that bind this codebase (lines naming this task's requirements)
**R11. Work that leaves the database is queued in the same transaction as the state change.** A state change and its `core.task` row commit together; never call a vendor inside the transaction that changes status. Brandur: enqueue mid-transaction and the job runs too early; enqueue after commit and a crash loses it ("Data is persisted, but the background work doesn't get done"). Here the queue is in the same database, so the insert is simply part of the transaction. Serves JOB-004, JOB-005, JOB-006, Arch 4 rule 2.
**R12. Claim with `SKIP LOCKED`, keep claim transactions short, hold a lease, re-check on run.** PostgreSQL: skipping locked rows "can be used to avoid lock contention with multiple consumers accessing a queue-like table" (select.sgml text, see postgres brain P9). Long transactions pin the vacuum horizon and degrade a hot queue (Brandur 2015; PlanetScale 2026). So: claim and commit, run the handler outside that transaction, finish with a fenced update. Handlers first re-check the current status (JOB-006). Serves JOB-006, Arch 5 task queue.
