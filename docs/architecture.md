# Ask Hava architecture

Written in kit step K4 (`BUILD_BRIEF.md:598`). This file finalizes the module boundaries that `BUILD_BRIEF.md:124`–`BUILD_BRIEF.md:152` fixes, and pins the stack versions (`BUILD_BRIEF.md:121`). Since D-453 the server is Rust (`BUILD_BRIEF.md:105`); sections 2, 4, 5, 7 and 11 describe the Rust layout. It restates and arranges rules; where it had to choose, the choice is logged in `docs/decisions.md` (D-090 to D-100) and named here. If this file and a cited source disagree, the source wins and this file is the bug. Every PR that changes a boundary, table owner, state, timeout or pinned version updates this file in the same PR (`BUILD_BRIEF.md:489`).

Citations are `path:LINE`. "Changes file" means `sources/01_spec/Changes_Since_v9.3_AUTHORITATIVE.md`; "v9.3" means `sources/01_spec/Havasu_Home_Quotes_Technical_Blueprint_v9.3.md`. Requirement IDs (for example `PRIV-005`) are in `docs/spec/`.

## 1. Shape at a glance

One web app and one PostgreSQL database do all the work; every outside service sits behind an adapter (`sources/01_spec/Havasu_Home_Quotes_Technical_Blueprint_v9.3.md:44`; `BUILD_BRIEF.md:146`).

```
 Homeowner (text, web chat,      Business (email, portal  Casey (owner portal,
 quote page, homeowner portal)   links; no calls; text    alert emails, HELP
                                 only if chosen)          notifications, calls)
            \                         |                        /
             +------------ web process (Rust: Axum + Askama) -+
                                      |
          worker process (Rust: scheduler + task runner, same crates)
                                      |
                PostgreSQL 16: one schema per module, contact vault encrypted
                                      |
                         adapters (real | sandbox | stand-in)
   Twilio texts (homeowner number; a business number only if approved, TXT-035)
   Twilio calls | Twilio Verify | Stripe | Claude API (zero retention)
   Resend email | Lob letters | license sources | object storage
   Kept outside the database: Twilio and Stripe records, web request log,
   audit stream, AI structured readings (OPS-011)
```

## 2. Processes and code layout

| Process | Runs | Notes |
|---|---|---|
| `web` | The `server` binary (Axum on Tokio): pages, portals, web chat, webhooks, `/healthz` | Stateless; any number of replicas; server-rendered Askama pages that work without JS (`BUILD_BRIEF.md:106`) |
| `worker` | The `worker` binary: the scheduler and the task runner, polling `core.task` with `SELECT … FOR UPDATE SKIP LOCKED` | Timers, outbox sends, retries, nightly jobs (`BUILD_BRIEF.md:108`; JOB-006). Same image, started with a different command |

Both binaries are built from one Cargo workspace into one Docker image (`BUILD_BRIEF.md:119`), pinned by digest (SEC-021).

- Sentinel scan: `tests/security/tests/sentinel_db_logs.rs` (T217) writes the fixture sentinels (`askhava-fixtures`) through the vault, sends a request carrying them through the `build_router` layers and runs the off-database stream, then searches every table but `privacy.contact` (bytea as hex too), the JSON log, the stream's stand-in objects and a capturing Sentry transport for them; T120 repeats it after J1 to J4 (TD-PRIV-02, PRIV-016, PRIV-019, D-795).
- AI calls: `app/ai` sends only `ScrubbedText` through its `Transport` (over `adapters`' `StandInAi` in the build) to `/v1/messages`, with the versioned instruction, the text inside one escaped `<homeowner_message>` tag, `schemas/intake_reading.json` without its `$schema` and `$id` as `output_config` (the file holds only keywords the API supports, so the 0-to-1 confidence range is checked in code, D-2760) and no tools; it retries per AI-023 within the `ASKHAVA_AI_TIMEOUT_SECONDS` budget, stops at `ASKHAVA_AI_DAILY_CAP`, writes one `ai.call_stat` row per call (model, instruction version, request ID, outcome, alert ID) and screens AI-written text with `catalog`'s CARD-010 list, a link ban and length caps, on a normalized copy (T024, D-810 to D-814).
- AI-008 gate: in live, `ai::api::read_intake` calls the AI only when a zero-retention signing date is recorded or the owner's "AI on scrubbed text" switch is on with the newest `ai.provider_terms` row complete (training-free, flagged-content retention, a Console spend limit at most 3 times the expected cost) and today's `ai.privacy_policy_version` holding the AI-018 sentence; otherwise it returns `AiOff::SwitchOff` without a call and intake runs keyword-only. Each reading is stored in `ai.reading` with no text column and its trade, job type and flags are queued for the off-database stream in the call record's transaction; `ai::api::weekly_counts` gives the weekly summary its counts (T025, D-841 to D-843).
- Text outbox: every text is queued through `messaging::api::enqueue` under an idempotency key derived (`sms.send`, `ID_SECRET`) from its template ID, recipient ID and subject IDs, unique in `messaging.outbox`; `send` claims only a `queued` row in one statement (`sending`, `sending_since`), calls the `SmsAdapter` outside any transaction with the key re-derived from the stored IDs, then marks it sent and clears its body (D-850); Twilio does not dedupe by key (D-558), so a row left `sending` by a crash or an unknown answer is never resent: the outbox sender (`messaging.send_due`, T356, D-2628) marks it `unknown` after 5 minutes, and re-checks quiet hours and the line before every send (TXT-011); a homeowner's number is read from the vault for the row's recipient at send time, a business phone is given by the caller, and a send must name the recipient kind the row was queued for (D-849); a past customer is texted only after she wrote since her request closed, from times the caller supplies, checked at enqueue and again at send (TXT-009). `messaging.sender_directory` keeps each business main or staff phone as `sender-dir` blind-index digests for `sender_add`, `sender_remove` and `sender_business` (T028, D-492, D-846, D-847, D-849, D-850).
- Text retries and email (T094, D-1378 to D-1381): a failed text is retried 10, 20 and 30 minutes after its first failure (`messaging::api::record_failure`); then `give_up` marks it `failed` and, in one transaction, lists an important text in `messaging.portal_notice` and queues it as an email when an address is on file, or records a call-back (`messaging.text_retry`, `ops.alert` `messaging.call_back_due`, due 24 hours urgent, 4 days otherwise) for a homeowner with none (TXT-014, TXT-015, INT-023). Every email goes once through `messaging.email_outbox` (`queue_email`, `send_email`, key `email.send` over template, recipient and subject IDs, no address stored), rendered in `app/messaging/templates/email_layout.html` with `lang` and the SEC-028 footer; `Bulk` emails wait for the midnight-UTC reset above the daily limit's share, a provider 429 waits and is never dropped (OPS-038). Verified Resend webhooks are stored once in `messaging.email_event` in event-time order, a complaint and 24 hours of silence raise alerts (SEC-050, SEC-051). The homeowner's update channel is `messaging.update_channel` (TXT-018). Not wired yet: the email-sending worker handler, the Resend webhook route and the `core.task` email request for modules above `messaging` (D-1380).
- Inbox and delivery statuses: `messaging::api::receive_inbound` and `receive_status` take only a `VerifiedWebhook` from Twilio and the instant from the caller's injected clock (stored as every row's `received_at`, no database default, D-863), parse MessageSid (`SM`/`MM` plus 32), MessageStatus and ErrorCode once, and record the event in `messaging.webhook_event` (source `twilio_inbound` keyed on the MessageSid, `twilio_status` on (MessageSid, MessageStatus), SEC-039) in the same transaction as its effect, so a repeat changes nothing (TXT-012): the first inbound delivery makes one `messaging.inbox` row, the first status callback appends a `messaging.delivery_event` (status folded to queued, sending, sent, delivered, undelivered, failed, with the error code). `messaging::api::delivery_status` reads a text's status from its outbox row and the events for its provider SID: never moved back by a late earlier status, so a callback that arrived before the send was marked still counts (TXT-013, T178, D-861).
- Twilio webhook routes (T241, D-1307 to D-1309): `server`'s `inbound_text::routes` (`POST /webhooks/twilio/sms` and `POST /webhooks/twilio/status`), merged by `build_router` only when `server::webhooks` built them (D-1310, D-1311) (`ASKHAVA_PUBLIC_BASE_URL` set; unset is no routes in dev and CI and a start-up error in test and live). Each delivery is checked by `adapters::api::verify_webhook` over the public base URL plus the route path and query (403 and one log line otherwise, SEC-016) and then runs in one transaction, answered 200 unless the database failed (500). An inbound text: `receive_inbound` (a repeat MessageSid stops), `privacy::api::read_inbound` (the raw body goes no further), `on_inbound_text` (an opt-out stops), `reply_to_help` (a HELP text, also from a listed number, stops after its reply; any other text from a listed number stops), then for a number not in the sender directory `intake::api::receive_reply`; a business phone's STOP also calls `businesses::api::phone_stopped`, and its other texts queue `business_auto_reply` when `businesses::api::auto_reply_due` holds (T256, D-2039). A racing first text from a new phone continues with the contact that won the unique phone index, or rolls back with a 500 (D-1751). A text a non-database module error stops after the repeat check (`Halt::Failed`) is still answered 200 and raises one High `messaging.inbound_text_failed` alert about its inbox row, the failed step in the alert's `ops` audit row, in the delivery's transaction, with no body, phone or error text (T325, D-2207, D-3107). A status callback: `receive_status`.
- Opt-outs and the one suppression list: `messaging::api::on_inbound_text` takes an inbound text's scrubbed words, its `OptOutType` and emergency flag; `rules::detect_opt_out` (sole word or listed phrase, CON-008, CON-010, CON-011) or the provider's STOP lists the number in `messaging.suppression` (digests under the `homeowner-phone` index key) and logs `messaging.optout_event` (channel, how detected, time; append-only) in one transaction; the app queues the CON-009 confirmation only for words the provider did not answer, on the first listing (the one whose insert added the suppression rows) and while texting is not paused; only the provider's `OptOutType=START` (START or UNSTOP) lifts it; anything else from a listed number sends nothing, and an emergency flag on any message from it raises a critical `ops` alert. `messaging::api::suppress` is the entry for every other revocation channel. `messaging::api::send_checked` is the send every text takes: it refuses a listed number except the HELP reply and the current listing's confirmation within 5 minutes, and a 21610 refusal lists the number and marks the outbox row `blocked`, never claimed again (T029, CON-013 to CON-017, CON-030, CON-035, D-866 to D-868, D-870).

A sent row keeps no body (SEC-037); the daily `messaging.cut_bodies` task (`run_cut`, scheduled by the worker at start and by each run) cuts the body of any row still unsent 30 days after it was queued and ends it `failed`. No log row is deleted. `messaging.inbox` stores no words. A texted opt-out's `messaging.optout_event` row keeps its detection and the `inbox_id` of the message that carried it (migration 0128). ## 4. Dependency rules

1. **Layers.** A module may use only the `api` of a module in a lower layer, never its `models` or `service`; the pure decision functions a lower crate re-exports as `api::rules` are part of its `api` and may be called (D-091, D-481, D-484). In Rust this is a compile error, not a convention: a crate lists only its allowed lower crates in `Cargo.toml`, Cargo refuses a dependency cycle, and only `api` is `pub` (D-453):

   | Layer | Modules |
   |---|---|
   | 0 | `core` |
   | 1 | `ops`, `adapters` |
   | 2 | `catalog`, `privacy` |
   | 3 | `ai`, `messaging`, `payments`, `licensing` |
   | 4 | `businesses`, `jobs` |
   | 5 | `calls`, `quotes` |
   | 6 | `picks` |
   | 7 | `intake` |
   | 8 | `recovery`, `portals`, `site` |

   `adapters` uses only `core` and the HTTP and crypto crates. Same-layer imports are allowed only where section 3's "Calls" column lists them (none today). The layer table is kept in machine-readable form in `kit/layers.json` (protected), which the architecture test reads (D-479). There is no `testing` feature: unit and property tests live inside each crate, and the test-layer crates see only `api` (D-481).
2. **Events go up, calls go down.** When a lower module must tell a higher one something (Stripe says a charge succeeded; an inbound text arrives; a license lapses; an alert is raised), it enqueues a `core.task` with an event kind and IDs only, never personal details. `app/server/src/lib.rs` (`register_handlers()`) registers which module's handler runs for each kind (D-481). No module imports a higher one.
3. **Tables.** Every query and migration names its own module's schema. The architecture test (T175, SEC-029) reads every crate's `Cargo.toml` and every migration and fails on a dependency not allowed by the layer table, any cross-schema foreign key, and any query that names another module's schema (the exceptions: `core` may name `public`, to lock it down and hold `_sqlx_migrations`; and a `core` migration may name other modules' schemas only when every statement in it is `ALTER DEFAULT PRIVILEGES IN SCHEMA <schema>, … REVOKE <privileges> ON TABLES FROM askhava_app`, which can only take a default away, T250, D-1632), on a migration whose first line (or second, after `-- no-transaction`) does not name its module and task, whose number does not rise, whose owner is missing from `kit/tasks.json`, or whose number order disagrees with its tasks' dependency order; and on any SQL outside the query macros (the function forms, `AssertSqlSafe`, `QueryBuilder`, `Executor`, `query_unchecked!`), found by a lexer scan with comments and strings removed (D-491); and on dynamic SQL, which a scan of names cannot see through (in a migration a `DO` statement, an `EXECUTE` that runs a string or a `format` or `quote_*` call; in a query macro's SQL `DO` or `EXECUTE`), outside a short allow list in the test that gives each file's reason (T252, D-1677); SQLx checks each query against the schema when it compiles.
4. **Money** moves only through `payments` (FEE-032). **Vault plaintext** comes only from `privacy::api` and only to the readers in section 8. **Release needs proof:** the function that reads contact fields for a release takes a `ReleaseProof`. Because `privacy` (layer 2) cannot name a `payments` (layer 3) type, the design is a capability (D-481): `privacy::api` defines `ReleaseProof` and a non-`Clone` `ReleaseMint`, both with private fields; `privacy::api::release_mint()` can be called once per process and panics on a second call; `server/src/lib.rs` calls it once in `register_handlers()` and hands the mint to `payments` (which therefore calls `privacy`, D-488), and `payments` alone turns a signature-checked Stripe event for a succeeded charge, or a fee decision of no fee due, into a proof. What this proves and what it does not (the skeleton trial, D-488): the compile-fail cases in a crate with no feature on prove that no other crate can construct a proof or a mint (struct literal, `Default`, `Clone`); they cannot stop a crate that depends on `privacy` from calling `release_mint()` itself, so the once-guard and the architecture test's source scan for `ReleaseMint`, `release_mint`, `SessionMint` and `session_mint` outside `privacy`, `payments`, `server` (and `portals` for the session mint) are what stop a second minter (SEC-030). Because the mint is taken once per process, tests that build the composition share one fixture per test binary. The types are T022's; the minter and the server hookup are T189's. The homeowner and owner realm reads take the capability types of SEC-046 the same way.

## 5. Shared kernel (`core`)

`core` holds what every module needs and owns no business data (D-090):

- **Settings:** one settings struct built by `Settings::from_pairs(impl IntoIterator<Item = (String, String)>)` (a hand-written parser over the `ASKHAVA_` prefix: unknown `ASKHAVA_*` keys are refused, other variables ignored, and no error message ever echoes a value; `from_iter` would trip clippy's `should_implement_trait`, D-491), which the binaries feed from `std::env::vars()` and tests from a map (edition 2024 makes `set_var` unsafe, and `unsafe` is forbidden, D-481); it refuses to start on a missing value, a live key in a non-live environment, a test key in live, or a vendor account identifier from the other environment's allow-list (SEC-002, SEC-036; `BUILD_BRIEF.md:521`).
- **Database:** the SQLx connection pool and a transaction helper; the `Guarded<T>` outcome type (`Applied` or `MovedOn`) for "only if still in the expected status" updates, each module writing its own guarded `UPDATE … WHERE id = $1 AND status = $2 RETURNING …` as a literal macro, since one shared statement cannot name another module's table (JOB-004, D-491; `sources/01_spec/Havasu_Home_Quotes_Technical_Blueprint_v9.3.md:689`). Two database roles: a migration role that owns the schemas, and an app role with no `UPDATE` or `DELETE` on append-only tables (D-092). Roles are created outside migrations, by the host or a bootstrap script with passwords from host variables; migrations hold only idempotent `GRANT`s and `ALTER DEFAULT PRIVILEGES` per schema; `server migrate` (`sqlx::migrate!`) is the release step; the append-only tests run `SET ROLE askhava_app` so the rule is exercised, not assumed (D-481). The pool's `max_connections` per process is set so that web replicas times pool plus the worker stays under the host's connection limit.
- **Clock:** UTC storage; Arizona time (no daylight saving) and the business clock of 8:00 a.m.–8:00 p.m. every day (JOB-007, D-004); the local time in a recipient's zone, which `messaging` uses for quiet hours (D-003, D-025); tests inject the clock.
- **Webhook dedupe:** one helper that records a vendor event ID in the calling module's own `webhook_event` table and reports whether it was new, so every module dedupes the same way (SEC-017).
- **Derived IDs:** HMAC-SHA-256 under a server secret over what an ID identifies, for job cards, quotes, picks, quote-page links and Stripe idempotency keys (CARD-017, PICK-028, OPS-016).
- **Task queue:** `core.task` (kind, IDs-only payload, `run_at`, attempts, lease, unique dedupe key). Workers claim with `FOR UPDATE SKIP LOCKED` (`attempts < max_attempts`, lease expired or null, ordered by `run_at`, the lease end computed in Rust from an injected clock), finish or fail with the lease owner in the `WHERE` (fencing: a stale owner's finish returns false), hold a lease that is renewed at half-life, and a crashed worker's lease expires so another picks the task up; `register_handlers()` returns the registry, which tests hold in a `OnceLock` (D-488); the trial of D-491 measured 100 tasks of 20 ms across two workers in 1.0 s and about 350 to 400 instant tasks per second, each exactly once. Every handler first re-checks the current status and does nothing if things moved on (JOB-006). The worker is one Tokio runtime running a claim loop of fixed concurrency (a `JoinSet` behind a semaphore), a poll interval with backoff, lease renewal for long handlers, a per-handler timeout, and nightly jobs inserted under date-derived dedupe keys so several replicas never double-run; on SIGTERM it stops claiming, drains within the host's grace period and releases its leases; `web` uses `axum::serve(...).with_graceful_shutdown` (D-481). Timestamps are `timestamptz` read and written through `jiff-sqlx` (D-481).
- **Rate limits:** `core.rate_limit` counters per phone, IP and business (SEC-014, SEC-015).
- **Brand:** the one brand file `app/core/data/brand.json`, compiled in: display, business, short, legal and spoken legal names, domain, email sender, card-statement prefix, the words never used alone and the Spanish forms; `brand()` serves it (installed and checked at start-up, a fake one installable in a test) and `Brand::fill` fills the `{brand}`, `{brand_business}`, `{brand_short}`, `{brand_legal}` and `{domain}` tokens of text templates; the build's Python checks read it through `scripts/brand.py`. No customer-visible line names the brand outside it, except the versioned legal records (T291 to T295, D-1932, D-1933).
- **Logging:** `tracing` with a request ID on every line; contact values are wrapped in a `Redacted` type whose `Debug` and `Display` print only a marker, so they cannot reach a log by accident; no phone numbers, names or tokens in logs (PRIV-016); Sentry with default PII off plus a scrubber (PRIV-017). Secrets are `secrecy::SecretString`, zeroed on drop.

## 8. Contact vault data flow

**What is in the vault** (`privacy.contact` and friends): homeowner names, phone numbers, emails, street addresses, on-site contacts, original photos, and the raw text of homeowner messages (texts and web-chat lines, both ways) (PRIV-001; D-093). Every other table refers to them by ID. Business text is not homeowner data: a business's quote stays in `quotes.quote` as its original wording (PICK-003), checked there for contact details (PICK-007).

**Protection:** each field is encrypted with AES-256-GCM under `VAULT_KEY`, a variable separate from the database credentials (PRIV-002); the associated data binds each ciphertext to its table, column and row, so a ciphertext copied to another row fails to decrypt; each ciphertext names its key version so the key can be rotated. Phone lookup uses a blind index, HMAC-SHA-256 of the normalized number under `VAULT_INDEX_KEY`, so the database can find a number without holding it in clear. Every plaintext read writes an audit row naming the reader, the purpose and the record (PRIV-003). Photos are encrypted the same way, under `VAULT_KEY` with their job and photo ID as associated data, before the `storage` adapter writes them, and are served only by the app's photo route (PRIV-023, PRIV-014, D-454). An outside key service (envelope encryption under AWS or Google Cloud KMS) is an option for the account checkpoint, not part of the build; the key-version field lets it be added later (D-454).

**Flow of one request:**

1. **Inbound.** Twilio's webhook (signature checked) reaches `messaging`, which dedupes by message ID (TXT-012) and looks the sender up in its sender directory.
   - **From a business phone:** the text is business text. It is stored in `messaging.inbox`. For a business that chose text it is passed on (as an event with its ID) to `intake`, which routes it to `quotes` or `picks`; for a business on email it is never routed as a quote, command or homeowner request and is answered only as TXT-037 says (D-303).
   - **From anyone else (a homeowner):** `messaging` hands the raw text, with the keyword lists it reads from `catalog`, to `privacy.api.read_inbound()`. This is the only code that sees raw homeowner text. It stores the text in `privacy.message_body`; stores contact details the person gave ("my name is …", "my email is …") in the contact record (INT-012); matches the emergency keyword stems (INT-002) and the sole-word opt-out, HELP and START words (CON-008, CON-018) on the raw text; and returns the flags plus `ScrubbedText` (names after "this is / my name is", street-number patterns, 7+ digit runs, emails, and the homeowner's vault name removed; AI-002, AI-003). Short commands ("2 YES", "CLOSE 1042", "1", "ok") survive the scrub.
   - **Order** (`messaging`, then `intake`): dedupe; emergency check; then opt-out, HELP and START. An emergency match from an opted-out number still raises the critical alert to Casey and sends no text (CON-017, CON-013). Then `intake` gets an event with the message ID, the flags and the `ScrubbedText` (stored in `messaging.inbox`) and runs the safety flow, consent and routing. Web chat follows the same path from `site`.
2. **Intake** never sees raw homeowner text; it works from the flags and `ScrubbedText`. `businesses` keeps the sender directory current through `messaging.api` whenever a main or staff phone is added or removed.
3. **AI.** `ai` accepts only `ScrubbedText`, a type only `privacy` can build (AI-004); it returns schema-checked fields or nothing (AI-005). No AI call happens in live until zero retention is signed or the owner's "AI on scrubbed text" switch is on after the provider's terms are recorded (AI-008, D-412); either way photos never go to the AI before zero retention (CARD-013).
4. **Card.** `quotes` builds the card from the scrubbed description, fixed fields and the screened card photos it reads through `privacy.api` (CARD-013, CARD-014, D-477), and runs the final plain-code gate on every card (CARD-007, CARD-008). Cards carry town and kind of place only (CARD-006).
5. **Pick and release.** `picks` asks `payments` whether the pick is paid (or free); only then does it read first name, address, full-size photos (the screened card photos went out with the card) and, when the homeowner chose email contact, the email they chose to share (PICK-018), and hand them, through `picks.api`, to the signed-in business portal only (PICK-022, PRIV-005); `messaging` sends a release email that carries no homeowner detail, only the job number and a sign-in link (PICK-024, SEC-034, D-454), and never a text (TXT-036, D-306). The homeowner's phone number is never released; `calls` reads it only to connect a masked call (PICK-023, CALL-002). The owner portal's release power only re-sends such a release (D-074).
6. **Purge.** A daily `privacy` job deletes name, address, email and photos 180 days after close unless a dispute or complaint hold exists; keeps the phone, encrypted, only with its consent and opt-out records for 5 years after the last message; deletes photos 30 days after close; and after 30 days cuts every message body (TXT-020, D-079): an outbound text keeps only its template ID; an inbound text, which has no template ID, keeps only its kind (for example "inbound homeowner text" or "inbound business text"), its time, its sender reference and its job ID, and its raw text in `privacy.message_body` and its `ScrubbedText` copy in `messaging.inbox` are both deleted. The job's scrubbed description in `jobs.job` is kept 3 years (PRIV-008), and a business's quote wording stays in `quotes.quote` (PICK-003) (PRIV-007, PRIV-009).

   **Retention lock order (T274, D-1839, D-2150 to D-2154).** Everything that decides retention takes, in this order and never another: (1) the transaction-scoped retention advisory key (`hashtextextended('privacy.retention', 274)`), exclusive for a contact purge's decide-and-clear transaction (`privacy::api::lock_retention_for_purge`) and shared inside every `place_hold` and `release_hold`; (2) the homeowner row (`intake`'s `lock_homeowner`, which every request-opening writer also takes, the request upsert locking it); (3) the vault contact row (`purge_contact`'s `UPDATE`). `intake`'s contact stage and jobless-request stage (`run_purge`, `run_request_purge`) take (1) and (2), then read eligibility (her other live requests and all her jobs in one statement, and `privacy::api::any_held` over those jobs), and clear the contact in the same transaction (`purge_contact` as a savepoint). Before taking any lock they read `core::api::unfinished` for hold-producing tasks (any unfinished `businesses.complaint_hold` event, and another job's contact-stage `jobs.purge_due` or `privacy.purge_recheck`, where `payments` places dispute holds); a task's `done_at` is written only after its hold committed, so this is safe outside the lock and keeps the `core.task` scan off the exclusive key. With one unfinished the purge clears nothing and queues itself again an hour later (dedupe key naming the task that queued it) until it has finished (D-2153). Known gap: an answer to an open jobless request takes no homeowner lock (D-2154). A request or hold that commits first is seen; one that comes later waits and then finds the contact cleared, as it would today. No outside call is made inside it (`tests/integration/tests/retention_purge_races.rs`, TD-PRIV-18).
