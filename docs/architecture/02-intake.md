# Architecture section 2 notes: `intake`

Moved here verbatim from `docs/architecture.md` (D-6022), whose index lists every part. Until T885 makes `docs/architecture/` a shared path, a task adds new notes to the index, at the end of the section this part came from, and the next plan change moves them here.

The section 2 notes ("Processes and code layout") whose first named crate is `intake`, in their original order.

- Web-chat stops (T645, D-4292, D-4473, D-4468; INT-038, CON-008, CON-010, CON-035, TXT-002, TXT-041): after the Verify code, `intake::web_chat::chat_message` runs `messaging::api::detect_opt_out` first; a hit lists the session contact's number with no vault and no plaintext read, from `privacy::api::phone_digests` through the new `messaging::api::suppress_indexed` (`RevokeChannel::WebChat`, stored `web_chat`, migration 0210), in one transaction, and the page shows CON-009's words (never a text). Any other message runs `receive_text` and then `conversation::stop_if_under_18` in one transaction; under 13 it also deletes the `intake.web_chat_session` row (the app role gains DELETE on it, migration 0211). The pre-code screen answers the 911 text, an opt-out (nothing listed) and INT-038's reply before the business check. `intake.web_chat_session.language` (migration 0211, `en`/`es`) keeps the first message's language code, never its words; `check_code` sends the consent text in Spanish when it is `es` (else the page's language) and, with Spanish conversations off, queues `spanish_not_yet` after it.
- Consent sweep (T563, D-3844, D-4280, D-4387, D-4418; CON-022, CON-035): the daily `intake.consent_sweep` (`intake::consent_purge`, registered by `server::register_consent_sweep`, first queued by the worker's `schedule_checks`, each run queuing the next day) takes `messaging::api::due_numbers` and the contacts in `intake.consent_phone_wait` (migration 0196). Per number it builds `messaging::api::listing_key` from `privacy::api::phone_digests` outside any transaction, then in one READ COMMITTED transaction calls `still_unlisted` first, `intake.consent_phone_due`, `purge_optout_events`, `intake.purge_expired_consent` (`SECURITY DEFINER`; the one cross-schema call, `messaging.last_message_at(`, listed in `CROSS_SCHEMA_CALLS`) and `delete_message_log`, writes one `consent_purged` `ops` audit row per deleted ID, and last `privacy::api::clear_consent_phone` (`FOR UPDATE NOWAIT`; a held row rolls the number back for the next day). A listed number keeps its phone (D-079); one with no key yet keeps it and waits in `intake.consent_phone_wait` (SELECT, INSERT, DELETE for the app role) until a run after the rotation. Section 3's `intake` row does not list that table yet (locked; listed in D-4387).
- First reply and consent text (T038, D-907 to D-909): `intake::api::on_text` takes an inbound text's IDs, flags and scrubbed words after `messaging` has handled opt-outs and HELP; a contact with no open `intake.conversation` gets one opened, in one transaction with its audit row, with the 911 text (on a 911-list match) and then the CON-031 consent text queued in that order (`Handled::texts`, the order the caller sends them), English unless the message reads as Spanish and Spanish conversations are on (CON-026); one open conversation per homeowner (partial unique index) and the outbox key make the consent text go once per request; every later reply is a conversation step (`rules::Then`), never a wait for a reply (CON-027, D-419). Migration `0053_intake_tables.sql` creates the seven `intake` tables of section 3 (D-493).
- Consent and terms records (T181, D-933, D-934): `intake::api::receive_text` is the entry point for every inbound homeowner text; it runs the first reply inside its own transaction and, when that text queued the consent text, writes the `intake.consent_record` row (channel `sms`, inbound message ID, time, consent-text version `<template>:<language>:<hash>`) before one commit (CON-005). `card_allowed` (CON-007) and `may_text` (CON-021) are the gates the card and send tasks call first. `record_terms_acceptance` stores one `intake.terms_acceptance` row per pick (document, version, SHA256 of the published text, language, channel, assent line, time, request, pick, and the inbound message ID for a text pick; migration `0054_intake_terms_acceptance.sql`, TERMS-016, TERMS-033); no reply ever writes either record. Planned by D-5848 (T856 to T863, T801): a request may be texted only with an `sms` consent record of its own conversation (`service::may_text_request`; `may_text` counts only `sms` records, for callers with no request in hand; `card_allowed` keeps any record for CON-007's web-chat card); every request text passes T856's guard (`intake::consent_guard`): an `sms` request to the outbox, anything else refused; page delivery happens only through web dispatch's own page function, and legacy callers on a `web_chat`-only request keep the outbox under the guard's chat branch until T801 deletes it; the web chat's request runs through the new `intake::web_dispatch` on the page with zero texts; an address she types in her own conversation is sealed in `privacy.conversation_email` (migration `0218`) for the pick code by email (PICK-029). Built by T856 (D-5890 to D-5893): `intake::consent_guard::request_text` (request, `TextKind`) answers `Delivery::Outbox` or `IntakeError::NoConsent`; `service::handle` takes `rules::plan`'s consent input from `models::sms_consented` (a request with no record at all, test-only, keeps "sent"); a carrier first text into a web-opened request locks the conversation row (`models::lock_conversation`, `FOR UPDATE`), queues the consent text under its own inbox ID and gets its `sms` record, also when a reply step answers it before the screen (a LIST, a close, a "<n> YES", a check-in or HELP-window answer: `replies::consent_first`, D-5893); the web chat's turns go through `service::receive_chat` and `replies::receive_chat_reply`, which never reach `receive_text`, `receive_answer` or `models::record_consent`; `open_verified` writes the `web_chat` record before its texts.
- The one 911 text (T152, D-973): `intake::api::safety_text` renders the INT-004 `emergency_911` template exactly (the Spanish one stays on while Spanish conversations are off), `safety_outgoing` gives the send path its quiet-hours view (`Kind::Safety911`, which QH-004 never holds) and `sent_in_time` checks the 5-minute limit (`SAFETY_WITHIN`). No safety-contacts file exists or is loaded (D-436): `tests/docs/test_no_phone_numbers_in_templates.py` fails the build on any phone number other than 911, any other N11 code such as 211, a utility name or "cooling center" in a text template or in any file under an `app/*/templates` folder.
- The 911-list screen and the emergency flow (T039, D-978 to D-982): `intake::api::receive_text` runs `intake`'s stem matcher (`emergency::check`, after street-address patterns are removed; `receive_answer` with `Asked::NameAndAddress` skips the address answer) first on every message and alone decides the INT-004 text (INT-026); a match is an `intake.emergency_event` row and holds the cards until SAFE (`safe_hold`, INT-005); a smoke or CO alarm said only to beep gets the INT-037 question. `answer_how_soon` stores the INT-030 answer and, on answer 1 or after a 911 match answered SAFE, offers the INT-006 choice (never while a 911 text waits for SAFE: `Answered::choice_after_safe`, then `offer_emergency_choice` after SAFE; answer 4 always asks the day; one INT-004 text per hold, D-982), at night after the INT-033 count from `businesses::api::night_count` (`emergency_count`); `answer_choice` stores it, and `release_emergency` enqueues one `intake.emergency_released` `core.task` for `quotes` once consent, SAFE, the emergency choice and the ZIP and area check are done, before the trade questions (INT-029); since T747 (D-4748, D-4836) one per job with a stored emergency card, its payload carrying `job` and its key `intake.emergency_released.<request>.<job>` (a request with none yet keeps the request-wide payload and key), and `answer_choice`'s emergency calls `jobs::api::mark_emergency` in its transaction for every job of the request, so `jobs.job.emergency` (false to true only, version and timer version bumped, timer queued again) means INT-029's chosen emergency for every reader.
- What opens a job and the under-18 reply (T040, D-993 to D-995): `intake::api::begin_job` is the one job-opening path (also the ALSO reply's second job, INT-032): it refuses a message of one or two words without an emergency keyword and any cancel-like message (INT-007, INT-008), keeps one active job per homeowner, property and trade (INT-009) and otherwise calls `jobs::api::create`; the job links are `intake.intake_answer` rows (no new table). `joining_job` gives the job a follow-up within the INT-010 window joins (the after-window rule is T042's); `record_answer` stores an answer only for an open request and on an exact word match (INT-011, INT-012); `stop_if_under_18` sends the one INT-038 reply (`under_18`, Spanish stays on) and closes the request, deleting its data under 13 (a text the consent guard refuses is `None` and the close and purge still commit, D-5982); `ask_name_address` asks the INT-027 question after the area check and `take_name_address` stores the answer in the vault only.
- Every job a request opened (T745, D-4748, D-5553, D-5647): migration 0213 adds `intake.request_job` (conversation, job, opened_at; IDs and a time only, SELECT and INSERT for the app role), written by `models::set_first_job` in the job-opening transaction and never dropped by a close (the `job.%` links still are), so `intake::api::jobs_of_contact` (FEE-013's same-customer check, PRIV-011's delete) and the retention purge see an INT-032 ALSO-reply job after its request closes; it lives as long as its conversation row, which no purge deletes. `intake::api::job_answers` (CARD-023) returns a job's own trade-question answers as question ID and code, never a contact answer; a request's later job stores them as `bank.<job, 32 hex>.<question ID>`.
- The keyword second opinion and the trade question (T042, D-998, D-999): `intake::matching` (pure) holds the keyword rules (`keyword_reading`: category, catalog job type, whole-word phrases, license-boundary flag; AI-011), `second_opinion` (both readings agree and the keywords name that trade or none, or a `TradeQuestion` offering every distinct trade, readings first, up to three, D-104), `TradeQuestion::read` (a lone number, "Not sure", or the whole words of exactly one option: its trade's keywords or its label's words, INT-012, D-103) and `step` (one re-ask with the same options, then the fallback: the keyword trade if exactly one matched, else the first reading, INT-015), `candidates` (the chosen trade's reading and keyword job types, `<trade>_other` with "Which fits best?" only when none, plus every license-boundary keyword job type, D-102, D-105, CARD-001), `two_trades` and `starts_second` (INT-032). T183 (D-1003): candidates across trades are INT-014's "different licenses" (no class in the license map covers two of the keyword trades), "water heater", "pool heater" and "spa heater" keep the catalog's licensed-only "water heater replacement" and "gas pool heater" as license-boundary candidates beside any other job type of their trade, "Which fits best?" always offers every licensed candidate, and `Candidates::fit_step` reads its reply (a number and words naming different options are unusable; a choice leaves that job type alone under its trade; "Not sure" or a second unusable reply keeps all). `rules::follow_up_joins` adds INT-010's after-window rule (`shares_words`, `JOIN_SHARE_PERCENT`). Wiring these into the conversation and the `two_jobs` text belong to the copy- and conversation-owning task (D-999).
- Intake order on texts (T671, D-4360, D-4428; INT-043): `intake::order_dispatch` is the one walker after the consent text, called last by `replies::reply_in` inside the reply's transaction; it reads the request's place from stored rows (no new column), opens the early first job with `jobs::api::create`, keeps the opening words through `quotes::api::keep_description`, and counts the coverage with `quotes::api::pair_coverage` (T716, D-4777, D-5333: the stored (trade, job type) pairs, each under its own trade's license rule) before `routing::tell_coverage`. Since T715 (D-4441) SAFE and an INT-037 answer go to the crate-visible `order_dispatch::ask_open_again` (the open question again, no row written), a trade answer opens its job through `open_job`, and step 11 waits for step 5's `trade_check` marker. Since T716 (D-4441, D-4602, D-5400) step 5 asks "Which fits best?" (`which_fits`) or, with no trade read, `trade_ask` before the coverage line, the keyword pairs are stored as `job_type.<trade>` step markers (codes only) and read back through `matching::stored_job_types_of`, and a short first text's scrubbed words are held under the request's own ID (`keep_description`) until the ZIP's turn moves them to the new job and deletes the held row (`quotes::api::purge_job_text`). The card send uses the same pairs (T716, D-5606): `intake::cards_out` calls `quotes::api::pair_pool_at` with `order_dispatch::send_pairs`, or `card_pool_at` with the stored facts when the request stored no pair.
- Refusals in the intake order (T776, D-5081, D-5178; LIC-017, LIC-018, INT-017): `intake::refusal_inputs` reads her kept words for a move that leaves Arizona (phrase, state and nearby-town lists); `order_dispatch::tell` passes that reading, her words and the candidate job types to `routing::route`, and `order_dispatch::refuse_card` runs the same check before a card is stored, shown or sent, a refusal going through `routing::apply` (no recruiting-demand row, D-1008).
- Photos in the intake order (T675, D-4360, D-5241, D-5242; INT-044, INT-045, SEC-041): `order_dispatch::questions` hands a finished trade-question set to `intake::photos::photo_steps` (step 9's photo ask with `catalog::api::photo_asks` and her `/h/requests/{job}/photos` link, built from `portals::api::PHOTO_UPLOAD_ROUTE`'s text since `intake` may not depend on `portals`; step 10's look questions in a `design: true` category, no concept image), which calls step 11. The inbound route (`server::inbound_text`) keeps only Twilio media SIDs of its own message, writes a `photo_pending` marker and queues one `intake.picture_text` task (payload: inbox ID, message SID, up to 3 media SIDs); the task (`intake::picture_text`, registered in `register_twilio_handlers` over `server::ServerPictures`, which rebuilds the URL from the configured account SID and calls `privacy::api::take_picture_text` with T794's `TwilioPictureMedia`) runs outside any held transaction, then drives step 9 under the homeowner lock. A request with no job holds the picture (re-queued every 15 minutes, at most 72 hours). Every provider delete there goes through `PictureSource::discard`; a false answer queues one `intake.picture_delete` task per media (T783, D-5843), retried by the queue and dead-lettered after its last attempt.
- Pick review in her language (T589, D-4052, D-5492; PICK-016, PICK-049, TXT-039, CON-026): new `intake::job_language` gives `intake::api::job_language(db, job)`, the language of the request holding the job (`models::request_of_job`, `service::request_language`) and Spanish only while `messaging::api::spanish_switch` is on, English when no request holds it. `portals::pick_flow`'s review views (`review`, the unticked-share refusal and the keyless final Pick) call it and `businesses::api::public_names` for the bound business; a failed read keeps the English page with the generic share wording. `result_page` stays English.
- Text pick from her phone (T728, D-4727, D-5646, D-5732; PICK-015, PICK-016, PICK-031, TERMS-016, INT-002): new `intake::text_pick_reply` is called by `replies::in_request` after the close by text and before the name-and-address answer; a clear "<number> YES" whose ID is a `messaging.inbox` row (`messaging::api::inbox_message`, so web chat never picks) in a request with a live job goes to `intake::api::answer_text_pick` (a savepoint in the reply's transaction) and ends as `Reply::Picked`. New `core::homeowner_terms` holds the one `include_str!` of `docs/legal/homeowner-terms.md` (`core::api::homeowner_terms() -> (version, text)`); `server`'s `pick_code_keys` and the text pick both read it.
