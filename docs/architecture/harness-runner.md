# Architecture: the runner

Moved here verbatim from `docs/architecture.md` (D-6022), whose index lists every part. Until T885 makes `docs/architecture/` a shared path, a task adds new notes to the index, at the end of the section this part came from, and the next plan change moves them here.

Section 7's "The runner's logic" paragraph, then section 12's bullets about the runner's cycle, in their original order.

**The runner's logic** is `runner/`: `state.py` (the real `kit/state.json` shape: list of tasks, one lease per lane in `leases` with lane "1" mirrored in the top-level `lease`, `lanes` from `kit/runner.json`, 1 unless a logged plan change sets more (5 since D-5554, 7 from D-3269), D-515; a task in flight occupies its lane, by its live lease or, once MERGE_PENDING, by its own `lane` field, `in_flight`, D-620; claims, each reserving the task's block of decision numbers `decision_ids` above `main`'s highest entry, the state's `next_decision` and the entries on the head of every open plan or harness pull request (`GitHubEnv.open_plan_decision_numbers`: `claude/` branches that are not task branches, D-1144), D-530; eligibility, backoff; `sync_graph` adds new graph tasks and copies a `deps` list a plan change altered onto every entry not yet DONE or SKIPPED, so eligibility and the lane check read the same dependencies, D-1126), `verify.py` (path check: a changed `app/<crate>/NOTES.md` is shared exactly when that crate's `CLAUDE.md` is, D-3474, T437; model check from session records, the DONE check), `outbox.py` (outbox files, the account checkpoint and other owner gates, Gate P), `cycle.py` (one cycle, with git, GitHub and the worker session behind the `Env` protocol; inbox files are acknowledged only after the state recording them is pushed; lease renewal and the final lease release go through `update_state`, which re-reads and retries a lost race, D-515; an empty hand-in, with no commits on top of `main`, never waits for a pull request GitHub will not open: a cleanup task's resolves to DONE or to BLOCKED for its stage proof once `main`'s checks on that head are known green, and fails if they are red or stay unknown for 4 hours, and a task left MERGE_PENDING on one heals on the next cycle, while any other task's, or a hand-in with no task branch, is a failed attempt, D-551) and `proof.py` (the stage proofs the runner records itself from a green nightly run that contains every merge of the stage and the row's tests with no skip path, stage 1 only, D-551). A conditional gate (the real-texts question) clears on a short 'yes' or 'no', records `answer`, and `cycle.py` hands it to dependent tasks as `gate_answers` in the task file (D-552, D-553). The scheduled session supplies the real `Env` (`github_env.py`); `tests/test_failure_drills.py` supplies a fake one. The start-routine smoke test builds on the job's cached `target` (`CARGO_TARGET_DIR`), gets `SMOKE_TIMEOUT` (540 s; since D-2560 the in-session smoke runs detached within `PRE_SMOKE_TIMEOUT` and each call waits up to `SMOKE_WAIT`, 450 s, see section 12), and a timeout is recorded (`smoke_runs[].timed_out`), claims nothing, never counts as a D-498 strike and never sets `main` red, with one outbox note after three on a head (D-1178); the job's Rust build cache is keyed per commit so each run that may save leaves a fresh snapshot (D-1178). When a required check fails on a task's pull request, the failure the retry worker gets (`last_failure`) names each failed check, then, for each check's latest Actions job, its failed steps and the last 15 lines of the failed step's log, read through the jobs REST API with the job token (`RUNNER_CHECKS_TOKEN`, as for check runs) and kept to 1,500 characters; the step's command and `env:` block are left out, and on any API error the failure is the plain list of failed checks (D-582). When the log cannot be downloaded or holds no error line, the reason (the `gh` exit code and the first 200 characters of its stderr, redacted) goes to the cycle log and the check run's failure annotations (`path:line: message`, read with the same job token) stand in for the log lines (D-1263). Before every attempt the runner makes the local task branch itself (`prepare_branch`): from `main` on a first attempt; on a retry whose earlier attempt pushed the branch, from origin's tip with `main` merged in by a normal merge commit (`git merge-tree --write-tree`), so the new commits go on top and the push fast-forwards; an open pull request on a continued branch that has auto-merge on is closed with a comment first (its number kept in the task's `runner_closed_prs`, so later attempts still continue the branch), so no push of unreviewed work can merge, and the runner opens a fresh one after its review; when that branch's pull request was closed or merged by anyone else, cannot be read, or `main` does not merge cleanly, from `main` under a new name `<branch>-a<n>` recorded as the task's `branch` (on a conflict the old pull request is closed through REST with a comment; the old branch stays). Whether origin has a branch is asked with `git ls-remote --exit-code`, and a pull request is closed only while the attempt holds the lease. The hand-off carries `branch_ready`, `base` and a `branch_note` telling the session to switch to that branch and never recreate it, `--after` refuses a hand-in that does not build on origin's branch, a push rejected as not a fast-forward is a failed attempt rather than a credential block (the attempt's history and usage kept either way), and a pull request head that is not the task's `reviewed_sha` is never trusted unless its tree is exactly the clean automatic merge of the reviewed commit with the `main` commit the head is based on, never older than the reviewed commit's own fork point from `main` (`reviewed_plus_main`, which accepts GitHub's "Update branch" by merge or by rebase and rejects a new commit, a merge of anything else and a merge that adds content of its own; the reviewed commit is fetched first). Unmerged and not trusted, it fails the attempt instead of waiting forever for an auto-merge the runner refuses, and when auto-merge is on the pull request is closed first (with the `DROP_MARKER` comment and recorded in `runner_closed_prs`) so GitHub cannot merge that head; if the close fails, or a second read shows GitHub merged it just before the close, the task stays MERGE_PENDING so any merge is judged. A trusted updated head merges only if auto-merge is already on; with it off, the attempt fails. Merged and not trusted, the task is BLOCKED and `main` is red with check "review", so FIX-MAIN reverts it and the task then returns to the queue; a merged head git cannot place waits at most 2 hours (`HEAD_CHECK_WAIT`), then the task is BLOCKED with an outbox item for a person. A branch's earlier pull request never judges an empty hand-in whose head is already on `main` (D-584). After a session dies, only an open (or merged) pull request whose head is the reviewed head of that very attempt (its `review_lease`) is adopted as MERGE_PENDING; a closed, runner-closed or unreviewed one leaves the task for its retry (D-584). **A dead worker's lease (D-3417).** A lease is freed on expiry (`state.release_expired`) or, earlier, when its session is a backup-runner run (`actions-<run id>`, not the cycle's own) whose latest attempt GitHub reports `completed` for at least 10 minutes (`cycle.dead_sessions`, `GitHubEnv.run_status`, `state.release_dead`); both go through `_release_lane` in the same state write, so attempts, `stale_leases` and orphan adoption are the same, and any doubt (an API error, a running re-run, an unparsed answer) keeps the lease. No run is ever cancelled. `python3 -m runner --requeue T### --reason TEXT` moves a task BLOCKED by something outside its own work (a rejected push, no head, a permission block, a missing stage proof, an unchecked merge) back to QUEUED, with `attempts` unchanged (never past the 3-attempt cap) and the reason appended to its `last_failure` (D-584); it acts only while no lease is live, and records the re-queue in the task's `requeues` list (D-583); for FIX-MAIN it acts only while `main` is red and FIX-MAIN is BLOCKED, and restarts it with `attempts` 0 (D-1099), while `--plan-fix` still refuses FIX-MAIN. A FIX-MAIN BLOCKED for any reason while `main` is red is retried by the red-main step itself (`blocked_fix_main`, D-1099): the cycle that first finds it BLOCKED stamps `blocked_at`, at least 30 minutes later (`FIX_MAIN_COOL_OFF`) it is QUEUED again with `attempts` 0, `owns`, `revert_sha` and `offending_task` kept, the retry recorded in its and `main_red`'s `fix_main_rounds`, every earlier failure added to its goal and one `info` outbox item written per retry; after 3 retries (`FIX_MAIN_ROUNDS`) it stays BLOCKED with one `blocked` outbox item naming the files, the revert SHA and `--requeue FIX-MAIN`. A smoke run still red after FIX-MAIN's revert merged leaves FIX-MAIN DONE with one `blocked` outbox item (`revert_landed_red`), and each later cycle smoke-tests the head again; a retried or re-queued FIX-MAIN no longer counts as not started for the D-498 false-red withdrawal, and `main` stays red until a verified green run. That green run counts a failed attempt against the blamed task only when FIX-MAIN actually reverted it (`cycle.fix_main_reverted`, D-3752): FIX-MAIN's merged `files` include one of the offending merge's own paths (its files not under a shared path; with none, any of its files but `docs/decisions.md`), or either list was not recorded (the safe side); a FIX-MAIN that merged only shared paths or was an empty hand-in leaves the task as it was, and the `main_red_history` record says `outcome` (`reverted` or `fixed_otherwise`) and `fix_files`. The one way past the cap is a plan fix (D-677): `--requeue T### --plan-fix D-### --reason TEXT` gives a task that used all its attempts exactly one more, on Opus, only when, measured from the start of its last attempt (its `started_at`, else its `ended_at`, `cycle.plan_since`), D-### is in `main`'s `docs/decisions.md` and in the task's own `decisions` list (`verify.task_decisions`) now but in neither then, and the task's plan fingerprint (`verify.plan_fingerprint`: its `kit/tasks.json` entry and its prompt) differs between `main` then and now (`GitHubEnv.plan_evidence`); once per decision, never under a lease that matters, with `plan_fix`, `plan_since`, both `main` commits and both fingerprints kept in `requeues`. The same command brings back a task whose worker reported a plan gap (D-2859): a worker that finds the task cannot pass without a change the plan forbids it (a file or test owned by another task, two lines that contradict, a budget it cannot fit) opens its report with `PLAN GAP: <file:line> <owner or contradiction> <smallest plan change>` (`kit/prompts/TEMPLATE.md`), and the session hands in with `--outcome plan_gap` once its reviewer confirms the cited ownership or contradiction, passing `--log` through a quoted heredoc. `cycle.session_outcome`, run only by `--after` on the session's own `--log` (a RUNNER_WORKER_CMD result file reports its outcome itself), also turns a `tests_failed` into `plan_gap` when the log opens with the marker, or when its first sentence (up to the first ". " or line end) says "a/the plan change must" or "<T###, it, this task, the task, or ; : ,> needs a plan/harness change, task or fix" (or "needs plan/harness fix") with no hedge in that sentence (`PLAN_GAP_HEDGES`: not, no, never, n't, but, thought, think(s), if, whether, maybe, might, goal, says, said, a quotation mark or backtick). `cycle.record_plan_gap` counts the attempt and sets the task BLOCKED at once with a reason opening `plan gap reported`, which STATUS.md lists under "Needs attention", and writes the outbox item `T###-plan-gap` (as D-1869's owned gap does); `--plan-fix` lifts it after the plan fix with the attempts it has left, and a plain `--requeue T### --reason` lifts a mistaken block while attempts remain (the attempt stays counted; at the cap only D-677 applies), so the task is never claimed again on the prompt that could not pass. A pull request is closed before it is commented on, and the auto-merge closing comment carries a marker, so a later attempt still recognises a pull request the runner closed when recording it in `runner_closed_prs` was lost (D-584). **Lanes (D-620).** `runner/lanes.py` decides where a cycle may claim: at most `lanes` tasks in flight (1 while `lanes_fallback` is set), a backup-runner run claims only on the lane its gate picked (`RUNNER_LANE`; `run_lane` in `state.py`: for a merged pull request's run, that task's own lane whenever it holds no live lease, since the merge frees it, D-723; otherwise a lane with no task in flight, the event's task's own first, then a lane with no live lease, else lane 1; only lane 1 while `lanes_fallback` is set), and a task is claimed only with every dependency of its `kit/tasks.json` entry DONE or SKIPPED, checked with both lanes free too (a proof-waiting cleanup task of its own stage counts then, D-551; D-1127), and beside a task in flight only in the same stage, with no owned path overlapping (a task owning a locked file also owns `kit/plan.lock`), and never a cleanup task on either side; FIX-MAIN is exempt, and while `main` is red nothing else is eligible on any lane. Every MERGE_PENDING task is resolved each cycle; a waiting or failed result ends the cycle only on the run's own lane, so a run serving a free lane still claims. Pacing counts the recorded estimate of every other IN_PROGRESS task as used (`in_flight_tokens`); the plan usage the action reports about itself (its `rate_limit_event` messages, the last one kept from its execution file by the job step `python3 -m runner --usage-reading`, `runner/usage_reading.py`) is `usage.session_reading`, which pacing uses for the windows it holds while under six hours old, after a probe reading and before the ledger (D-1155); with `spread` in `kit/pacing.json` the week's spend is held to a straight line from an anchor reading to the effective budget a few hours before the reset, a claim above the line waiting until the line reaches it (`spend_line`, D-1128; `spread` is absent since D-1189, so the pacer claims whenever the task fits the five-hour and weekly budgets, and putting `spread` back restores the hold; a null `budget_tokens_five_hour`, as since D-3056, leaves the five-hour window out of that test, the standing and the projected finish, while a real reading at 100% for any window still holds the claim until its reset, `budgeted` and `at_limit`), and `kit/runner.json` is back to `lanes: 1` (D-1128). While `main` is red no pull request but FIX-MAIN's gets an update merge or auto-merge, and when no numbered lane can take FIX-MAIN (tasks that guard holds fill them, or a fall back or a lower `lanes` cut the capacity) it takes the reserved "fix" lane, which never counts against `lanes` (`lanes.fix_lane`); a cycle with no lane to claim on still runs the red-main step, so a finished FIX-MAIN always clears `main` (D-630). Two harness-type failures in a row on a lane above 1, each an attempt that ended (a rejected branch push, an attempt that lost its writes, a required check that failed on an update merge after the same check passed on the reviewed head it started from, judged on that head's final conclusions, read again when they were still running at the update (`checks_on`, D-630), an update merge that conflicted or whose third push was rejected), set `lanes_fallback`, write an outbox item and keep the runner on one lane until `python3 -m runner --restore-lanes`; a task on that lane reaching DONE or failing for its own work clears the strikes. With two or more lanes a lost race is tried again from a fresh read, `lanes - 1` times and at least twice, after a random wait of 1 to `1 + 2 × lanes` seconds (hand-off mode only), and a storm that outlasts the retries ends the run `lost_race`, a strike only when origin's state and lease refs did not move meanwhile (`raced` over `GitHubEnv.state_refs`: then every push failed for another reason), else contention and no strike (`lost_race_retries`, D-3269), and the run's report names the free lanes a task could be claimed on (`refill`; none while the pacer's last decision is a wait still ahead, D-723, or while `main` is red, D-3140, and none for a task a claim has marked `plan_gap` that the check still refuses, D-3812), from which `backup-runner.yml`'s chain step starts one run per lane after a result that moved a task, or a row whose `changed.tasks` shows a task moved, such as a run whose own lane still waits but which resolved another lane's merge (D-723), and every run that ends starts those runs at once itself, whatever its result (a hand-off, a hand-in, a run whose own lane waits on its merge, a requeue), unless it is a `REFILL_STOP` result, one that claimed nothing or changed nothing, so a run that claims nothing never starts another; a bookkeeping row (a usage reading, the keeper's record) follows its job's last row that tells and starts only the lanes that row did not (`refill_starts`, `job_row` over `GitHubEnv.read_cycle_log`, `start_refill`, `GitHubEnv.dispatch_lane`, `gh workflow run` with the job token `RUNNER_CHECKS_TOKEN`, D-723, D-3140; the row records them in `dispatched`, which the chain step does not start again), so a freed lane never waits for a worker's whole session (the chain step reads this job's own last row that did something; `--after` removes the hand-off once it finished the task, so the safety step adds no empty row); the chain step also starts the next cycle at once after this job's `smoke_timeout` row (an in-session smoke past `SMOKE_TIMEOUT` or this job's pre-session smoke past `PRE_SMOKE_TIMEOUT`, D-2028) when it is the first timeout on that head (the row's `changed.keys.smoke_runs` holds one `timed_out` run for the last run's SHA), since "Smoke build cache, save" has already kept the partial build; a second timeout on the same head waits for the keeper, so it chains at most once per commit of `main` (D-1970); finish's last write lays on only its own `usage` delta (a pacing window that rolled over keeps only the newer window's tokens, D-630) and its lane's strikes; `--requeue` with two lanes waits only for a lease on the task itself or on a task that could not run beside it; the hourly tick dispatches one run per lane without a live lease; the backup job's concurrency group is per lane (lane 1 keeps `backup-runner`). STATUS.md lists every lane's lease. **Plan-change numbers and plan gaps (D-1058).** `python3 -m runner --reserve-decision --reason TEXT` (`reserve_decision` in `runner/__main__.py`, `state.reserve_plan_number`) gives a change made outside the runner one D-number from the live counter through `update_state`: the first at or above `next_decision`, above `main`'s highest entry and above every reserved number, kept in the state's `plan_reservations` ({number, at, reason, session}, which `_reserved` and `scripts/check_state.py` count as reserved) with `next_decision` moved past it; refused with an empty reason or an unreadable `main` file. A submitted attempt whose only problems are files its plan did not list (`not owned by T###`, `cycle.plan_gap_failure`) goes back to QUEUED with `attempts` unchanged and one entry in the task's `plan_gap_strikes` ({at, paths, attempt}), its history entry marked `plan_gap`; a second such failure, one beside any other problem or a failed test run, or one on a task at the attempt cap (its plan-fix attempt) counts as an attempt. **FIX-MAIN keeps the log (D-1088).** Its goal (`_fix_main_fields`) tells the worker to revert the squash commit and then restore `docs/decisions.md` from `main` before appending its own entry, because a plain revert removes the reverted task's entries and fails the append-only rule. **Decision entries in order (D-1029).** When a retry's earlier pushed branch (`prepare_branch`) or a submitted hand-in (`collect_result`) has `docs/decisions.md` entries inserted before its merge base's last entry, as a worker holding a lower reserved block does when a plan change took a higher number, `UpdateMerge.in_order` (`runner/update_merge.py`) commits on top of it the base's file followed by the new entries in the branch's order, so `scripts/check_pr_change.py`'s append-only rule passes; a changed or removed entry is left alone and still fails. **Keeping pull requests current (D-620).** When a MERGE_PENDING task's pull request head is its reviewed head and `main` is not in it (behind, or conflicted), `GitHubEnv.update_branch` merges `main` in itself: a normal merge commit (reviewed head first, `main` second, dated at `main`'s commit so two runners make the same commit), pushed as a fast-forward only while origin's branch is still the reviewed head, never rebased or forced. Its tree is `UpdateMerge.tree` (`runner/update_merge.py`): `git merge-tree --write-tree`, with `docs/decisions.md` as `main`'s text then the lines the branch appended (whatever the union driver did; a branch that edited old entries or reused a number `main` has is a conflict) and `kit/plan.lock` recomputed by `scripts/check_plan_lock.py` when both sides rewrote it, each side's lock matched its own tree and neither side changed that script; a conflicting `docs/for-casey-review.md`, `docs/architecture.md`, `Cargo.toml`, crate `app/<crate>/CLAUDE.md` or crate `app/<crate>/src/api.rs` (the last two since D-3269) is resolved only when every conflict in it is a pure insertion on both sides at the same place (`git merge-file --diff3` shows no base line between them), keeping main's block then the branch's, a block after a new section opening its own, no side holding a line shaped like a 40-character conflict marker, a resolved `Cargo.toml` that still parses with no inserted dotted key and no locked section of `docs/architecture.md` that is neither side's (D-891); a resolved crate `CLAUDE.md` must pass `scripts/check_code_docs.py`'s `check_crate_doc` (120 lines, the six headings), as must any crate `CLAUDE.md` both sides changed that git merged cleanly (`_docs_broken`), no non-blank line may be inserted by both sides into a crate file, a Markdown table row may not meet a non-row across the join in any resolved file, and a resolved `api.rs` only when every inserted line is a one-line `pub use`/`pub mod` re-export, no name is exported twice, and `rustfmt` leaves the file unchanged (D-3269); any other conflicting path, or a check that fails or cannot run, is a real conflict. `prepare_branch` merges `main` into a retry's branch with the same tree, and a new review drops the attempt's `update_merges`. `enable_auto_merge` waits up to 30 seconds for the pull request to show a just-pushed head, and update pushes use `RUNNER_PUSH_TOKEN` like any task-branch push. The merge commit is checked against that tree before it is pushed, then becomes the task's `reviewed_sha` (recorded in `update_merges`), so `_merged`, the unreviewed-head path and auto-merge treat it as reviewed; `reviewed_plus_main` uses the same tree. A head that is an update merge of the reviewed head (parents exactly the reviewed commit and a commit on `main`, that tree) is adopted as reviewed when the record was lost, and a PR still showing an earlier reviewed head just after an update waits. A real conflict is resynced on the same attempt (D-891): a PR with auto-merge on is closed first (as for an unreviewed head; a failed close keeps the task MERGE_PENDING), the task goes back to QUEUED with `attempts` unchanged and a `resync` record (attempt, reviewed head, main, paths; kept in `resyncs`), the next claim on any lane takes it first, `prepare_branch` makes the branch at the reviewed head without `main` merged in (only while origin's tip is still that head and its PR was not ended by someone else), and the worker, told only to merge `main` in and resolve (`resync_log`, the hand-off's `resync` and `branch_note`), hands in through the normal path check, fresh-eyes review, review record, push and auto-merge; its history entry carries `resync: true` and `plan_since` skips it. A crashed resync re-runs like any crashed attempt, and one whose reviewed merge origin already holds drops its `resync` and goes on normally. A resync that cannot start on the reviewed head, fails, or a conflict after 2 resyncs in the attempt (`RESYNC_LIMIT`) fails the attempt, and the retry starts from the branch through `prepare_branch` (`main` merged in, or fresh on `-a<n>` when that still conflicts, D-583); rejected update pushes fail the attempt after 3, and an update git cannot make waits at most 2 hours (`UPDATE_WAIT`). This works with one lane too, for a `main` moved by a person. **The hand-in merge (D-2798).** When a hand-in's reviewed head is already behind `main` at the push, `finish` (`cycle._hand_in_merge`) asks `GitHubEnv.hand_in_merge` for the very update merge stage C would build later (`_built_update`, shared with `update_branch`: `UpdateMerge.commit` checked by `is_update_merge` against the reviewed head and `main`'s head; same tree, parents, message and dates), and the review record adopts it in the same write (`_adopt_update`, `how: "hand-in"`, `from` the reviewed head), so the state names the pushed head before the one push carries both commits and only the merged head's checks run; auto-merge, the PR-head check and crash adoption see one reviewed head. Not behind, `main` red (for any task but FIX-MAIN, checked before the build and again in the review record's write, as stage C refuses an update merge then), a conflict, a failed tree check, a git error, a dry run or an `Env` without the method push the reviewed head unmerged as before, and stage C (and its resync) handles it; `main` moving again during the checks is stage C's as always. The pre-hand-in gate still runs on the reviewed head. A red check on such a merge neither strikes its lane nor clears the lane's strikes (`_unjudged_hand_in`: there is no earlier round on the reviewed head to compare, so `_earlier_of_failed` cannot judge it). Likewise a red check whose earlier results on the reviewed head hold no `success` and at least one `cancelled` (a run cancelled on a superseded head) neither strikes nor clears (D-5601). **Claim order (D-2540).** A cycle tries the claimable ids (eligible, by day, compatible with the lanes) in the order `cycle.claim_order` gives: a resync first (D-891), then the ids `kit/runner.json` lists in `claim_first` (read by `runner/__main__.py` `claim_first`, `()` when missing or malformed), in the list's order, then the rest in state order; only the order changes, so a listed id that is not claimable is ignored and plan health and pacing still judge each candidate in turn. With `"order": "critical_path"` in `kit/runner.json` (D-2591; read by `runner/__main__.py` `claim_order_setting`, `"state"` when missing, malformed or any other value) the rest are tried longest chain first: `cycle.chain_lengths` counts, for each plan task, the tasks on its longest chain of dependents not DONE or SKIPPED, itself and gate tasks included (memoised, iterative, a malformed cycle cut where it closes), and state order breaks ties; removing the key restores the state order. With `"prefer_disjoint_crates": true` in `kit/runner.json` (D-3082; read by `runner/__main__.py` `prefer_disjoint_crates`, false when missing, malformed or anything but `true`) one more key comes after the chain and before state order: an id that owns a path in an `app/` crate that a task in flight (a live lease or MERGE_PENDING, `state.in_flight`) also owns (`lanes.crowded`, crates from `lanes.crates`) is tried after the ids of equal resync, `claim_first` and chain rank that share none, since both would update that crate's `CLAUDE.md` and the later one would need a resync (D-891). It never drops an id, so when every candidate shares a crate the claim is the same as before and every lane still fills; setting it false restores the order without it. With `"exclusive_crates": true` (D-3269; read by `runner/__main__.py` `exclusive_crates`, false when missing, malformed or anything but `true`) the preference becomes a refusal: `cycle._exclusive` runs `lanes.exclusive_ids` over the ordered ids, which drops an id that writes an `app/` crate (`lanes.task_crates`: its owned paths under `app/<crate>/` and its `module`) already written by as many tasks in flight as the crate's limit (`lanes.crate_clash`; never the task itself, so a resync of the task holding the crate is not blocked by it; FIX-MAIN exempt). The limit (`lanes.crate_limit`, D-3303) is `"crate_cap"` (read by `runner/__main__.py` `crate_cap`; 1, D-3269's hard exclusion, when missing, malformed or below 1; 2 since D-3303), but 1 for a crate whose `app/<crate>/CLAUDE.md` on origin's `main` (`crate_doc_text`: `git show origin/main:...`, else the runner's checkout), counted in lines plus the tasks in flight in it, reaches `scripts/check_code_docs.py`'s `MAX_CRATE_DOC_LINES` (120), or whose UTF-8 bytes plus `(held + 1) * CRATE_DOC_TASK_BYTES` (400) pass `MAX_CRATE_DOC_BYTES` (8,192; D-3474, T437; the line rule alone when the check lacks those constants), read at each claim (`crate_doc_full`; a missing file counts as full), since each task adds at least a line or bullet and another cannot fit there. When the highest-ranked id is refused only for that, its crates are reserved for it: no later id may take the last free slot in one of them (`lanes.takes_last_slot`; with a limit of 1 that is any id writing one), so narrower tasks cannot overtake it for ever.
