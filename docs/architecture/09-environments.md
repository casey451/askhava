## 9. Environments and deployment shape

| Environment | Where | Data | Adapters | Keys |
|---|---|---|---|---|
| Build | Cloud session VM, local PostgreSQL 16 | Fake only | `stand_in` | None in Phase 1; sandbox network secrets in Phase 2 (`BUILD_BRIEF.md:296`) |
| CI | GitHub Actions, Postgres service container | Fake only | `stand_in` | None (`BUILD_BRIEF.md:517`) |
| Test | Railway **test** project | Fake only | `sandbox` | Test keys in test-project variables |
| Live | Railway **live** project | Real | `live` | Live keys entered by Casey at Gate C |

(`BUILD_BRIEF.md:512`–`BUILD_BRIEF.md:521`.) "Railway" means the host chosen per the changes file (OPS-012, D-024). In CI the check workflows `ci.yml` (`Ci`), `twin.yml` (`Twin`) and `a11y.yml` (`Ally`) start only on a push to `claude/**` or `dependabot/**` (never on `pull_request`), so each head commit gets exactly one run of each and one `governance.yml` run after its `ci` run; `governance.yml` publishes nothing for a head whose pull request has already merged (D-1087).

Each Railway project has four services: `web`, `worker`, `migrate` and PostgreSQL 16 (plus, from T648, a throwaway PostgreSQL 16 service on the private network that only the monthly test restore reaches, through `ASKHAVA_RESTORE_ADMIN_URL`, D-4293), plus its own phone numbers, webhook endpoints, `VAULT_KEY`, `VAULT_INDEX_KEY`, `ID_SECRET`, storage bucket and vendor keys; nothing is shared between test and live (SEC-003). The test project auto-deploys from `main`; the live project has auto-deploy off and deploys only when Casey presses Deploy (OPS-022; `sources/01_spec/Changes_Since_v9.3_AUTHORITATIVE.md:305`). Live deploys from a protected `release` branch Casey moves to the signed SHA (OPS-043). Claude never holds a hosting key. Migrations run on a separate `migrate` service (`server migrate`, restart Never), the only holder of `ASKHAVA_MIGRATION_DATABASE_URL` and the bootstrap token; it deploys before `web` and `worker`, and each migration keeps the previous release working (SEC-052, D-491). Settings live in the `docs/deploy.md` table, never a `railway.toml` (OPS-050); `web` and `worker` restart On Failure and exit after 3 minutes of failed liveness (OPS-049); never roll back past a key rotation (OPS-054); the roles themselves are created once per cluster by `scripts/bootstrap_roles.sql` (T012; its timeouts and grants, D-699; T109 adds `askhava_backup`, holding `pg_read_all_data`, which the nightly export connects as through `ASKHAVA_BACKUP_DATABASE_URL`, D-4293), never by a migration, and `scripts/smoke.sh` and `Ci` create `askhava_app` and `askhava_migrator` before any migration. Migration numbers are frozen from the first deploy to the test project: sqlx refuses a renumbered applied migration, so a later migration may have a lower number but an applied one never changes (D-491). The live project serves askhava.com through Cloudflare DNS, every hostname DNS-only at launch, webhooks on `hooks.askhava.com` (SEC-053, SEC-054); the test project uses only its own host-provided domain.

The monthly test restore (T648; OPS-013, OPS-051, D-4846): `recovery::api::register_restore` handles `recovery.test_restore`, first queued by `schedule_restore` for 12:00 UTC after the next nightly export and then a month on (one per calendar month by dedupe key). A run has 100 seconds in all (`RESTORE_DEADLINE`, under the worker's 120-second handler timeout; create to check stop at 70 seconds, the drop ends by 90, every tool and the check connection has a 10-second connect timeout, and a run cut off is recorded as `timeout` and alerted): a database it creates on the throwaway service, `scripts/bootstrap_roles.sql` (embedded) through `psql`, `pg_dump -Fc` piped into `pg_restore --single-transaction`, the owner and append-only grant check, the database dropped, then the newest export row checked (ok, within 26 hours, size and hash). Each result is a `recovery.backup_check` row of kind `restore` with a `recovery.restore_passed` or `recovery.restore_failed` audit entry; a failure raises one High `recovery.test_restore_failed` alert, which is not a safe-mode kind. The worker refuses to start in test and live without `ASKHAVA_RESTORE_ADMIN_URL`.

The nightly export's failure alert (T781; OPS-013, PRIV-029, D-5081): an export run that ends not `ok` (any failure, including `timeout` past `EXPORT_DEADLINE`) raises one High `recovery.export_failed` alert through `ops::api::raise_alert` in the same transaction as its `recovery.backup_check` row, unless an earlier failed export row started the same Arizona day (by the injected clock), with no subject; it is not a safe-mode kind. A stored export raises nothing.
