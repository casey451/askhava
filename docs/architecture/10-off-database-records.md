## 10. Off-database records and recovery

Written as they happen to the `storage` adapter (OPS-010, OPS-011; `sources/01_spec/Havasu_Home_Quotes_Technical_Blueprint_v9.3.md:690`): the audit stream, the web request log (request IDs, routes with tokens redacted, status codes) and the AI structured readings. With Twilio's and Stripe's own records, they are the replay inputs after a restore (OPS-015 to OPS-019). The nightly encrypted export (`pg_dump -Fc`) goes to the same bucket under a separate key, kept 30 days (OPS-013); a restore runs the role bootstrap first (OPS-051). The export is `recovery`'s nightly `recovery.nightly_export` task (T109): `pg_dump -Fc` as `askhava_backup`, encrypted with `age` to `ASKHAVA_EXPORT_RECIPIENT` (no private key on the host), stored as `exports/<date>/<task>.age`, each result one `recovery.backup_check` row and one `ops` audit entry that `ops::api::latest_audit` reads for the owner health page. Point-in-time recovery comes from the host (OPS-012).

The replay's helpers (T481, D-4005): `messaging::api::replay_window`, `replay_match` and `mark_replayed_sent` match unsent outbox rows to Twilio's sent log inside `messaging` (windows `CLOCK_SKEW` 5 minutes, `NO_BODY_WINDOW` 10 minutes) and answer row IDs only; `payments::api::rebuild_charge` books a lost Stripe charge through the success path, never calling Stripe. The replay itself is `recovery::api::replay` (T110, D-4841, D-4842): charges from `CHARGE_MARGIN` (10 minutes) before `charges_since` through any `ChargeSource` (every `payments::api::ReconcileStripe` client) into `rebuild_charge`, then each sending number's Twilio sent log (`adapters::api::SmsSentLog::list_sent`: `From`, `DateSent>`, `DateSent<`, `next_page_uri`, never a key) into `replay_match` and `mark_replayed_sent`; a vendor it cannot reach is retried (`Retry::STANDARD`, ten calls a minute apart); each run is one `recovery.replay_run` row, with ambiguous or refused texts and unmatched or refunded charges as `recovery.replay_item` rows (IDs only) for Casey; it sends, charges and refunds nothing (D-3889). `recovery.restore_drill` (migration 0199) holds one row per drill for T206.

The restore drill (T206; OPS-013, OPS-018, OPS-019; D-3889, D-4932, D-4971): `server replay <plain-dump-file> <export-object-name> <backup-time>` calls `recovery::api::run_drill`, which runs `pg_restore --single-transaction --exit-on-error` of an operator-supplied, already-decrypted dump into the fresh database behind `ASKHAVA_MIGRATION_DATABASE_URL` (roles made first by `scripts/bootstrap_roles.sql`), then the replay there. The host never reads an export back and never holds an `age` identity: fetching the object and `age -d` are the operator's steps. While Twilio or Stripe is unreachable the whole replay is run again (`Retry::STANDARD`: ten replays a minute apart, each call itself retried ten times), never guessed. Each drill that restored is one `recovery.restore_drill` row; a replay that listed anything in `recovery.replay_item` raises one High alert `recovery.replay_items_listed` about its `recovery.replay_run`, and a drill whose replay never passed is recorded `failed` with one High `recovery.test_restore_failed` about the drill row. The replay moves no money: an unmatched charge is refunded by the nightly reconcile (FEE-032).
