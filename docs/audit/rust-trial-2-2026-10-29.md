## 1. Two database roles (D-092)

**Built:** `tools/bootstrap_roles.sql`, run outside migrations by a superuser through psql with `\getenv` for the passwords. It:
- uses a `DO $$ … IF NOT EXISTS … CREATE ROLE` block for `askhava_migrator` (LOGIN NOINHERIT) and `askhava_app`;
- sets the passwords and the app role's timeouts with `ALTER ROLE`;
- grants `CONNECT, CREATE ON DATABASE` to the migrator;
- runs `REVOKE CREATE ON SCHEMA public FROM PUBLIC` and `GRANT USAGE, CREATE ON SCHEMA public TO askhava_migrator`;
- on test clusters only (`-v test_cluster=1`), adds `ALTER ROLE askhava_migrator CREATEDB` and `GRANT askhava_app TO askhava_migrator WITH INHERIT FALSE, SET TRUE`.

Running it twice gives rc=0 both times.

Each module's first migration does:
- `CREATE SCHEMA IF NOT EXISTS x`
- `GRANT USAGE ON SCHEMA x TO askhava_app`
- `ALTER DEFAULT PRIVILEGES IN SCHEMA x GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO askhava_app`

Each append-only table gets `REVOKE UPDATE, DELETE, TRUNCATE ... FROM askhava_app`.

**What held:**
- `sqlx migrate run` as the migrator applied 5 migrations in 0.16 s. `server migrate` took 0.216 s and was a no-op the second time.
- `#[sqlx::test]` ran as `askhava_migrator` with CREATEDB.
- Identity columns needed no grant on their sequences.
- `query!("SET ROLE askhava_app")`, `TRUNCATE` and `ALTER` all work inside `query!`, so `raw_sql` is not needed.

Exact errors as the app role (all SQLSTATE 42501):
- `permission denied for table audit_log` (UPDATE and TRUNCATE)
- `permission denied for table ledger_entry` (DELETE)
- `must be owner of table audit_log` (ALTER)
- `permission denied for schema core` and `permission denied for schema public` (CREATE TABLE)
- `server migrate` run as the app role: `permission denied for schema public`

## 2. Worker claim loop (JOB-006)

**Built:**
- `core.task` with these columns: kind, an IDs-only jsonb payload, run_at, attempts/max_attempts, lease_owner (uuid), lease_until, last_error, done_at, dead_at, dedupe_key. It has a unique index on the dedupe key and a partial due-index.
- `app/core/src/tasks.rs`: enqueue (`ON CONFLICT (dedupe_key) DO NOTHING RETURNING id`), claim, fenced finish/fail/renew, release_leases, reap_expired.
- `app/core/src/worker.rs`: a `Registry`, then `run_worker` with a `JoinSet` behind a `Semaphore`, idle backoff, lease renewal at half-life, a per-handler timeout, drain-then-release on shutdown, and an injected clock.
- The claim is the brain's shape: `UPDATE … WHERE id IN (SELECT … AND attempts < max_attempts AND (lease_until IS NULL OR lease_until < $3) ORDER BY run_at LIMIT $4 FOR UPDATE SKIP LOCKED)`.
- `register_handlers()` now returns the `Registry`. Tests share it through a `OnceLock` because of the mint (D-488).

**Results (`tests/integration/tests/task_queue.rs`):**
- **100 tasks of 20 ms, 2 workers × 4:** 1.02–1.03 s. Splits were 68/32, 71/29 and 69/31. 100 runs over 100 distinct tasks. 20 of 20 repeat runs were green.
- **1000 instant tasks:** 2.47–2.88 s (about 350–400 tasks/s), split roughly 516/484. Exactly once every time.
- **Expired lease:** reclaimed at t+31 s with attempts=2. The old owner's `finish` returned false and its `fail` returned `LeaseLost`.
- **Duplicate dedupe key:** refused (`None`), count stays 1.
- **Failing task:** backed off (no claim before `retry_at`), then dead-lettered at attempts=3 with last_error "probe asked to fail".
- **Real `worker` binary:** ran 20 probe tasks. A task with an unregistered kind got `last_error` "no handler registered for this kind". SIGTERM gives exit 0 with no leases left.

## 5. Migration order and cross-schema checks (SEC-029, T175)

**Added to `tests/integration/tests/architecture.rs`:**
- file names must be `0NNN_<slug>.sql`;
- numbers strictly increasing, no duplicates;
- first line must be `-- <module> (T###)`, naming a real module;

## 6. Non-literal `sqlx::query` check

Clippy has no lint for this. **New fact:** sqlx 0.9 already refuses dynamic strings at compile time:
- `sqlx::query(&s)` and `raw_sql(&s)` give `E0277: dynamic SQL strings should be audited for possible injections`;
- `pool.execute(sql.as_str())` gives `E0597`.

What still compiles and needs the scan:
- `sqlx::query(sqlx::AssertSqlSafe(s))`
- the function form with a literal
- `Executor` with a leaked `&'static str`

**Built:** a lexer-based scan (comments removed, string bodies blanked, ~80 lines; `syn` is not on the allow-list). It flags:
- the `sqlx::query`/`query_as`/`query_scalar`/`*_with`/`raw_sql` function forms, telling literal from non-literal;
- `AssertSqlSafe`, `QueryBuilder`, `sqlx::Executor` and `query_unchecked!`;
- `use sqlx::{…query…|Executor}`;
- executor methods called directly on an identifier (`pool.execute(`).

The planted cases are all caught, and doc comments, block comments and strings containing the patterns are not flagged.

**False-positive risk:** `let q = sqlx::query!(…); q.execute(&pool)` would be flagged by the identifier-receiver rule. A macro that generates sqlx calls hides them from the scan.

## 10. Deviations the plan takes (D-491)

1. **The migrator role must be the role that runs migrations, including in tests.**
   - **Plan:** brain P3/P4 (`docs/brains/postgres-operations.md:56-66`) shows `CREATE SCHEMA … AUTHORIZATION askhava_migrator` and `ALTER DEFAULT PRIVILEGES FOR ROLE askhava_migrator`.
   - **Failed:** run as `root` or `askhava_ci`, these give `must be able to SET ROLE "askhava_migrator"` and `permission denied to change default privileges`.
   - **Did instead:** plain `ALTER DEFAULT PRIVILEGES IN SCHEMA x` (applies to the current role), with every `DATABASE_URL` used for migrations being `askhava_migrator`.
   - **Smallest fix:** the brain shape loses `FOR ROLE` and `AUTHORIZATION`; architecture section 5 says local, CI and test `DATABASE_URL`s connect as `askhava_migrator`.
2. **Nothing creates the two roles.**
   - **Plan:** `scripts/smoke.sh:30-35` creates only `askhava_ci`, and no task owns a bootstrap script.
   - **Failed:** the first migration's `GRANT … TO askhava_app` fails with `role "askhava_app" does not exist` in every session.
   - **Smallest fix:** T012 owns `scripts/bootstrap_roles.sql`; `smoke.sh` (a harness change) and T169's `ci.yml` run it before `sqlx migrate run`.
3. **The test role needs three privileges the plan does not list** (it says only CREATEDB):
   - CREATEDB, or you get `permission denied to create database`;
   - CREATE on the master database, because sqlx 0.9 creates `_sqlx_test` there (`sqlx-postgres/src/testing/mod.rs:138`);
   - SET on the app role, or you get `permission denied to set role "askhava_app"`. The fix is `GRANT askhava_app TO askhava_migrator WITH INHERIT FALSE, SET TRUE` (PostgreSQL 16), on build and CI clusters only.
4. **The migrator needs CREATE on `public` for `_sqlx_migrations`.** On a host-created database, `server migrate` fails with `permission denied for schema public`. **Fix:** the bootstrap grants it.
5. **The release step's credentials are unspecified.** Section 9 says migrations run "with the migration role", but web, worker and the pre-deploy step share one set of service variables. **Fix:** a separate optional setting, e.g. `ASKHAVA_MIGRATION_DATABASE_URL`, read only by `server migrate`. Not verified on Railway.
6. **T012's acceptance names tables that don't exist yet.** It tests that ledger and audit rows are append-only, but those tables come from T067 (0099) and T015 (0020). **Fix:** drop that clause from T012; T067 already owns `ledger_append_only.rs`, and T015 has `audit_log.rs`.
7. **A shared core helper can't hold SQL for another module's table.** This affects:
   - the JOB-004 "row-lock helper every status change uses" (T012 goal);
   - the webhook dedupe helper that writes "in the calling module's own `webhook_event` table" (architecture section 5, T014).

   Literal macros plus the own-schema rule make one shared SQL statement impossible. **Fix:** core offers only the `Guarded<T>` outcome type and the convention; each module writes its own guarded `UPDATE` and its own `INSERT … ON CONFLICT DO NOTHING RETURNING`.
8. **sqlx 0.9 test database names are a hash of the test path, shared across the cluster.** A database left by a failed run as another role blocks later runs with `must be owner of database _sqlx_test_eK5f…`, and two sessions on one cluster would collide. **Fix:** a prompt note (always use one role; clean leftovers in `smoke.sh`).
9. **tokio's `sync` feature is not declared** (the section 11 tokio row lists no features). The worker's Semaphore and watch compile only because sqlx enables `sync`. **Fix:** list the tokio features `macros, rt-multi-thread, signal, net, time, sync`.
10. **`Settings::from_iter` fails clippy `should_implement_trait` under `-D warnings`.** I used `#[expect(…, reason)]`. **Fix:** rename it `from_pairs`.
11. **`deny_unknown_fields` cannot apply to the whole environment** (PATH, HOME, RAILWAY_*), and serde's error messages echo the value. **Fix:** architecture section 5 says unknown keys are refused within the `ASKHAVA_` prefix and the parser is hand-written.
12. **`-- no-transaction` must be the first line.** sqlx checks `sql.starts_with("-- no-transaction")` (`sqlx-core/src/migrate/source.rs:234`). With the owner comment first, I got `CREATE INDEX CONCURRENTLY cannot run inside a transaction block`. **Fix:** allow the owner comment on line 2 after the directive (architecture section 2, brain P2, and the T175 check).
13. **"No gaps" in migration numbers contradicts D-485.** The real plan has 33 gaps among 57 migrations, so I implemented "strictly increasing, no duplicates". Renumbering after any deploy breaks the database: `migration 21 was previously applied but is missing in the resolved migrations`. Adding a lower number later does apply (verified with 0050 after 0098). **Fix:** freeze migration numbers from the first deploy to the test project.
14. **SEC-029 and TD-SEC-10 disagree.** SEC-029 says "only SQLx query macros"; TD-SEC-10 fails only "SQL not a string literal". I implemented the strict reading. **Fix:** align TD-SEC-10 to name the function form, `AssertSqlSafe` and `Executor`.
15. **`architecture.rs` grew from 278 to 781 lines; T175's budget is 200.** Clippy's `excessive_nesting` counts an if/else inside nested loops, and `too_many_lines` applies to test functions, so planted fixtures must be split into helpers. **Fix:** raise T175's line budget to about 800, or split the checks into a second owned test file.
16. **The web binary needs SIGTERM handling.** Exit 137 in a container otherwise. **Fix:** a T009 prompt note; brain 3.10 already has the right shape.
17. **The web binary must bind `0.0.0.0:$PORT`.** The spike bound `127.0.0.1:3000`. Now it uses `Settings.port`.
18. **T074 gaps:**
    - `cargo build -p askhava-server --bin rules_bridge` compiles all 19 crates and their query macros, so `twin.yml` needs `SQLX_OFFLINE=true`.
    - There is no JSON-schema crate on the allow-list, so the Rust side needs the hand validator.
    - serde's `flatten` does not combine with `deny_unknown_fields`, which is why the request shape is `{id, call, args}`.
    - In the working tree, T074 now owns the schema and the Python test, but the Rust contract test file still has no owner.
19. **Docker gaps:**
    - cargo-chef 0.1.78 (2026-08-12, Apache-2.0 OR MIT) is not in section 11 or on the allow-list.
    - Debian 13's package is `libssl3t64`, not `libssl3`.
    - `rust-toolchain.toml` would make rustup download clippy and rustfmt inside the image; I set `RUSTUP_TOOLCHAIN` instead (my inference, not built).
    - Anonymous Docker Hub requests hit 429, so CI needs an authenticated login or a mirror.
    - No `# syntax=` line, since that line pulls an image.
20. **Prompt note only:** in `query!`, a bind parameter inside `CASE` needs an explicit `::timestamptz` cast, otherwise `column "dead_at" is of type timestamp with time zone but expression is of type text`.
