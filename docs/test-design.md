# Ask Hava test design

Written in kit step K5 (`BUILD_BRIEF.md:599`; `sources/02_build_plan/Kit_Plan_Before_Coding.md:34`). It says what is tested, at which layer, against which requirement, and who writes and runs it. Tests are designed per **behavior, boundary, failure and invariant**, never one per requirement (stress-test F17, `sources/04_reviews/ChatGPT_Build_StressTest_Report.md:76`). Every requirement ID in `docs/spec/` appears in at least one entry below or, for A11Y, in the section 6 table (whose rows are the accessibility tests' IDs for rule 2: a test names its section 6 row by its first words, D-482). The twin's warnings and the hard-failing `Twin` check are in `docs/twin-warnings.md`. Decisions are D-101 to D-110 in `docs/decisions.md`; the round-2 simulation fixes changed or added entries under D-127 to D-162 (D-162 lists them); the business-side fix plan changed or added entries under D-172 to D-207; the three-angle fix plan changed or added entries under D-208 to D-267.

---

## 1. Rules for every test

1. **Assert what the outside world sees.** A test passes on what the fake carrier delivered, what Stripe's mock recorded, what the page shows, what the database and audit log hold; never on "function X was called". This is how the twin's checks work (`sources/01_spec/hhq_twin/README.md:53`) and why they catch bugs the app's own labels hide.
2. **Name the rule.** Each Rust test carries a doc comment `/// TD-FEE-01; FEE-001, ...` (and each Playwright or pytest test the same IDs in its title or marker); a docs test fails on a test file that names none. The test name says the case (`exactly_500_00_is_the_75_tier`), not the function (D-453).
3. **Boundaries both sides.** Every number in the spec is tested at, just under and just over the edge (amounts to the cent, times to the second).
4. **Failures are first-class.** Every outside call has at least one test where the vendor errors, times out, answers twice or answers late.
5. **Fake data only** (`BUILD_BRIEF.md:66`; PRIV-019). Fixtures come from one generator module: names from a fixed fake list, phones in the fictional `555-0100` to `555-0199` range under area codes in the quiet-hours table (for example `+1 928 555 0142`), emails at `example.com`, streets like "1 Test Way" (D-109). No real job text, photo or person is ever pasted in.
6. **Time is injected.** Tests use the `core` clock (`docs/architecture.md` section 5) and advance it; no test sleeps. Timers fire by running due tasks after advancing the clock.
7. **Deterministic in `Ci`.** proptest runs with a fixed seed in `Ci` and randomized with more cases in the nightly run; any failing case found at night is committed to the test's `proptest-regressions` file and kept (D-101, D-453).
8. **Tests are owned.** A test changes only with its owning task or through a spec change logged in `docs/decisions.md` (`BUILD_BRIEF.md:69`). A wrong expected value is fixed in the spec first, then the test.
9. **Reviewers judge assertions, not counts.** The fresh-eyes reviewer (`BUILD_BRIEF.md:249`) checks that each test would fail if the rule it names were broken. A test with no assertion on an outside effect, or that passes with the rule deleted, is sent back.

## 4. Deliberate-break tests (mutation)

`BUILD_BRIEF.md:472` requires that breaking the 4-month rule or the license filter turns tests red; the Kit Plan makes it K5's done criterion (`sources/02_build_plan/Kit_Plan_Before_Coding.md:34`). K5 extends the same treatment to fee tiers, consent and opt-out, and quiet hours (D-108).

**Two mechanisms (D-108):**

- **Named mutants** (`tests/mutation/mutants.toml`, protected): each entry gives a file, an exact text replacement and the tests that must fail. `scripts/run_named_mutants.py` (T056) applies each one in place in the working tree with one shared `CARGO_TARGET_DIR`, runs only the named test binaries (`cargo test -p <crate> -- <test>`), restores the file, and fails `Ci` if any mutant survives. On a PR it runs only the mutants of files that PR changed; nightly it runs the full list; a PR touching `app/payments/src/rules.rs` must finish the step in under 10 minutes (D-481). The task that writes the code writes its mutants; the list below is the minimum.
- **cargo-mutants** (nightly) on `app/payments/src/rules.rs`, `app/catalog/src/rules.rs`, `app/licensing/src/rules.rs`, `app/quotes/src/rules.rs` (matching), `app/messaging/src/rules.rs` (quiet hours, opt-out words) and `app/intake/src/rules.rs` (consent, cancel intent). `tests/mutation/mutants.toml` lists the files; the in-crate tests run against each mutant (D-481). Every surviving mutant is either killed by a new test or listed in `tests/mutation/equivalent.toml` with the reason, after an Opus review.

## 5. The four end-to-end journeys

Playwright (TypeScript) against `web` and `worker` with every adapter on its stand-in, a real local PostgreSQL, and a test-only control router (advance the clock, read the fake carrier's delivered messages, read stripe-mock's records). The control router is compiled out of the release binary under the Cargo feature `test-control` that SEC-035 names and, where compiled in, accepts only the per-run bearer secret; TD-SEC-05 and TD-SEC-15 check it is absent in live configuration and in the release build (D-491). Each journey also runs keyboard-only and with axe at three widths (section 6), so the same steps feed `Ci` and `Ally` (A11Y-021). Every journey ends with the same **closing checks**: no duplicate outbound message or charge, the ledger reconciles to stripe-mock to the cent, every status change has an audit row, and no sentinel contact detail appears outside the vault (TD-PRIV-02).
