## K4 (architecture, threat model and stack versions), October 27, 2026

K4 finalizes the module boundaries fixed by `BUILD_BRIEF.md:124`–`BUILD_BRIEF.md:152` in `docs/architecture.md` and writes `docs/threat-model.md`. Each item below is a *how* choice the brief leaves open, decided by the §16 rule (`BUILD_BRIEF.md:537`).

- **D-090** Question: the brief's module list (`BUILD_BRIEF.md:128`–`BUILD_BRIEF.md:146`) has no owner for the shared job table and timers (`BUILD_BRIEF.md:108`), settings, the database session, derived IDs or rate limits, which every module needs. Choice: a shared kernel package `core` that is not a business module and owns only `core.task` (task queue and timers) and `core.rate_limit`; everything else stays in the brief's modules. Reason: putting these in any business module would make every other module depend on it and create cycles; the module boundaries themselves are unchanged.
- **D-091** Question: how is "no module reaches into another's tables" (`BUILD_BRIEF.md:126`) enforced, and how does a lower module tell a higher one something (for example Stripe's payment result reaching `picks`)? Choice: one Postgres schema per module; modules import only lower layers' `api.py` (layers in `docs/architecture.md` section 4); an import-and-schema test built on Python's `ast` (no new library) fails on cross-schema foreign keys, imports of another module's internals and upward imports; upward signals are `core.task` events carrying IDs only, with handlers registered in `app/main.py`. Reason: makes the boundary checkable by a test in `Ci`; events keep the import graph one-way.
- **D-092** Question: how are append-only records (ledger, audit log, consent and opt-out events; `sources/01_spec/Havasu_Home_Quotes_Technical_Blueprint_v9.3.md:94`, `sources/01_spec/Havasu_Home_Quotes_Technical_Blueprint_v9.3.md:96`) protected from edits? Choice: two database roles: a migration role that owns the schemas and runs Alembic, and an app role used by `web` and `worker` with no `UPDATE` or `DELETE` on append-only tables. Reason: an application bug or injection can't rewrite money or audit history (threat T6); smallest change that adds a database-level guard.
- **D-093** Question: PRIV-004 lets only "the messaging and release code" read the vault (`sources/01_spec/Havasu_Home_Quotes_Technical_Blueprint_v9.3.md:85`), but masked calls must dial the homeowner (CALL-002), the homeowner portal shows the homeowner their own data (PRIV-021), and raw message text may contain names and addresses. Choice: plaintext vault reads only through `privacy.api`, by `messaging` (sending), `picks` (release), `calls` (bridging a call; the number goes straight to the voice adapter), `portals` (the signed-in homeowner's own record, and what `picks` released to a business) and `privacy` itself (scrub, purge); every read is audit-logged with its purpose. Raw inbound and outbound message text and web-chat text are stored in the vault (`privacy.message_body`) and cut to the template ID after 30 days (TXT-020). Fields are AES-256-GCM with the table, column and row as associated data and a key version; phone lookup uses an HMAC blind index under a separate key. Reason: keeps PRIV-001's "only in the vault" true for free text, and keeps the reader list as narrow as the features allow.
- **D-094** Question: where do photos, the off-database records (`sources/01_spec/Havasu_Home_Quotes_Technical_Blueprint_v9.3.md:690`) and the nightly encrypted export "to separate storage" (`sources/01_spec/Havasu_Home_Quotes_Technical_Blueprint_v9.3.md:469`) live? The sources name no storage vendor. Choice: photos are stored encrypted in the `privacy` schema in PostgreSQL; the off-database stream and the nightly export go to an object-storage bucket behind a `storage` adapter (stand-in: a local directory). The task that builds the adapter logs its client library as its own new-library entry. Reason: photos in the database need no extra vendor and are covered by backups and purge; the export and stream must survive loss of the database host, so they can't live there.
