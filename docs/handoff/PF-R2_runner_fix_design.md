## (B) Corrections to the earlier PF-R design

1. **Do not assume `checks_state` takes only the newest run per check.** It scans every projected run on the head and fails if any of them is cancelled/timed out, regardless of a successful sibling (`verify.py:111–120`). `pr_for` currently gets a default-`latest` API response (`github_env.py:1886`), whereas `green_twin_tree` intentionally uses `filter=all` and will reject an earlier red run (`1777–1802`). Preserve both strict checks; use an additional read-only evidence lookup for supersession.
2. **Do not describe `_required_checks` as interchangeable with `checks_state`.** It first reduces check runs to the **latest per name**, sorted by `started_at`, and returns `True`/`False`/`None` (`github_env.py:1826–1849`). Its cancelled/timed-out `False` may charge an empty cleanup. A separate inspection is needed to distinguish an actual failing latest check from an obsolete cancellation; do not globally redefine `False`.
3. **Revise the cleanup strategy.** A cleanup attestation on main commit `H0` cannot automatically be marked DONE based on CI for newer commit `H1`. If the *same anchored check* has a genuine newer rerun, remain MERGE_PENDING and wait for normal green verification **on H0**. If main itself moved to `H1` and made the old CI obsolete, close the obsolete empty hand-in as a **non-charged superseded attempt**, then run a *fresh cleanup certification on H1* using the existing worker/claim route. Keeping `H0` MERGE_PENDING forever or silently substituting `H1` into `_mark_done` is wrong.
4. **Update `runner/status.py`; the previous design missed it.** Keep existing Last 24 Hours legacy-row behavior, but for newly written rows show their **own** reason, not a later task-wide `last_failure`. Never put an old failure into a newer successful row in the new-format path.
5. **Do not derive history reasons indiscriminately from `task.last_failure`.** `last_failure` can contain requeue text or a prior error, and the final BLOCKED branch of `record_failure` does not update it (`cycle.py:480–487`). Use the **reason generated by that code path**; update terminal `last_failure` so it describes the last charged failure.
6. **Do not change the meaning of history `result`.** For immediate worker errors it may be `QUEUED`/`BLOCKED`, not `tests_failed`. Preserve it for compatibility. A resync may produce two entries labeled attempt 1; in STATUS these are *events/rows for the same attempted number*, not attempts 1 and 2.
7. **Include `clear_main_red` and `_push_failed` in the history write map.** Both were too easy to miss in the original row-timing design. A reverted task may get charged after its original history row was already closed; a rejected branch push may turn `MERGE_PENDING` into BLOCKED after its history row was appended.
8. **Clarify the API-error policy.** Existing `pr_for` API failure aborts its read rather than charging; `checks_on` represents unreadability as unknown. A *new* failed evidence read must not assert a successor. `_resolve_empty`'s already-existing four-hour unknown-check timeout is an independent preexisting accounting policy; do not silently change it as part of a cancellation-only fix.

### D2. Required control flow and proof boundaries

1. Normal `pr_for` reads a head `H0` and checks on **H0**. For true `failure` on a required check, use existing `record_failure`/`_close_history`. A cancellation elsewhere is **not** a blanket exemption. Do not count failed optional checks unless the existing required-check verdict already fails.
2. For a cancellation-only/timed-out-only required-check failure on **H0**, read the same PR fresh. If it now points at **H1 != H0**, the judged snapshot is stale. Stay MERGE_PENDING; on the next cycle the regular `_head_reviewed` test decides if H1 is a legitimate main update or an unreviewed push. No worker retry solely to dismiss H0's cancellation.
3. If the same PR is still at H0, a second run of **the same required check on H0** must be clearly newer **and from the same trusted app/suite** to count as a replacement. Use check `id` plus start/status information, and `filter=all` with page completeness checked. When IDs, app identity, ordering or page completeness cannot establish this, return `unknown`, not a free attempt. A replacement in progress is **pending**, never green.
4. Once the normal latest snapshot reflects the successor, judge it normally: new success -> regular pending/merge/DONE path; new failure/timed_out -> normal charge or red-main decision; new head not reviewed -> existing unreviewed-head handling. **Do not pass a filtered/collapsed check list to `verify.check_done` as if an earlier red run never existed.** `verify.check_done` and `green_twin_tree` remain unchanged.
5. On a GitHub API error in this *extra diagnostic read*, log and return `unknown`/keep MERGE_PENDING (or propagate the existing read failure without updating state). Do not turn errors into `current`, `success` or `superseded`. `run_status` for backup-runner sessions (`github_env.py:1814–1825`) remains unrelated.
6. Empty cleanup: if `H0`'s required check has an established newer rerun on the **same anchored PR head**, wait and re-evaluate `main_checks_green(H0)`; never certify H0 before ordinary success. If the check was cancelled when a successor main commit `H1` replaced it, verify ancestry and reason evidence, close that obsolete certification **without increasing `attempts`**, clear obsolete `empty_since`/reviewed-head wait fields, retain an audit row with `result='ci_superseded'`, then let the next cleanup worker hand in on fresh main. A new audit row may share the same `attempt` number (as free resync already does); it is not another paid/charged attempt.
7. Preserve `MAX_ATTEMPTS`, lane strike logic, WIP/review-head gates, exact PR identity and tree equality. No automatic re-run or auto-merge of unreviewed work.

**Important subtlety:** A failed *fresh* `pr_for` call already interrupts normal PR resolution rather than charging. A failed diagnostic read on `main_checks_green`'s path is currently `None`; after four hours `_resolve_empty` can still charge for unknown checks. That preexisting timeout policy is not evidence of superseded cancellation and is **not silently removed**. If this operational policy is also a bug, it warrants a separate decision/test, not an unreviewed timeout exemption.

### E2. Required data handling

1. **Write-time cap:** `failure_reason = str(cause).strip()[:1500]` (or an equivalent bounded, safe summary), added only when a cause **from this attempt/event** is known. Don't rely on `maxLength` in schema: the bundled validator doesn't implement it.
2. **Immediate worker outcomes** (`_after_worker`, `finish`): `tests_failed`, failed submission path/model/reviewer checks, plan-gap report, `NO_CHANGES`, `permission_blocked`, exhausted API-death *safe label*. A usage-limit hold, vendor outage or other free pause may have an audit row but must **not inherit** the previous attempt's error. Preserve the existing `api_error_free`, `plan_gap`, and `resync` markers.
3. **Deferred outcomes** (`_close_history`): the submitted worker's history entry already exists. Attach this specific CI, update, review-head, empty-hand-in or proof diagnostic to **that row** and keep `attempts` unchanged except where existing `record_failure` explicitly increments. The row's `result` is updated exactly as the existing caller currently does.
4. **Explicit/manual requeues** (`requeue`, `requeue_plan_fix`, `cycle.py:3154–3175,3262–3281`): only modify `requeues`, `reason` and `last_failure` as today. Do not create a new worker-history row or rewrite previous failure causes. D-677 may allow an attempt numbered greater than three; do not truncate history by count.
5. **Terminal BLOCKED**: distinguish the public `reason` from the retry-facing `last_failure`, but set them both to the *latest charged* failure in `record_failure` to prevent lane-strike attribution to an old cause (`_lane_outcome:1093–1095`). Other operational blocks may use a special public reason, while the history row keeps the underlying cause (plan gaps, stage proof, push permissions).
6. **Legacy state**: missing `failure_reason` is normal. Show no invented historical reasons in the BLOCKED detail; the old Last 24 Hours fallback applies **only** when the task's entire history lacks the new field.
7. **Privacy/rendering**: normalize new history detail to one line, redact with `github_env._redact` before output, escape table pipes in `status._cell`, cap output separately (120 chars in Last 24 Hours and, e.g., 200 per BLOCKED detail). The existing raw BLOCKED header is a pre-existing exposure risk; do not add a second unredacted copy of logs. An optional one-line redaction of its *message* can be separately reviewed if broader privacy hardening is approved.
8. **Do not conflate attempt rows with charged attempts:** `history[].attempt` may repeat for resync, free API retries, and the superseded-empty-certification path. Rendering and aggregation must not infer `attempts == len(history)` or enumerate rows starting at 1.

Example when an eventual third attempt is BLOCKED (note that immediate worker history `result` may be `QUEUED`/`BLOCKED`):

```text
- BLOCKED T123: Twin check failed on the reviewed head
  - Attempt 1 [QUEUED]: missing catalog fixture
  - Attempt 2 [check_failed]: Ci: migration check red
  - Attempt 3 [check_failed]: Twin: oracle not regenerated
```
